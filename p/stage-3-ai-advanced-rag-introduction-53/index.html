RAG 模型选型与运行框架 · 榜单可以信，但不能只信

本内容改编自开源项目 Easy-Vibe，为二次演绎配音版。本篇对应源文档 stage-3/ai-advanced/rag-introduction/index.md 的 5.1.2 重排模型、5.1.3 大语言模型、5.2 运行框架部分，配套音频为本目录下的 stage-3-ai-advanced-rag-introduction-53-播客.mp3。

一、这篇在讲什么

一句话概括：流程上的每个环节该选什么模型，以及整套系统要不要自己从零搭。

贯穿全文的核心提醒：

榜单可以看，但不能只看榜单。工业上的好用和分数高，不一定是一回事。

选型从来不是找「最好」，而是找「最合适」——在你的数据上表现够好、在你的预算里跑得起、在你的延迟要求内来得及，三者同时成立才算数。

二、能力地图

完成这一节后，你应该具备：

  1. 重排定位能力：理解召回与精排的分工，知道重排改变顺序、不改变内容。
  2. 榜单阅读能力：理解重排榜单的测试流程、评分机制与两组互补指标。
  3. 选型纪律：掌握「先看能不能用，再看好不好用」的筛选顺序。
  4. 生成模型选型能力：知道私有化部署与云端接口两类用法的取舍。
  5. 评测能力：能构建二十到三十题的代表性测试集，做端到端评估。
  6. 框架选型能力：能按团队储备在低代码平台与代码框架之间做选择，并知道可以混合使用。

三、重排模型 · 在召回之上再排一次序

它做什么

接收用户查询和候选文档，为每一对「查询 - 文档」计算精确的相关性分数，分数越高匹配度越好。

为什么必须分两步

阶段面对规模目标计算方式
召回海量文档快、全问题和文档各自压成向量再比距离，两者之间没有真正交互
精排几十条候选准问题和文档拼在一起送进模型，在模型内部充分比对

提示一 · 重排改变顺序，不改变内容

它救不了召回阶段就已经漏掉的东西。如果正确的那一段压根没进前五十，重排再准也排不出来。

优化有先后顺序：先把召回的网撒够大，再来谈排序有多准。

很多人一上来就加重排模型却发现没什么提升，原因往往就在这里。

提示二 · 候选数量要控制在合理区间

因为精排要把问题和文档拼接后送进模型，它算得慢但看得细：

  • 几十条是合理区间
  • 几百条会明显拖慢响应

四、重排榜单是怎么测出来的

测试流程

  1. 用向量数据库从大规模文档库检索出前 50 个候选
  2. 由待测重排模型对这 50 个文档重新排序
  3. 同时关注排序质量与推理延迟两个维度
只追求高精度而忽视响应速度 → 损害用户体验
只追求速度却牺牲排序质量 → 结果实用性下降

评分机制

针对每次查询，以一个强模型作为客观裁判，对两个不同重排模型的输出结果做成对比较，判定哪个把真正相关的文档排得更合理、更靠前。经过海量查询的持续对比，获胜频率更高的模型拿到更高分数。

两组互补指标

指标组衡量什么对应能力更关键的场景
排序精准度相关文档是否被合理置于结果前列排得准问答（用户只看前几条）
结果覆盖面能否识别出所有相关文档找得全生成完整报告（漏一份资料结论就不完整）

提示三 · 先看场景要什么，再决定优化哪一侧

排得准影响「用户第一眼看到的东西对不对」；找得全影响「系统有没有漏掉关键证据」。两者在工程上的含义完全不同。

五、生成模型 · 两类用法与四个关键点

流程末端

经过语义检索和精准筛选后，相关片段与原始问题一起整合进提示词，由大语言模型完成阅读理解、信息整合与自然语言生成。

两类用法

用法适用优势代价
私有化部署注重数据隐私、成本可控、需要深度定制数据与成本可控；主流开源系列表现优异（某系列 7B / 14B 版本在较小资源占用下有良好指令遵循与中文理解能力）需自己承担运维与升级
云端接口服务追求快速上线、弹性扩展、持续迭代省心、弹性数据在别人那里

提示四 · 私有化还有一笔隐性成本

模型不是装上就完事：要占显存、要有人调参数、要在新版本出来时决定要不要换。

选私有化之前先确认团队里有没有人能长期承担这件事，否则省下的调用费很可能被运维成本吃掉。

但如果场景对数据出境有硬性要求，这条路再麻烦也得走——这就不是成本问题，而是合规问题。

选云端模型看四件事

  1. 回答质量是否准确流畅
  2. 价格是否合理
  3. 响应速度是否够快
  4. 上下文窗口是否足够大（能放下检索回的多个文档）

第 4 点最容易被忽略：检索回五段资料，窗口只放得下三段，前面的检索做得再好也白费。

提示五 · 大小模型搭配的关键在「会不会分流」

分流判据可以是：

  • 问题复杂度：需多步推理或整合多来源 → 大模型
  • 风险高低：面向客户、出错代价高 → 大模型；内部草稿 → 小模型

规则不用一开始就完美，先定一条粗的跑起来再调。只要分流存在，成本结构就比一刀切健康得多。

六、评测 · 榜单是初筛，不是结论

通用评测基准

业界广泛认可的评测平台采用盲测对战机制：人类评估者在不知晓模型身份的情况下，对两个匿名模型针对同一提示的回复做质量比较，通过大量两两对比排名。

  • 独特价值：更贴近真实用户体验，而非单纯依赖自动化指标
  • 细分维度：推理能力、创造能力、多语言支持等
  • 规模：累计超过一百万次人类评估，涵盖五十多个主流模型

但必须做自己的测试

把榜单排名作为初步筛选依据，再结合企业特定数据做对照测试。特别是在医疗、法律、金融等专业领域，通用榜单排名与实际表现可能存在较大差异。

最佳实践

构建一个小型但代表性的测试集，包含 20-30 个典型业务问题，对候选模型做端到端的完整流程评估，而非只评估单点性能。

提示六 · 测试集的关键是代表性，不是数量

要刻意把最容易出问题的三类放进去：

  1. 答案跨多个文档的问题
  2. 资料里有相互冲突说法的问题
  3. 资料里根本找不到答案的问题
第三类尤其重要，它考验的是系统敢不敢说不知道。如果找不到答案时也能编得头头是道，前面的检索做得再漂亮也没有意义。

七、运行框架 · 要不要自己从零搭

答案通常是不需要。 业界已有多个成熟框架。

低代码 / 可视化平台

平台特色适合
可视化搭建平台 A直观界面，内置多模型接入、工作流编排、提示词管理非技术团队 / 快速原型验证
零代码平台 B与自家大模型深度集成，插件市场、定时任务、多渠道发布面向普通用户的对话应用 / 企业内部助手
节点式工作流平台 C开源，连接各类应用、接口与数据源把预处理、向量库操作、模型调用、后续动作串成自动化流程
深度文档解析平台 D专注版面分析与知识抽取多栏排版、表格密集等复杂文档
国内开源方案 E知识库管理 + 对话流程编排 + 应用发布，中文文档完善快速部署中文场景应用

代码框架

框架定位适合
检索专用框架丰富的数据连接器、索引结构、查询引擎，模块化程度高深度定制检索策略 / 集成多种数据源
通用应用开发框架生态丰富、组件齐全，支持复杂智能体与工作流编排复杂多模块应用（学习曲线较陡）

怎么选

  • 团队技术储备有限、追求快速上线 → 低代码平台
  • 需要深度定制检索框架、对接特殊数据源、优化性能细节 → 代码框架
  • 实际项目可用混合方案：低代码快速验证可行性 → 代码框架做生产级部署与性能优化
这些框架大多支持主流向量化、重排和大语言模型的快速接入，可基于前文选型标准灵活组合。

一句话：先用最轻的方式跑通，再用最合适的方式做深。

八、审查清单

  • 是否先确认召回的网够大，再加精排？
  • 重排的候选数量是否控制在几十条？
  • 是否按「能不能用 → 好不好用」的顺序筛模型？
  • 是否同时看了排序质量与推理延迟？
  • 是否根据场景决定了优化「排得准」还是「找得全」？
  • 选云端模型时是否确认了上下文窗口能放下所有检索片段？
  • 是否设计了大小模型的分流规则？
  • 是否建了 20-30 题的代表性测试集？
  • 测试集是否包含「资料里没有答案」这一类？
  • 是否做过端到端评估，而不是只测单点？
  • 框架选择是否匹配团队技术储备？

能力自测

不用真的把系统搭出来，用下面五个问题检验：

  1. 加了重排之后效果没提升，最可能的原因是什么？
  2. 你的候选文档平均两千字，选生成模型时最该先确认哪一项？
  3. 通用榜单第一名在你的专业领域表现一般，下一步该做什么？
  4. 二十道题的测试集里，哪一类题目最容易被漏掉却最关键？
  5. 团队只有两个人、两周时间，该选低代码平台还是代码框架？

能答上三个以上，说明「先看能不能用，再看好不好用」这条纪律你已经建立了。

十、时间不够时的最小可行路径

顺序动作理由
1用低代码平台跑通整条链路先证明可行，再谈优化
2用厂商默认或推荐的模型组合省去选型试错
3建一个十题的小测试集先有基线，再谈提升
4观察失败案例属于哪一类（召回漏 / 排序错 / 生成差）定位比盲目优化重要
5按定位逐项优化召回漏 → 加分块与元数据；排序错 → 加重排；生成差 → 换模型或调提示词

十一、常见误区与纠正

误区表现纠正
一上来就问哪个模型最强脱离场景谈强弱找最合适，不是找最好
召回没做够就加重排加了没提升先撒大网，再谈排序
候选塞几百条给精排响应明显变慢控制在几十条
只看榜单分数工业上不好用榜单是初筛，自己测了才算
忽略上下文窗口检索回五段只放得下三段选模型时先算容量
一刀切用同一个模型成本居高不下大小模型搭配 + 分流
只测单点性能检索好但答案差端到端评估
技术有限却硬上代码框架迟迟跑不起来低代码先验证，再深入

十二、一页纸总结

环节一句话要点
总纲找最合适的，不是找最好的
重排在召回之上再排一次序；改变顺序不改变内容
重排规模几十条合理，几百条拖慢
榜单前五十候选重排，质量与延迟双维度
指标排得准（问答）与找得全（报告）按场景选侧重
纪律先看能不能用，再看好不好用
生成模型私有化控成本与数据，云端求快与弹性
云端四看质量、价格、速度、上下文窗口
省钱大小模型搭配，关键在分流
评测20-30 题代表性测试集，端到端评估
