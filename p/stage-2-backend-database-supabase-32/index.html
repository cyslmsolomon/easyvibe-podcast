三、能力地图

完成本集学习与实践后，你应该能够：

  1. 用两种方式建表：可视化新建，或让模型生成语句后执行。
  2. 解释外键：能用「班级表 / 学生表」的例子向别人讲清引用关系。
  3. 看懂表间连线：知道连线代表字段指向另一张表的主键。
  4. 建表时一次想清三件事：列名、类型、约束。
  5. 执行插入并即时验证：每插一批就查一次。
  6. 用条件层层收窄查询：从全表到指定列、指定状态、嵌套字段提取。
  7. 安全删除：先跑查询确认范围、能更新就不删除、批量前先导出。
  8. 组织提示词让模型设计表结构：先要设计，再要实现，再要排错。
  9. 说清选型理由：掌控力与上线速度的矛盾、开源带来的迁移自由。
  10. 复述授权五步流程：重定向、授权、授权码、换令牌、建会话。
  11. 完成第三方登录配置：拿到编号与密钥，填对重定向地址。

四、逐段要点

开场 · 真正动手建第一张表

本集从建表一路走到第三方登录。两条贯穿习惯：动手前先想清数据结构；动手后先用查询确认范围再改数据。前提是先有一个可用项目。

二 · 可视化建表与外键

两种建表方式：推荐让模型生成语句后在语句执行器执行；或在数据库模块中新建表，用图形界面填写列名与类型。

外键：一个或一组字段，在子表中的值引用父表主键的值。

示例：班级表主键为班级编号（一零一 = 一年级一班，一零二 = 一年级二班）；学生表增加「所属班级编号」列，该列即外键。理解了这一点，再看数据库模块里的表间连线，就会明白连线代表的是「某字段指向另一张表的主键」。

平台中添加外键可直接选择关联表与列，无需手写语句。

三 · 建表与插入

创建表语句用于定义模式：列名、数据类型、约束。执行成功会提示脚本完成，可在表编辑器中看到新表。

插入语句用于添加数据行。执行后可去表编辑器刷新，或在语句执行器中新开窗口查询全部数据验证。

建表时一次想清三件事：列名要有意义、类型要定对（文字 / 数字 / 日期）、约束要考虑（非空、唯一）。

习惯：每插入一批数据立刻查一次，避免到最后才发现问题。

四 · 查询

四个递进示例：

  1. 返回全部行与列 —— 适合表还很小的时候；
  2. 加状态筛选 + 只取指定列 —— 结果从几十行收到几行；
  3. 叠加第二个条件（已支付）—— 条件可叠加，越精确结果越小；
  4. 从详情字段中提取商品数组 —— 说明数据库能挖掘嵌套内容。

核心思路不变：用条件不断缩小范围。入门阶段不必纠结语句内部执行顺序，结果对即语句对。

五 · 删除

硬规矩：删除前先把条件放进查询语句跑一遍，确认选中范围无误，再把同样条件用于删除。

其他要点：删除通常必须带条件，无条件删除等于清空整张表；能更新就别删除（很多时候真正想要的是改状态而非抹掉记录）；批量删除前先导出备份。

六 · 让人工智能设计表（排行榜案例）

第一轮提示词：说明「我有一个贪吃蛇游戏，目录在某处，想增加在线排行榜 + 用户登录，排行榜按用户名和邮箱显示排名，请分析需要哪些表、每张表有哪些字段」。

第二轮提示词：基于上一轮设计与建表文件，实现排行榜页面，按邮箱和用户名区分总分，并支持基于邮箱的注册登录。

实践技巧：对话轮次过多时，把建表文件作为上下文开新会话；登录实现不稳时，可附上已跑通的参考项目地址，并提醒检查连接后端的必要配置；效果不符时完整记录现象反馈给它。

验收标准：用户能完成注册登录，登录后能看到属于自己的排行榜单。

七 · 为什么选它

矛盾：想要完全掌控后端，又必须快速上线。自建后端要投入数月搭建数据库、实时同步、认证、接口、存储、定时任务、监控告警等组件；在资金与窗口双重压力下容易陷入基础设施泥潭。

平台把这些能力打包为开箱即用的服务，让团队聚焦核心功能。

同类方案：PocketBase（轻量极简）、Appwrite（跨平台适配）。综合功能完整性、生态成熟度与社区关注度，本平台更适合长期运行。

开源优势：支持私有化部署，规避闭源平台带来的绑定与高迁移成本。

选型匹配规模：个人/极小测试用超轻量方案；复杂身份系统与合规审计用企业级身份治理；验证原型与承载早期用户，本平台可支撑万级用户并灵活集成支付、邮件、内容分发等第三方服务。

务实提醒：没有银弹，关键是三个月后还能否快速迭代；选错不是灾难，代价是迁移时间。

八 · 第三方登录（授权五步）

核心是开放授权协议，本质是授权代理：允许应用访问第三方平台上的公开信息（邮箱、头像），但不暴露第三方密码。

五步（以 Google 为例）：

  1. 用户点击按钮 → 应用重定向到官方授权页面（防钓鱼）；
  2. 用户在官方页面登录并同意授权范围；
  3. 官方重定向回约定的回调地址，附带一次性、短期有效的授权码；
  4. 平台后端用授权码向官方接口换取访问令牌（令牌不在前端传输）；
  5. 平台用令牌拉取公开信息，自动创建或关联账户，生成会话，完成登录。

配套能力：完整的认证系统必须提供安全可靠的密码重置；第三方登录不能完全取代邮箱验证，因为邮箱往往是在第三方账号出问题时唯一的联系通道。

九 · 配置要点与收尾

必备两样：客户端编号（Client ID）与客户端密钥（Client Secret）。

以 Google 为例：进控制台创建或选择项目 → 配置授权同意屏幕（用户类型选外部，填应用名称与支持邮箱，授权域名添加平台域名）→ 创建凭据（应用类型选网络应用，填写已授权的重定向地址，该地址可在平台身份认证服务商页面找到）→ 创建瞬间弹出的编号与密钥务必立刻复制保存。

两个高频错误点：重定向地址必须与平台显示的完全一致（多一个或少一个斜杠都会失败）；编号与密钥只显示一次，关掉弹窗只能重新生成。

五、审查清单

  • 项目已创建且状态为可用
  • 已选定建表方式（语句执行器或可视化）
  • 列名、类型、约束在建表时已一次确定
  • 外键已建立，数据库模块中的表间连线符合预期
  • 插入数据后已立即执行查询验证
  • 查询条件已按需要从全表收窄到目标行
  • 删除前已用相同条件跑过查询确认范围
  • 批量删除前已导出备份
  • 让模型设计表结构时，提示词包含项目背景、目标功能与期望输出
  • 第三方登录的重定向地址与平台显示完全一致
  • 客户端编号与密钥已当场保存
  • 密码重置流程已验证可用

六、实践提示

提示一 · 把外键想成「指向别人的身份证」

外键不是自己的主键，而是指向另一张表主键的一列。用班级表与学生表这个例子对别人讲一遍，讲得通就说明真懂了；讲不通，说明还需要再走一遍建表流程。

提示二 · 删除前先跑一遍查询

把「删除条件先当查询条件跑一遍」写成肌肉记忆。这条规矩的成本是几秒钟，收益是避免一次不可逆的数据丢失。

提示三 · 让模型先出设计再出代码

不要一上来就让它写代码。先要表结构设计，确认无误后再让它基于这份设计实现功能。两步走的好处是，设计阶段的错误很容易改，代码阶段的错误很难找。

提示四 · 提示词里说清「验收标准」

在让模型实现登录或排行榜时，把成功标准一起写进去，例如「用户能完成注册登录，登录后能看到属于自己的排行榜单」。有明确标准，它才知道什么时候算做完。

提示五 · 第三方登录配置只盯两件事

重定向地址是否完全一致、编号与密钥是否当场保存。绝大多数配置失败都出在这两处，其余步骤照着控制台走即可。

九、常见误区与纠正

误区一：把外键当成另一张表的主键。

外键在自己这张表里并不保证唯一，它只是「引用了别人的主键」。把它和主键混为一谈，设计出来的表结构往往会出错。

误区二：建表时随便定类型，后面再改。

类型一旦定了又改，已有数据的转换成本很高，尤其是数据量上来之后。宁可建表时多花五分钟想清楚。

误区三：直接执行删除语句。

没先用查询确认范围就删除，是数据事故最常见的起点。先查后删这条规矩，值得写成团队规范强制执行。

误区四：让模型一步到位写完整个功能。

先要设计、再要实现、最后再排错，三步走的成功率远高于一次性提一个大需求。设计阶段改起来最便宜。

误区五：认为第三方登录可以完全取代邮箱验证。

第三方账号可能失效、可能被封，邮箱往往是唯一还能联系到用户的通道。密码重置与邮箱验证仍然是认证系统的必备项。

误区六：以为重定向地址差不多就行。

授权流程对地址匹配要求严格，多一个或少一个斜杠都会失败。复制粘贴比手打可靠。

十、建议的动手顺序

如果你打算跟着做一遍，建议按下面的顺序推进，每一步都验证通过再进入下一步，避免在多个环节同时出错却不知道问题在哪。

  1. 创建项目，等状态变为可用；
  2. 用语句执行器建第一张表，去表编辑器确认表已出现；
  3. 插入若干行数据，立刻查询验证；
  4. 建立第二张表与外键，在数据库模块中确认连线正确；
  5. 练习带条件的查询，从全表逐步收窄到目标行；
  6. 用「先查询后删除」的方式删掉一行测试数据；
  7. 让模型设计一个小功能的表结构，确认后再让它实现；
  8. 最后再接第三方登录，先跑通邮箱登录作为对照。

这套顺序的原则是，先建立对数据的感觉，再叠加认证与集成。跳过中间步骤直接做登录，很容易在表结构还没理顺的情况下同时遇到两类问题，排查起来非常痛苦。

  1. 建表两种方式，推荐让模型生成语句后执行。
  2. 外键是指向别人主键的一列，表间连线画的就是它。
  3. 建表一次想清三件事，列名、类型、约束。
  4. 插一批查一次，别攒到最后再验证。
  5. 查询就是不断用条件缩小范围。

  8. 选型看三点，上线速度、生态成熟度、迁移自由度。
