一、这一集在解决什么问题

几乎每个做产品的人都会纠结一个问题：我的应用到底该做在哪个平台上？

多数人的第一反应是问技术栈——用 Flutter 还是 Electron，还是做微信小程序。原文一开头就指出：这个顺序反了。

平台不是技术偏好题，它取决于三件事：用户在哪里打开软件、任务发生在什么设备上、软件需要多深的系统权限。

原文随后给出十个平台选项（网站/PWA、微信小程序、iOS/Android 原生、Flutter/React Native、Electron/Tauri、Qt/原生桌面、浏览器插件、VS Code 插件/CLI、Godot 游戏引擎、多端企业系统）、一张「第一版选型表」、四个行业组合案例，以及三个必须记住的误区。

音频稿按「三个问题 → 网页与小程序 → 原生与跨端 → 桌面两条路 → 插件与命令行 → 游戏引擎与多端组合 → 选型表与三个不要 → 收尾」重排。

一句话概括：能用链接解决的先做 Web；用户就在微信里先做小程序；需要系统权限再考虑原生；多角色就共用一个后端。

三、逐段拆解

3.1 先问三个问题

问题一：用户会从哪里打开它？

  • 搜索 / 链接 / 企业门户 → 网站或 PWA
  • 微信群 / 公众号 / 线下二维码 → 微信小程序
  • 每天长时间使用、窗口一直开着 → 桌面端
  • 工作本来就在浏览器或编辑器里 → 浏览器插件 / IDE 插件

问题二：它需要哪些设备能力？

常见误解：相机、扫码、定位不一定要原生 App。真正拉开差距的是——长时间后台运行、蓝牙与串口通信、本地大文件处理、系统级快捷键、设备驱动、严格性能要求。原则是权限越深越靠近操作系统。

问题三：谁来长期维护？

「一套代码发布多个平台」减少重复工作，但不消除平台差异：应用商店审核、登录、支付、通知、权限、文件系统、窗口行为，最后都要分别测试。

这三个问题还有一个用法——拿它们去检验别人给你的建议。反问三句「用户从哪进来 / 要碰什么硬件 / 几个人维护」，大部分站不住脚的建议自己就散了。

顺序也有讲究：用户在哪最大，设备能力次之，维护成本最后。前两个决定能不能做成，第三个只决定做得有多累。

3.2 网站 / PWA 与微信小程序

Web / PWA：第一版最省力的选择。PWA 本质仍是网站，只是多了安装到桌面、离线缓存。适合 SaaS 后台、CRM、数据看板、知识库、在线教育、预约系统、内容网站。边界是——需要长期后台运行或深度访问蓝牙、系统文件、设备驱动时，别硬把网页包装成原生。

微信小程序：优势不是「比 App 高级」，而是用户不用安装。适合会员中心、门店点单、活动报名、预约、售后工单、物流查询、轻量商城。受微信运行环境与审核规则约束。

两条补充经验：

  • 小程序适合短流程、低频次动作。用户每天要在里面待 40 分钟处理复杂任务时，它大概率会让你失望。判断标准不是功能能不能实现，而是用户愿不愿意在那个环境里久留。
  • 网页与小程序的发布都不用过应用商店审核，改个错别字当天上线。在业务未验证、需要快速迭代的阶段，这个优势比任何技术指标都重要。

3.3 原生与跨端

原生离操作系统最近：后台定位、蓝牙、健康数据、音视频、复杂动画、系统级安全。适合运动健康、导航、金融客户端、相机与剪辑工具、车机配套、蓝牙设备控制、高频消费类 App。代价是两个工程、两套发布流程、两份测试成本。

跨端（Flutter / React Native）适用条件明确：团队确实需要覆盖两端，又不想维护两套完整业务代码。大部分界面与业务逻辑共享，平台能力通过插件或原生模块接入。

必须破除的幻想：跨端不是按一下按钮就自动适配。 通知、支付、地图、权限、商店发布仍要两端分别验证；重度 3D、复杂音视频、大量平台专属能力可能要回到原生。

两个判断信号：

  • 该放弃跨端的信号：团队讨论平台兼容的时间超过讨论业务功能的时间。
  • 跨端最划算的场景：业务逻辑重、界面相对标准、平台能力用得少——电商、会员、销售拜访、现场服务、内部办公、内容社区。这些的大部分代码是表单、列表、网络请求和状态管理，恰好最容易共享。

3.4 桌面端两条路

Electron / Tauri：团队熟悉前端框架、又需要独立窗口、托盘、文件读写、桌面通知时最快。Electron 自带 Chromium 与 Node.js，生态成熟；Tauri 用系统 WebView 并通过更底层语言连接系统，包体更轻。适合协作客户端、AI 桌面助手、知识库、数据导入工具、客服工作台、内部运营工具。

Qt / 原生桌面：常被误解为「工厂大屏」。实际用于设备控制台、医疗影像、汽车诊断、实验室软件、交易终端、工程设计工具、长期运行的桌面客户端——共同点是要连串口、工业总线、控制器、仪器或本地数据库，还要跨桌面系统与嵌入式设备稳定运行。

边界与提醒：

  • 需要极低内存、复杂图形、设备驱动或严格实时响应时，仅靠 Web 桌面方案不合适。这不是性能优化能解决的，是架构层级不匹配。
  • Electron 类方案上手快，但客户端装在用户机器上，升级不像网页改完就生效。做之前先想清楚怎么分发、怎么强制升级、出问题怎么回滚。

3.5 浏览器插件与 VS Code 插件 / CLI

浏览器插件：用户工作本来就在网页里时，别再让他复制、切系统、粘贴、提交。插件可直接读取当前页面，在侧边栏或右键菜单完成下一步。适合翻译、密码填充、销售线索补全、客服知识助手、合规检查、数据采集、内部流程快捷入口。

红线：插件权限很敏感，只申请真正需要的站点与能力，共享密钥必须放在企业后端。 需要脱离浏览器独立运行时，插件不是合适的容器。

VS Code 插件 / CLI：面向开发者的工具应出现在他们已工作的地方。要读当前文件、展示诊断、提供编辑器交互 → 编辑器插件；要进脚本、CI、批处理 → CLI。适合代码规范、依赖升级、脚手架、发布检查、数据库迁移、内部平台接入、AI 编程助手。

值得学的组合：很多工具最后会同时提供插件与 CLI——一个管交互，一个管自动化。 自己做内部工具时可照抄：核心能力做成库或命令，上面再挂界面。

另外，别小看 CLI 的生命力——界面会过时，插件市场会改规则，但一条能写进脚本的命令往往能用很多年。

3.6 游戏引擎与多端组合

Godot 等游戏引擎：横版、像素、3D 都需要持续更新画面并处理输入、碰撞、动画、声音、关卡。引擎已把这些能力放进同一编辑器，比从网页或原生 UI 框架里重新搭游戏循环合适。适合独立游戏、教学游戏、互动展览、产品演示、轻量 3D。但发布时桌面、Android、iOS、Web 仍要分别导出并实测；选了引擎不代表美术、玩法和性能优化会自动完成。

多端企业系统：消费者、现场员工、运营、管理者的工作环境不同，强迫所有人用同一种客户端体验通常很差。常见组合——小程序服务消费者、移动端服务现场人员、Web 后台服务运营、桌面端连本地文件或设备，下面共用统一身份、业务 API、数据库、文件存储、审计日志。

重点：真正需要共享的是业务规则和数据，不是每个端的界面代码。 而且后端边界必须先稳定——多端铺开后，任何接口改动都要同时改好几处；边界没定就铺开，会陷入「改一个字段要发五个版本」的痛苦状态。

三个不要：

  1. 一套代码不等于一次测试——跨端能共享代码，但不能替你完成权限、支付、通知、窗口、应用商店和真机兼容测试。
  2. 企业软件不等于工控软件——CRM、审批、排班、售后、知识库、零售会员都只属于企业使用场景；只有真要连设备、协议、实时数据或本地大文件时，Qt 与原生桌面才自然成为优先项。
  3. 不要第一天就做全平台——同时做五端，很容易得到五个都不完整的版本。

更隐蔽的坑：五个端都做了六成，看上去进展喜人，实际上一个完整业务闭环都没跑通。 没有闭环就收不到真实反馈，剩下四成该往哪使劲全靠猜。一个端做到十成，哪怕覆盖面小，也能立刻开始验证——这就是「少做反而更快」的原因。

四、约束

约束一：三个问题的顺序不能反。 用户在哪最大，设备能力次之，维护成本最后。反了就容易为了省事选一个根本触达不到用户的平台。

约束二：需要系统级能力时不要硬套 Web。 长期后台运行、设备驱动、严格实时响应，属于架构层级不匹配，性能优化解决不了。

约束三：跨端前先算清平台差异的量。 通知、支付、地图、权限、商店发布都要两端验证；差异压过共享收益时，要么收窄范围，要么回原生。

约束四：多端铺开前先定稳后端边界。 接口未定就铺客户端，改一个字段要发五个版本。

约束五：插件只申请必要权限，密钥放后端。 这是安全红线，不是优化建议。

五、与 Easy-Vibe 其他章节的关系

在 Easy-Vibe 的脉络里，这一集处在一个关键位置：它是「想做什么」和「用什么做」之间的那道闸门。

前面的章节讲的是怎么把需求写清楚、怎么让 AI 帮你实现；这一集讲的是在动手之前先确定容器。经验是，需求写得再清楚，容器选错也会让后面每一步都变贵——因为平台决定了发布节奏、测试方式和迭代速度。

再往后看，这一集列出的十个选项，其实对应后面一系列具体教程（PWA、微信小程序、iOS/Android、Flutter、Electron、Qt、浏览器插件、VS Code 插件、Godot）。这一集是目录，后面那些是正文。

还有一个可以迁移的观点：「先做最短入口验证业务」和前几集讲的「先跑通一条闭环」是同一个道理。 无论是长时任务还是平台选型，先拿到真实反馈，永远比先铺开覆盖面更重要。

六、审查清单

选型之前逐条打勾：

  • 已回答「用户从哪里打开它」，并据此缩小到 1–2 个候选
  • 已列出真正需要的设备能力，区分「想当然需要原生」和「真的需要原生」
  • 已确认长期维护的人数和能力
  • 已确认所选平台的发布节奏是否满足当前迭代速度
  • 若选跨端，已列出必须在两端分别验证的功能清单
  • 若选桌面方案，已想清楚分发、强制升级与回滚方案
  • 若选插件，已确认权限最小化且密钥放在后端
  • 若选多端组合，已先定稳后端接口边界
  • 已确认第一版只做最关键的那一个入口
  • 已排除「第一天就做全平台」的冲动

七、实践提示

提示1 · 用三个反问拆解别人的技术建议

下次有人力荐某个框架，反问三句：我们的用户从哪进来？我们要碰什么硬件？我们几个人维护？三句问完，站不住脚的建议自己就散了。

提示2 · 用「停留时长」判断小程序合不合适

短流程低频次适合小程序；用户每天要在里面待几十分钟处理复杂任务，就不适合。判断标准不是功能能否实现，而是用户愿不愿意在这个环境里久留。

提示3 · 跨端的止损信号

当团队讨论平台兼容的时间超过讨论业务功能的时间，说明差异已压过共享收益。要么收窄范围，要么回原生。

提示4 · 做桌面客户端前先回答三个运维问题

怎么分发、怎么强制升级、出问题怎么回滚。这三件没想好，上线第一天就会遇到版本分裂。

提示5 · 先让一个端做到十成，而不是五个端各做六成

没有完整闭环就收不到真实反馈，剩下四成该往哪使劲全靠猜。覆盖面可以小，闭环不能缺。

八、收尾

这一集真正想留下的不是那张选型表——表随时能查。而是那个提问的顺序：用户在哪里、需要什么系统能力、谁来维护，最后才轮到用什么框架。

原文结尾那句话值得记住：平台选型不需要一次决定产品未来五年的样子。 先选一个最容易接触到用户、也最能验证核心流程的入口，把第一版做出来。真实反馈出现以后，再决定要不要增加第二个平台。

如果还是拿不准，就回到开头那三个问题。答案指向哪一端，就从哪一端开始。做完一条完整链路，比停在架构图里反复比较有用得多。
