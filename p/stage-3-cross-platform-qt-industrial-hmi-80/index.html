三、Qt 在工业界做什么

Qt 不是买来就能用的 SCADA 或 PLC 软件，而是企业拿来开发这些软件的工具。常见成品：机床、产线和包装设备的 HMI 操作面板；控制室的 SCADA 监控、趋势和报警客户端；CNC 控制面板和机器人示教器；工程机械、农业机械和船舶的驾驶室显示终端；设备配置、诊断、维护和远程运营工具；数字孪生、产线仿真和设备群管理平台。

官方案例可见 Siemens SIMATIC Unified Comfort Panels、DMG MORI 的 CELOS 机床操作系统、BOMAG 的 myCOCKPIT、Parker Application Designer 等真实产品。共同点：把复杂状态变成操作员能迅速看懂的界面。

四、五个案例的要点

  • BOMAG myCOCKPIT：压路机等工程机械的驾驶室界面。驾驶员要快速看到作业参数、车速、温度和设备状态，常用操作要足够大，戴手套仍易点击。显示屏只是整机一部分，需与控制器、摄像头、传感器和车辆总线协同。使用 Qt 超过十年，同一套思路适应不同尺寸与设备。
  • Agile Robots 示教器：操作员配置动作、查看程序和排查问题的手持终端。一套 Qt 代码同时服务 Windows 和 Linux，研发测试界面与生产现场保持一致。
  • Parker Application Designer：给设备制造商的 HMI 设计工具，让厂商自组按钮、仪表和应用再部署到显示终端。看点不是图标而是平台化——同一块终端装不同应用，不必为每款机器重做整套界面；案例亦介绍 QML 的作用。
  • Blue Ctrl X-CONNECT：船舶自动化平台，把电力、推进、压载水和报警收进一套界面。适合观察信息层级：总览页只放最重要状态，报警页强调异常，详细参数进下一层。
  • Precision Planting 20|20：农机实时监视器，持续显示多行作业数据、速度、覆盖和异常位置。与普通数据大屏的区别：驾驶员正在操作机器，不能停下来读长段文字，颜色、位置和报警必须一眼看懂。

看案例的正确姿势：不照抄深色背景或仪表盘，学四件事——最重要的状态放在哪里、异常怎样被看见、操作是否需要二次确认、设备离线后页面怎样告诉用户。抄得走配色，抄不走信息层级。

提示一 · 用四个问题审查任何工业界面

拿到一个工业界面设计，先用四问过一遍：总览页能否三秒看出设备状态；异常是否用颜色、位置和层级突出；危险操作是否有确认但不泛滥；断线时是否明确提示且过期数据不冒充实时值。四问全过，再谈视觉风格。

五、上位机与下位机

定义：上位机是人观察和管理设备的入口，运行在工业电脑、工程师站、控制室工作站或设备触摸屏上，Qt 最常出现在这一层；下位机直接靠近生产设备和现场信号，如 PLC、MCU、运动控制器、机器人控制器、数据采集板和远程 I/O，按固定周期读输入、控输出，负责运行顺序、速度控制、条件判断、安全联锁和故障保护。

相对性：上与下指控制链路中的位置，不是电脑大小或高级程度。同一台 PLC 面对控制室 SCADA 时是下位机，管理伺服驱动器和远程模块时又在上层。判断依据是它在当前系统负责哪一层，不是外形。

易混淆点：下位机不等于低配置电脑——性能很强的机器人控制器仍是下位机；很小的触摸屏也可能是上位机。

配合方式：通过串口、TCP、CAN、Modbus、OPC UA 或厂商协议通信。典型流程：操作员点击「启动水泵」→ 上位机发请求给 PLC → PLC 检查急停、阀门、液位 → 条件满足才启动，不满足则拒绝并回传原因。下位机负责把设备控制正确，上位机负责让人看得懂、管得住、查得到。

教程映射：本地 TCP 模拟器扮演简化下位机（持续发压力、温度、振动），PySide6 客户端是上位机（连接、显示趋势、触发报警、保存记录）。模拟器仅用于学习通信与断线处理，不具备真实 PLC 的实时控制与安全联锁；接入真实项目时换成 Modbus TCP、OPC UA 或企业接口，界面与数据处理思路不变。

提示二 · 安全逻辑永远放在离设备最近的一层

新手最常见的错误是在上位机里写安全逻辑。界面再漂亮也挡不住程序崩溃；急停、安全联锁、电机保护必须留在 PLC、MCU 或机器人控制器，上位机只发请求。这样界面退出或网络断开时，设备仍能自行进入安全状态。

六、上位机的数据从哪里来

Qt 只负责把数据接进来、处理好、显示给人看。温度、压力、转速通常不是 Qt 生成，也很少让上位机直连每个传感器；常见来源是 PLC、机器人控制器、仪表和数据采集模块。

来源常见接法拿到什么
PLC、仪表、运动控制器Modbus TCP、Modbus RTU、厂商协议温度、压力、开关状态、转速、故障码
机器人、CNC、专用设备厂商 SDK 或网络接口当前程序、坐标、运行阶段、报警
OPC UA 服务器或边缘网关OPC UA、MQTT多台设备整理后的实时数据与连接状态
MES、工单、企业后端HTTP API、WebSocket工单、配方、权限、维护任务
历史数据库SQLite、SQL 或企业查询接口报警历史、趋势、操作记录、生产统计

三要素：企业项目特别关心数值、采集时间和数据是否可信。显示 0℃ 可能是真零度，也可能是刚断线；只传数字无法区分，必须同时记录时间、连接状态和数据质量，过期数据明确显示「离线」或「数据已过期」，不能冒充实时值。

简单分工：设备状态从控制器或网关来，工单和配方从企业后端来，历史记录从数据库来。第一次接真实设备不必学遍所有协议——设备开放什么就先按说明书读什么，Qt 负责连接和展示。

提示三 · 给每个数字配一个新鲜度

设计上位机数据流时，为每个数值附带采集时间与质量标记，界面按新鲜度渲染：实时值正常显示，过期值置灰并标注，断线值明确提示。这一个机制能避免「界面显示正常、现场早已停机」的事故。

七、用什么语言写

语言和工具通常负责什么
C++设备通信、数据处理、业务逻辑，性能与内存敏感部分
QML / Qt Quick触摸屏、仪表盘、动画、随屏幕尺寸变化的现代界面
Qt Widgets + C++工程师工具、诊断软件、需长期维护的传统桌面客户端
Python + PySide6内部工具、测试诊断、数据处理较多的客户端、快速第一版

新嵌入式 HMI 的常见做法是 QML 负责界面、C++ 负责业务与设备通信，设计师调页面、底层协议与控制逻辑保持清晰。本篇选 PySide6（Qt 官方 Python 绑定，非仿制框架），便于第一次跟随做并快速验证界面、TCP 通信、报警和 SQLite。进入企业项目后不必因「工业软件」四字立刻全改 C++——先按刷新频率、数据量、启动速度和团队维护能力测试，再决定哪些部分迁移。企业后端也不一定用 Qt，可通过 OPC UA、MQTT、HTTP 等接口连接 Java、Go、C#、Python 服务。

提示四 · 选型跟着测量数据走

语言选型的依据是测量而非标签：统计界面刷新频率、单次数据量、启动耗时和团队维护成本，再决定哪些模块需要 C++。很多内部工具用 Python 完全够用，把工程师时间花在协议和报警逻辑上回报更高。

八、企业怎样保证它一直能用

  1. 守住控制边界：急停、安全联锁、电机保护放在 PLC/MCU/机器人控制器；Qt 上位机只发操作请求，不作为设备安全的唯一保障。
  2. 专门测试故障：拔网线、关模拟器、发错误数据、写满数据库，看界面是否卡死、能否重连、报警是否留记录；通信与耗时任务不能堵住界面线程，每次请求都要有超时、错误提示和恢复办法。
  3. 干净电脑验证：固定 Qt 与依赖版本，生成可安装包，放到无开发环境的电脑上连续运行。检查项：重启后能否恢复；断网断电后数据是否损坏；日志是否无限占满磁盘；新版本失败能否回退；安装包是否完成签名；商业版/开源版是否按许可证要求发布。
  4. 现场可维护：保留日志、崩溃信息和版本号，问题可回答「哪台设备、哪个版本、什么时间、发生了什么」，而非一句「软件打不开」。

这才是企业项目所说的「稳定」——不是演示十分钟没有报错。

提示五 · 把「拔网线」列进验收清单

任何上位机交付前，验收清单必须包含故障注入：拔网线、关服务器、发错误数据、写满磁盘。只在正常页面点一遍的验收，等于把第一次故障留给生产现场。

九、审查清单

  • 已明确 Qt 是开发工具而非成品软件，能说出六类常见成品
  • 看案例时关注信息层级、异常可见性、二次确认、离线提示四件事
  • 能解释上位机与下位机的定义及其相对性
  • 安全联锁与急停留在下位机，未在上位机写安全逻辑
  • 数据流包含数值、采集时间、数据可信三要素
  • 过期与断线数据有明确标识，不冒充实时值
  • 语言选型有测量依据（刷新频率、数据量、启动速度、维护成本）
  • 已评估官方绑定与 C++ 的迁移边界
  • 故障测试覆盖拔网线、错误数据、数据库写满
  • 请求有超时、错误提示和恢复办法，界面线程未被堵
  • 干净电脑连续运行验证通过，含重启与断网断电
  • 日志有上限，版本可回退，安装包已签名
  • 现场问题可按设备、版本、时间、现象四要素定位
