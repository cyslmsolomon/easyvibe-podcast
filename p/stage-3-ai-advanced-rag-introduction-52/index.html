检索增强生成的三代演进 · 从「能检索」到「会编排」

本内容改编自开源项目 Easy-Vibe，为二次演绎配音版。本篇对应源文档 stage-3/ai-advanced/rag-introduction/index.md 的 4.1 - 4.3 三代演进与 5.1 模型选型部分，配套音频为本目录下的 stage-3-ai-advanced-rag-introduction-52-播客.mp3。

一、这篇在讲什么

一句话概括：从「能跑」到「好用」之间，检索增强生成要补的到底是什么。

整条演进线的核心不是检索本身，而是三件事：

把该存的存好，把该问的问清，把检回来的用对。
代际解决的问题关键词
第一代（基础形态）有没有先查再答这条路走得通
第二代（精细化优化）准不准检索前 + 检索后双向优化
第三代（模块化）够不够用可插拔模块 + 编排 + 自我决策

二、能力地图

完成这一节后，你应该具备：

  1. 代际判断能力：能说出一个 RAG 系统处在哪一代，以及下一步该补什么。
  2. 索引设计能力：理解语义感知分块、滑动窗口、元数据附加的价值。
  3. 查询改写能力：掌握查询重写、多路查询、子问题分解、回溯提示四种手法。
  4. 上下文治理能力：理解重排、去重压缩、引用对齐为什么必要。
  5. 架构视野：知道企业级场景需要哪些模块（路由 / 多源融合 / 记忆 / 治理）。
  6. 选型能力：知道选向量化模型要看维度和上下文长度两个参数。

三、第一代 · 基础检索增强

三步走

步骤动作产出
1. 预处理与索引清洗 → 固定长度切块 → 向量化 → 写入向量库可检索的向量集合
2. 相似度检索问题向量化 → 相似度搜索 → 取回 Top-K 文本块候选片段
3. 增强生成片段 + 原问题直接拼接 → 长提示词 → 模型作答最终回答

价值

以极低门槛验证了「先查再答」有效：相比完全依赖模型内部记忆，明显缓解知识截止与部分幻觉，成为大量演示、原型与入门教程的首选。

三条局限

局限表现后果
分块粗糙固定长度切分，截断完整语义段落 / 多主题混在一块影响检索准确性，增加模型理解负担
信号单一只依赖向量相似度，不用关键词、时间戳、来源可信度、访问权限无法回答「上个月改了什么」「某部门范围内生效的规定」
不做治理噪音、重复、矛盾片段原样塞进上下文紧张的上下文窗口被低价值信息占据

提示一 · 一个方案成为教程首选，说明它简单，不说明它够用

很多人拿教程里的三行代码跑通之后直接搬进生产，然后被各种奇怪的召回失败折磨。

不是技术不行，而是用原型的标准去要求生产系统。分清你现在处在哪个阶段，比急着优化细节重要得多。

提示二 · 三条局限指向同一个根因

第一代把检索当成了一次纯粹的数学运算——算向量距离。

但真实的知识查找从来不只是比距离，你还关心这份资料是什么时候的、谁写的、能不能看、跟问题是不是真的相关。

把检索从一道算术题还原成一次有上下文的查找，正是后面两代要补的课。

四、第二代 · 检索前后双向优化

检索前 · 索引端

优化从到
分块固定长度切分语义感知分块 + 分层索引（章节 / 小节 / 段落 / 句子边界 + 滑动窗口 + 多粒度）
元数据无来源、时间、作者、主题、文档类型

滑动窗口的价值：让相邻文本块之间有重叠，即使段落被切开，两段各自仍保留上下文，不会出现半句话。

固定长度切分像是把一本书按页数均分；语义感知分块是按章节段落分，且每份都标好出处。检索从靠猜变成了靠条件。

检索前 · 查询端（四种手法）

手法核心示例
查询重写把模糊、口语化、不规范的原查询转成标准化表述「咋查明天北京的天气啊」→「查询北京市明日全天实时天气」；结合历史行为「推荐好看的电影」→「推荐某年高分悬疑题材电影」
多路查询生成多个语义相关但角度不同的查询，覆盖用户未明确的需求「如何给刚满月的宝宝拍嗝」→ 正确姿势 / 避免吐奶 / 零到一个月月龄 / 新手爸妈技巧
子问题分解复合问题拆成独立简单子查询「北京到上海高铁的班次 / 票价 / 时长」→ 三条独立查询
回溯提示先生成更宏观的上位问题，再回推检索方向「某品牌销量为何下降」→ 先问「影响新能源品牌短期销量波动的核心因素」，再检索产品更新 / 竞品定价 / 补贴政策

检索后 · 三件事

  1. 重排：用专门的重排模型或大语言模型对候选文档二次排序，修正初步排序的语义偏差，让最关键内容优先进入上下文
  2. 筛选、去重与压缩：去掉无关或高度重复的片段，缓解长上下文中部信息被忽略的问题
  3. 轻量微调 + 引用：让模型更倾向于依据检索证据作答，并附带引用或出处

提示三 · 上下文不是越大越好

去重压缩这一步常被低估。窗口塞得太满反而会让模型抓不住重点。

第二代关注的三个更大挑战：

  • 能否精准定位到真正关键的段落
  • 传给模型的上下文是否简洁有序、易于高效利用
  • 面对信息噪音、内容冲突、多资料源时系统是否稳健

五、第三代 · 模块化

三个企业级压力

  1. 同一系统既要支持简单问答，又要生成长篇报告、做代码检索、调用数据库
  2. 需要同时接入向量库、全文检索、关系数据库、知识图谱、外部搜索引擎
  3. 需要在多轮交互中保持用户偏好与历史决策记忆，并对输出做合规审核与溯源

四类典型模块

模块职责示例
查询理解与路由意图识别、问题重写、子任务拆解、路径选择「这条错误日志代表什么问题」→ 代码与日志知识库；「该行业监管新规有哪些变化」→ 互联网搜索 / 合规法规库
多源检索与融合同时查向量库、全文检索、结构化 DB、知识图谱，统一融合排序客户年度分析报告 = 成交额（业务系统）+ 项目复盘（文档库）+ 行业关系（知识图谱）
记忆与个性化长期用户画像、短期会话记忆、领域知识缓存记住某用户偏好「先结论后细节」、所在业务线与常用术语
任务适配与治理适配器约束格式语气风格；事实核查、风险过滤、引用对齐同一批检索结果 → 产品经理得到结构化需求文档模板，法务得到正式合规审查意见

提示四 · 真正的分水岭是「能不能回头再查」

传统做法是一轮检索配一轮生成就结束；模块化打破了这种单一流程。

当生成过程中发现信息不足，系统可以主动触发新的检索轮次，甚至多次往返。

再进一步的两个能力：

  • 自我决策：把握大的问题直接基于内部知识或短上下文作答；不确定时才发起检索或调用工具，保证质量的前提下节约资源
  • 假设性线索：对表达不清、信息缺失严重的查询，先由模型生成假设性答案或中间文档，再拿它当线索去检索真实文档，不断逼近可靠信息源
到这一步，它已不只是给模型补几段参考资料的组件，而是企业级智能应用的中枢式知识编排层。

六、模型选型 · 三类模型与两个参数

三类核心模型

模型职责
向量化模型把文本转化为可检索的语义向量，决定召回质量
重排模型对初步检索结果做精细筛选与重排序
大语言模型基于筛选后的上下文生成最终答案

向量化模型的两个关键参数

参数含义选型建议
维度输出向量的维度数，反映描述语义时的「特征数量」维度高 → 细节丰富、区分度强，适合医疗、法律等精准检索；维度低 → 成本低、速度快，适合千万级文档高并发强实时场景
上下文长度单次可处理的最大文本长度（词元计，1 中文词元约 1 个汉字），超出会被截断短句 / 问答对选 512-1024；论文、报告等长文本选 2048 及以上

提示五 · 这两个参数选错，后面再怎么优化流程都补不回来

分块和查询改写都是在已有向量上做文章；如果向量本身因为维度太低丢了区分度、或者因为上下文长度不足被截断丢失关键信息，上游的缺陷无法在下游修复。

七、审查清单

  • 能否说清自己的系统处在哪一代，下一步该补什么？
  • 分块是否用了语义感知策略与滑动窗口，而不是纯固定长度？
  • 文档块是否附加了来源、时间、作者、主题、文档类型等元数据？
  • 是否实现了至少一种查询改写手法（重写 / 多路 / 子问题 / 回溯）？
  • 检索后是否有重排环节？
  • 是否做了去重与压缩，而不是把候选片段全塞进去？
  • 回答是否附带引用或出处？
  • 多数据源场景是否有路由与融合模块？
  • 是否有记忆与个性化（用户偏好、业务线、常用术语）？
  • 是否有事实核查与引用对齐等治理机制？
  • 生成中信息不足时，能否触发新的检索轮次？
  • 向量化模型的维度与上下文长度是否匹配你的文档长度与精度要求？

能力自测

不用真的搭一套系统，用下面五个问题检验：

  1. 用户问「上个月那份规定改了什么」，第一代系统为什么答不好？缺的是检索还是索引？
  2. 固定长度切分把一个段落切成两半，滑动窗口是怎么救回来的？
  3. 「北京到上海高铁的班次、票价、时长」该用四种查询手法里的哪一种？为什么多路查询解决不了它？
  4. 候选片段有二十条、上下文只放得下五条，中间该加哪个环节？
  5. 文档都是上万字的论文，你选向量化模型时最该看哪个参数？为什么？

能答上三个以上，说明三代演进这条主线你已经抓住了。

九、时间不够时怎么砍出最小可用版本

优先级项目理由
必做语义感知分块 + 滑动窗口投入小，直接决定召回质量
必做建索引时带上元数据后期补元数据等于重建索引
必做至少一种查询改写用户原话直接检索的效果通常很差
次优先加一个重排环节收益明显，但需要额外模型
次优先去重与压缩上下文紧张时才显著
可后置多源融合、记忆、治理模块属于第三代能力，需求到了再做
可后置自我决策与假设性线索对工程复杂度要求较高

十、常见误区与纠正

误区表现纠正
教程跑通就上生产三行代码直接搬到业务系统分清原型标准与生产标准
只优化提示词召回失败却一直在改提示词问题常在分块与检索阶段
固定长度一刀切段落被切成半句话语义感知分块 + 滑动窗口
忽略元数据无法按时间、来源筛选建索引时就把元数据带上
拿用户原话直接检索口语化问题召回很差先做查询重写 / 多路 / 拆解
候选片段全塞进去上下文塞满，模型抓不住重点重排 + 去重 + 压缩
只接一种数据源结构化数据查不到多源检索与融合模块
先选模型再想场景维度与长度不匹配文档先看文档长度与精度要求

十一、一页纸总结

环节一句话要点
主线把该存的存好，把该问的问清，把检回来的用对
第一代三步走：切块索引 → 相似度检索 → 拼接生成
第一代局限分块粗糙、信号单一、不做治理
