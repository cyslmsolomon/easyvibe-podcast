如何开发 VS Code 插件 · Engineering Guard：从命令到安装包

一、这篇在讲什么

本篇从一个真实插件 Engineering Guard 出发，走完企业插件的完整链路：创建可调试项目、增加命令、加入本地规则、把结果放进侧边栏与问题面板、增加菜单和状态栏、让结果看得懂、把模型能力放到最后、从头验收、打包安装包、装进另一个编辑器。

开始之前先看两个已成熟的插件建立分寸感：Container Tools 没有重做 Docker，ESLint 插件没有重做检查流水线。企业插件的方法论只有一句：克制地把最常用的几步接进来。为什么拿代码检查当例子。它足够小，规则写在本机、结果一眼可见；又足够真，企业里每天都要用。学会这一条链路，换成项目模板检查、依赖检查、发布前检查，路子不变。阅读前不需要编程基础，涉及的概念都用日常语言解释。

三、两个真实插件学克制

Container Tools 覆盖编写容器描述文件与编排文件、生成容器配置、启动调试、查看容器与日志、管理镜像网络数据卷和镜像仓库。它没有替代 Docker 或云平台，而是把最常用的容器动作整理成命令和树形视图，复杂能力留在后端工具中，插件提供上下文和操作入口。

ESLint 插件读取项目安装的检查工具与规则配置，把错误直接标在代码里，并提供修复所有可自动修复问题等命令。它的价值来自一致性：规则随项目提交，编辑器按同一份配置提醒，持续集成在提交后再次检查。插件尽早反馈，流水线最后把关。

判断一个插件想法值不值得做，先问一句：团队每天重复做的是哪几步，现在散落在几个窗口里。答案越具体越值得做；问不出来，说明还没找到真问题。

提示一 · 插件是接力的，不是重做的

平台已有的功能不在插件里重做；后端继续跑后端，插件只负责连接。重做会导致两边行为不一致，维护成本翻倍。接得准比功能多更接近企业真正想要的东西。

四、内部插件的五条做法

一，能放进命令面板、侧边栏或问题面板的就沿用编辑器原有位置。二，平台与内部系统继续在后端运行，插件只负责连接。三，打开哪个仓库、文件或代码位置，就显示与这里有关的操作，不堆一排用不上的按钮。四，出错时不只报失败，还告诉用户问题在哪、下一步怎么办。五，需要登录、读取文件或连接公司系统时，把权限说清楚，不悄悄来。这五条合起来就是一个词，分寸，知道哪里是自己的边界，边界外的事交给后端和平台。

内部插件常见形态：创建符合规范的新项目、检查依赖版本、查当前服务负责人、打开内部文档、提交工单、发布前跑安全检查。先把每天重复的几步接进来即可，不必一开始上模型。

五、插件怎样进入编辑器

普通桌面插件运行在扩展宿主进程。编辑器负责界面、命令面板、侧边栏与状态栏，插件通过扩展接口注册功能。某个插件出错时，不应把编辑器主界面一起拖死。分工上，清单文件告诉编辑器有哪些命令与界面入口，插件入口执行检查，树视图或问题面板展示结果。官方示例中文件是父节点、命中位置是子节点、点击回到代码。本插件沿用原生交互，不为显示几行结果先做复杂页面。插件跑在独立进程里，出错只挂插件本身，把展示层交给原生面板也是守这条边界。

六、十关分解（上）：创建调试、命令、规则

第一关创建能调试的插件：安装当前长期支持版本 Node.js 与 VS Code，用官方生成器创建 TypeScript 插件，按 F 键加数字五调试，打开带有扩展开发宿主标记的测试窗口；调试失败只修调试配置；看到默认通知说明项目、编译与调试环境已连通。注意两个窗口的分工：原窗口写代码看日志，测试窗口当用户，验收要跑到测试窗口点。

第二关先增加一条命令：检查当前文件，运行后先显示文件名。验收两个状态，打开文件时文件名正确，未打开文件时提示请先打开文件。两个状态正常，说明插件已能读取编辑器上下文。

第三关加入三条本地规则：疑似硬编码密钥、没有超时的网络请求、字符串拼接 SQL，只扫描当前文件不上传代码。用专门测试文件每种问题放一处，三条都出现，改一处再查对应问题消失。规则不要一次加几十条，企业检查最怕什么都报、最后所有人学会忽略。每条规则要有清楚的命中条件、位置和修改建议，三样缺一样就成了摆设。

提示二 · 能复用原生位置和交互，就不要自己造

用户已熟悉问题面板的用法，插件复用即零学习成本。为显示几行结果先做复杂页面，成本花在刀背上。

七、十关分解（中）：侧边栏、菜单、状态栏、看得懂

第四关把结果显示在问题面板和侧边栏，点击跳到对应文件与行号。侧边栏先处理四种状态：还没检查、没有问题、发现问题、原文件已关闭；空状态也要告诉用户下一步做什么。第五关增加菜单与状态栏：编辑器右键菜单增加检查选中代码，无选中内容时不显示；资源管理器右键增加检查这些文件，跳过图片、依赖目录和超大文件；状态栏显示最近一次结果，点击打开侧边栏，只显示未检查、通过或问题数量，不闪烁不弹通知。入口贴着用户动作但不打扰。第六关让结果看得懂：每条结果回答哪里有问题、为什么有风险、下一步做什么，点击回到对应代码，不让用户自己搜行号。最重要的不是风险分数。

八、十关分解（下）：模型放最后、验收、打包、安装

第七关模型能力放最后：本地规则完整跑通后，才加可选的解释入口，只解释当前选中结果，无模型权限时本地检查继续工作。发送代码前明确告诉用户包含哪些内容；企业版本遵守仓库权限、组织策略与数据边界，不默认把整个项目上传外部服务。判断标准应写死在规则里，模型只做解释与润色。

第八关从头验收八项：命令面板可找到检查当前文件；无问题文件显示通过；测试文件稳定命中三条规则；点击侧边栏与问题面板结果回到正确行；编辑器右键与资源管理器多选都能运行；修复后旧问题消失；禁用模型后本地检查仍可用；重新加载窗口后命令、视图、状态栏仍存在。失败时只描述第几部失败、现象是什么，请只修复这一项。

第九关打包：先补齐名称、版本、图标、仓库、许可证和隐私说明，再用官方工具打包并排除测试数据；换配置或换电脑从安装文件安装后重跑一遍。内部可放制品库或走组织分发，公开发布再按发布文档创建发布者提交。

第十关装进另一个编辑器：打开测试代码，从命令面板运行检查，侧边栏出结果、点击回行、关掉模型本地规则仍工作，才算真的离开开发窗口。十关连起来是一条完整链路：编辑器命令，读取当前文件，本地规则，问题面板与树视图，菜单与状态栏，安装包。这个插件还不是企业级代码安全产品，但命令、规则、定位与安装包已经齐备，后续可以把规则换成公司的项目模板、规则服务、代码负责人、工单系统或发布门禁。无论接入多少能力，三件事不能丢：让用户知道插件读了什么，让错误能回到具体代码，别让本地检查因为模型不可用就一起消失。

提示三 · 本地能力是底盘，模型是选配

先做不依赖任何外部的本地能力，再谈智能。模型一抖动整个插件就像没做完。这个次序不能颠倒。落到企业场景还有一层：哪些代码算高危是团队的安全基线，应写死在规则里，不能每次问模型要答案；把判断标准变成规则，把规则交给本地，把解释和润色交给模型，各归其位，插件才既稳又聪明。

提示四 · 验收清单把大的不确定切成小的可确认

八项里七项过、只挂一项，就只修一项；一上来就说整个插件都坏，AI 只能从头猜。清单的真正用途是把交付风险切成可逐条确认的小块，也是给协作方留下的接力棒。

九、审查清单

  1. 项目用官方生成器创建，调试窗口能打开，默认通知已见。
  2. 命令验收覆盖打开文件与未打开文件两种状态。
  3. 三条规则各有清楚命中条件、位置与修改建议。
  4. 测试文件每种问题一处，增删改后命中同步变化。
  5. 侧边栏四种状态齐全，空状态有下一步指引。
  6. 右键菜单按选中条件显隐，资源管理器跳过无关文件。
  7. 状态栏只显示摘要，不闪烁不弹通知。
  8. 每条结果能回答哪里有问题、为什么有风险、下一步做什么。
  9. 模型入口可选，禁用后本地检查完整可用。
  10. 发送代码前告知内容范围，遵守仓库权限与数据边界。
  11. 八项验收逐条跑过，失败项单独修复。
  12. 元数据齐全后才打包，安装包在另一环境重跑通过。

十一、常见误区与纠正

误区表现纠正
重做平台功能插件与后端行为不一致插件只连接，复杂能力留后端
一次加几十条规则全都报等于全不报先少而准，每条可验证
规则三要素不全误报无法判断，跳不过去命中条件、位置、建议齐备
自建复杂页面展示成本花在刀背上复用问题面板与树视图
空状态留白板用户不知道下一步空状态也给指引
状态栏闪烁弹通知用户烦躁后卸载只显示摘要，安静待命
先接模型再写规则模型一抖全插件瘫痪本地底盘优先，模型选配
默认上传整个项目触碰数据边界发送前告知内容与范围
只看最终页面验收中间步骤坏掉没发现八项清单逐条跑
停在开发宿主窗口用户环境装不上换环境从安装文件重装验证
