从凭感觉写代码到规格先行：一页纸把需求说清楚

本集对应 Easy-Vibe 教程 stage-3/core-skills/spec-coding/index.md，是一次面向零基础听众的二次演绎配音版。音频里不出现代码，只讲“为什么”和“怎么做判断”。

本集定位

这一集解决的是一个非常普遍、但很少被说破的问题：同样是让人工智能写代码，为什么有的人三轮就收敛，有的人三十轮还在原地打转。差别不在模型，也不在提示词技巧，而在于动手之前有没有一份关于“预期行为”的书面约定。这一集把教程里分散在四处的知识——规格的定义、四层结构、三份文档的分工、四步写法、五段式工作流、工具选型、六种可迁移方法——串成一条从零到一的主线。

听完之后，你应该能独立完成三件事：给一个小功能写出一页可用的规格；判断自己现在缺的是澄清、模板、任务拆解还是工程纪律；以及在六种主流工具里选出一个当下真正需要的。

核心概念速查

  • 规格：一份关于预期行为的共同约定，写给人和机器一起看。
  • 三个必须回答的问题：要做什么、边界在哪里、怎样证明完成。
  • 四层结构：产品目标 → 用户行为 → 规则与边界 → 验收证据。
  • 三份文档：规格文档锚定价值，方案文档锚定手段，任务文档锚定顺序。
  • 五段式工作流：写规格 → 做方案 → 拆任务 → 实现 → 验证。
  • 三种生命周期：快照式、持续锚定式、以规格为唯一源头。

分节讲解

一、凭感觉写代码的边界在哪里

凭感觉写代码并不是错的，它在探索期非常高效。它的失效点在于“记忆不可靠”和“假设不可见”：你说过的需求散落在十几轮对话里，你和模型各自补了一部分假设，谁也没写下来。等到功能变多，两处假设冲突，就表现为“越改越乱”。规格的作用是外化这些假设，让冲突在写代码的阶段之前就暴露。

二、规格是预期行为的共同约定

注意定义里的两个词。第一是“预期行为”，它描述系统应该表现出什么，而不是代码长什么样；第二是“共同”，意味着读者既包括人，也包括后面接手的模型。三个必须回答的问题里，第三个“怎样证明完成”最常被跳过，而它恰恰决定了这个功能能不能被验收。

三、四层结构与通知中心示例

以通知中心为例：产品目标是让用户在一个地方处理重要消息；用户行为是查看、筛选、标记单条或全部已读；规则与边界是只能读自己的、失败可重试；验收证据是未读数正确变化、权限测试通过。这四层的顺序有意义，越往下越接近机器可检查的东西，因此写的时候建议自上而下，不要跳层。

四、规格、方案、任务不是同一个东西

这是本集最容易被忽视、却最省钱的一节。规格文档写“用户可以将单条通知标记为已读”，方案文档写“用某个接口更新状态”，任务文档写“先做列表，再做单条已读”。技术栈换了，方案重写；但只要用户还需要标记已读，规格里的行为就不该变。把三者混写，技术一换就会连需求一起丢掉。

五、四步写法

第一步先让人工智能提问，不要马上写代码，并明确限定“每次最多问四个、给出你的推荐”。第二步把形容词改成验收标准，判据是“能不能被看到或被测试”。第三步补齐四类边界：空状态、失败状态、权限边界、重复操作。第四步承认未知，把没答案的问题写进“未解决问题”，而不是让模型自行猜测。

六、仓库结构与五段式工作流

长期有效的项目规则放进总规则文件（例如如何跑测试、哪些目录不能改、金额怎么存），具体功能的需求放进独立的规格目录，一个功能一个文件夹。推进按五段走：写规格、做方案、拆任务、实现、验证。每一段都有明确的检查项，前一段的产物是后一段的输入，一段没过不要往下走。

七、工具怎么选

六套方案解决的问题并不相同：有的把对话与任务系统连成线，适合持续在协作平台上干活；有的提供模板与一致性分析，适合新项目和需要治理的团队；有的以“一次变更”为单位维护增量规格，适合已有代码库的小团队；有的把规格内置进编辑器，适合喜欢图形界面的人；有的用强制技能与验证关卡约束实现质量；有的走多角色流程，适合从零规划的大产品。选型的正确问法是“我缺的是需求澄清、规格文件、任务管理，还是实现质量”。

八、六种不依赖工具的方法

固定句式减少歧义；给定前提、当操作发生、那么结果如何，把业务规则写成可执行场景；决策记录保存重要技术选择的原因；纵向切片让每张任务都交付一小段完整价值；验证关卡防止只靠勾选任务宣布完成；提前决定规格生命周期。工具会过时，这六种方法不会。

审查清单

拿到一份规格，逐条打勾：

  1. 三个问题（要做什么、边界在哪里、怎样证明完成）都有明确答案。
  2. 四层结构齐全，没有直接跳到技术方案。
  3. 每一条验收标准都能被观察到，不含“优雅”“最佳实践”这类主观描述。
  4. 空状态、失败状态、权限边界、重复操作四类边界至少各有一条。
  5. 非目标写清楚了，明确说明这一版不做什么。
  6. 未解决问题单独成栏，没有让模型自行猜测的空白。
  7. 规格、方案、任务三份文档分开存放，职责不混。
  8. 生命周期已经选定：快照、持续锚定，还是以规格为唯一源头。

实践提示

提示1 · 二十分钟写一页的最小练习

挑一个你最近想做的小功能，只写四段：为什么做、用户能做什么、边界是什么、怎样算完成。写完先别动手，把它丢给模型，看它的理解跟你想的差多少。那个差距就是你原先凭感觉付出的代价。

提示2 · 用“最多问四个”逼出决策

不要问“你有什么问题”，要问“请找出会影响范围、数据结构和验收方式的问题，每次最多问四个，并给出你的推荐”。限定数量是为了让人愿意认真回答，要求给推荐是为了避免它把选择题原样丢回来。

提示3 · 形容词转译模板

遇到“实时”“安全”“友好”，统一追问一句：发生什么操作之后，用户应该看到什么结果。例如把“未读数实时变化”改写成“标记已读后，列表状态与顶部未读数在同一次操作完成后更新，不要求跨设备同步”。

提示4 · 边界四问

空状态显示什么、失败能不能重试、能不能读到别人的数据、重复操作会怎样。这四问每次开工前过一遍，成本极低，收益极高。

提示5 · 先定生命周期再谈维护

交付后丢掉的快照、持续维护的锚点、以规格为唯一源头，三种模式没有唯一正确答案，但团队必须明确选一个。最糟的情况不是选错，而是没选，于是文档看起来一直有效，实际上早就落后了。

常见误区与纠正

误区为什么会犯怎么纠正
规格越长越好把文档厚度当成严谨程度小功能一页就够，判据是可验证而不是篇幅
一上来写技术方案技术人员习惯从实现出发先写用户行为，再谈数据结构与接口
验收标准写“代码优雅”主观判断无法执行只写能被看到或被测试跑出来的结果
让模型自己补未知不想承认还没想清楚单设“未解决问题”一栏，明确禁止猜测
为了流程完整硬造规格把工具当作业一个来回能完成的工作，直接做
规格与方案混在一份文件图省事分开存，规格锚定价值，方案锚定手段

时间不够时怎么砍

先保住“三个问题”和“四类边界”，这两块决定成败；工具对比可以整段跳过，它只影响效率不影响正确性；六种可迁移方法里，优先留下“形容词转译”和“边界四问”，这两条立刻能用。

一页纸总结

规格是一份关于预期行为的共同约定，回答要做什么、边界在哪里、怎样证明完成。用四层结构搭骨架，用三份文档分开价值、手段和顺序，用四步写法把形容词换成可验证的结果、把边界补齐、把未知单列。推进走五段式，一段不过不往下走。工具按“我缺的是什么”来选，而真正值得长期掌握的是六种不依赖工具的方法。最后一件事别忘了，提前决定规格的生命周期。

三个典型场景演练

场景一，给博客加一个搜索框。 目标写“让读者三秒内找到文章”，用户行为写“输入关键词、看到结果列表、点进详情”，边界写“空结果给出引导、请求失败可重试、只搜已发布文章”，验收写“输入存在的标题能在结果首位看到”。

场景二，给后台加导出功能。 目标写“运营每天手工整理数据太慢”，用户行为写“选择时间范围、点导出、拿到文件”，边界写“超过一万行改异步、无数据时不生成空文件、只能导出本部门数据”，验收写“导出的行数与页面统计一致”。

场景三，给表单加校验。 目标写“减少无效提交”，用户行为写“输入时即时提示、提交失败时定位到错误项”，边界写“网络断开保留草稿、重复点击只提交一次、前后端规则一致”，验收写“每条错误都能被一条测试用例覆盖”。

常见疑问三问

问，小功能也要写规格吗？ 要，但可以只写一页。判断标准不是功能大小，而是这件事会不会跨越多个会话、会不会有人接手。会，就值得写。

问，规格写完就过时了怎么办？ 这正是要提前决定生命周期的原因。快照式就明确交付后作废，持续锚定式就把更新纳入日常，选一个并执行，比纠结哪个更好重要。

问，让模型提问它问不到点上怎么办？ 限定问题范围。与其让它自由发挥，不如指定“只问会影响范围、数据结构和验收方式的问题”，并要求给推荐，回答成本立刻下降。

三十分钟上手练习

第一步，五分钟，挑一个小功能，写下为什么做。第二步，十分钟，列出用户能做的三到五个动作，用动词开头。第三步，八分钟，补齐四类边界各一条。第四步，五分钟，把每条验收标准改成“做了什么之后，能看到什么”。第五步，两分钟，把还没想清楚的写进未解决问题。走完这五步，你就拥有一份可以交给任何模型的规格。

逐节要点回顾

第一节提醒我们，凭感觉的失效点是记忆不可靠与假设不可见。第二节给出规格的定义与三个必答问题。第三节用四层结构把抽象目标落成可检查的证据。第四节区分了规格、方案与任务的寿命。第五节是四步写法，核心是把形容词换成可观察结果。第六节给出仓库结构与五段式推进节奏。第七节把工具选型翻译成“我缺什么”。第八节留下六种不依赖工具的方法，并强调提前决定规格的生命周期。八节串起来只有一句话，先把话说清楚，再让机器动手。

一张对照表：写规格前与写规格后

维度凭感觉写代码规格先行
需求来源散落在十几轮对话里集中在一页纸上
假设双方各补一半，不可见显式写下，未解决的单独列
边界用到才想起开工前过一遍四问
验收跑通就算完逐条对照可观察结果

这张表最值得看的是最后两行。规格先行并不会让工作量变少，它只是把返工从最贵的阶段搬到了最便宜的阶段。写代码时改需求要动数据库和接口，写规格时改需求只需要划掉一句话，这两者的成本差着一个数量级，这就是规格先行全部的经济学理由。

一句话带走

写规格不是为了约束人工智能，而是为了约束我们自己的模糊。你写下的每一条验收标准，都是在替未来的自己省一次返工。

给零基础听众的三条起步建议

第一，不要追求格式完美，先把三个问题的答案写出来，格式可以在第二份、第三份规格里慢慢补齐。第二，每次只练一个动作，这一周只练把形容词改成可观察结果，下一周再练边界四问，比一次全上更容易坚持。第三，把写好的规格当成给朋友的留言来写，写完自己朗读一遍，凡是读着拗口、读着心虚的地方，通常就是还没想清楚的地方，回去补就是了。
