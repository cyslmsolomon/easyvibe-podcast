guide-introduction-md-88 项目介绍与学习地图 · 解读与音频稿件

本稿为音频配套解读，围绕 Easy-Vibe 的「项目介绍 / 学习地图」一页，拆解为什么多数人用 AI 写代码却停在玩具阶段，并逐段铺开三阶段实战路径、附录方法论与前后端章节，最后给出三类学习者各自的使用走法与审查清单。

一、这一集在能力地图上的位置

这是整份教程的第一页，也是最容易被跳过的一页。它讲的是项目介绍和学习地图，听起来像前言，但要解决的问题很硬：为什么那么多人已经会用 AI 写代码了，做出来的东西却始终停留在玩具层面。

在 Easy-Vibe 的能力地图里，这一页承担的是「定位」职能。它不教你具体怎么写代码，而是告诉你整条路线长什么样、你现在站在哪一段、下一步该翻哪一章。没有这个定位，后面的章节就会变成一堆零散的知识点，学完也不知道自己练到了什么程度。

一个很常见的现象是：很多人学完一整份教程，能说出每一章讲了什么，但说不出自己现在能交付什么。这就是缺定位的典型症状。知识点是散的，能力是整体的，中间缺的那层就是把知识点串起来的路线图。

这一页还隐含了一个判断，值得单独拎出来：AI 已经把「写代码」这件事的门槛降到了很低，所以这份教程真正要教的不是怎么写代码，而是怎么组织一次完整的开发。 这决定了它的编排逻辑——按交付物复杂度递进，而不是按知识点难度递进。

二、卡点不在工具，在流程

原文把卡点说得很清楚，一共三件事：

  1. 不知道如何用 Vibe Coding 组织开发流程
  2. 不知道该选哪些工具
  3. 不清楚从原型到上线中间还差哪些关键步骤

这三件事里，只有第二件是关于工具的，而工具恰恰是最容易补的。搜索一下就有答案，花半天就能上手。真正难的是另外两件——流程和路径。

流程没人告诉你，你就会一直在原地打转：今天做一个贪吃蛇，明天做一个待办清单，每一个都能跑，但每一个都走不到上线。这种「能跑但不成产品」的状态，就是原文说的「玩具层面」。

所以这份教程的设计重点不在教你用哪个工具，而在给你一条能走通的路线，让你在每个阶段都知道自己在练什么、练完能拿到什么。

三、三阶段实战路径

阶段目标关键动作
新手入门建立手感与信心通过小游戏快速上手 AI 编程
第一阶段掌握 Vibe Coding 工作方式完成 Web 应用原型
第二阶段全栈开发与部署上线把原型变成真正能访问的东西
第三阶段构建跨平台复杂应用处理更真实、更复杂的场景

这条路径是循序渐进的，不能跳。设计原则是每个阶段都配有完整项目实战——不是为了让你多做一个练习，而是因为 AI 编程光看学不会，必须在一个真实挑战里把整条链路走一遍，才会暴露出那些看教程时根本想不到的问题。

这份教程的目标写得很直白：让你在真实挑战中从玩具走向产品，最终具备把任何想法落地为可用应用的能力。

四、新手入门（幼儿园）：两个章节

  • 学习地图：整体学习路径导览，先看清全貌再决定往哪走
  • AI 时代，会说话就会编程：通过贪吃蛇等案例初步感受 AI 编程的能力

这一阶段的目标只有一个：建立手感。你不需要理解架构，不需要知道什么是接口，只需要反复体验一件事——把你想做的东西说出来，然后看它真的长出来。

这个体验积累够了，后面讲方法和流程时你才接得住。完全的新手不要跳过这一段，手感这件事省不掉。

五、第一阶段（AI 产品经理）：四章闭环

  1. 认识 AI IDE 工具：学会使用 IDE，掌握界面结构和高效提示方式
  2. 动手做出原型：从产品分析拆解，到多页面产品原型实现的完整闭环
  3. 给原型加上 AI 能力：理解并完成文本、图片、视频等常见 AI 能力的 API 接入
  4. 完整项目实战：模拟真实场景、接受用户反馈迭代并完成项目展示（含大作业）

这四章合起来是一条完整的链：先会用工具，再会拆需求，再会接能力，最后在一个真实项目里把前三样串起来。

注意顺序不能乱。很多人直接从第 3 章开始，觉得接个大模型接口很酷，但因为不会拆需求（第 2 章），做出来的东西往往没有一个清晰的用户路径。

六、附录区：产品思维的地基

六块内容，目前全部是完成状态：

  • 附录 A：产品思维补充——从想法评估到需求拆解与 MVP 的完整框架
  • 附录 B：常见报错及解决方案——Vibe Coding 中的常见错误及排查方法（建议当工具书用）
  • 从哪里找点子——从参考应用、趋势和 VC 清单里收出细分方向
  • 双钻模型——先定义问题，再展开方案设计的完整节奏
  • Jobs to Be Done——用 JTBD 看清用户真正想完成的事
  • The Mom Test 用户访谈法——通过用户访谈验证需求

这四块方法论看起来偏软，但它们决定的是你做出来的东西有没有人要，而不是能不能跑起来。这是两个完全不同维度的问题，而后者才是绝大多数玩具产品的死因。

九、三类学习者各自的走法

这份教程面向三类学习者：

新手（普通人 / 产品与运营侧）：帮助非技术背景角色和入门学习者听懂关键概念，完成第一个 AI 小工具或产品原型。建议严格按顺序走，从幼儿园开始，不要跳。

初中级开发者（有一定基础的学生和开发者）：系统掌握 vibe coding 与原生 AI 应用开发。可以直接进第一阶段，但附录那四块方法论建议补上，那通常正是这一类人缺的部分。

高级开发者（公司与初创、开源与独立开发者）：支持团队和个人快速搭建、验证与迭代原生 AI 应用。把这份材料当检索手册用，按需翻章节即可。

地图上有两种状态标记：已完成（可以直接学）与建设中（还在更新，遇到问题时以仓库里的实际内容为准）。

十、如何判断自己是否已经脱离玩具阶段

「玩具」和「产品」的分界，其实有很具体的判据，不需要靠感觉。

第一条是有没有别人在用。自己跑着玩的 demo，再精致也是玩具；哪怕只有一个真实用户每天打开一次，性质就变了。

第二条是有没有部署到公网。本地能跑和能被别人访问，中间隔着环境变量、构建配置、域名、静态资源路径这一整串麻烦。跨不过去，就永远停在原型阶段。

第三条是有没有数据落地。只有界面没有持久化数据的应用，本质上还是个演示稿。数据一旦要存，就会牵出用户体系、权限和备份这一系列真实问题。

第四条是有没有被验证过需求。没人验证过的东西，做得越完整，沉没成本越高。

这四条里只要有两条回答是「没有」，你就还在玩具阶段。对照着看，比凭感觉判断靠谱得多，也能直接告诉你该补哪一段。

十一、审查清单

在开始学习之前，用这份清单给自己做一次定位：

  1. 我能不能说清楚「从原型到上线」中间到底有哪几步？说不清就说明卡在流程上。
  2. 我最近做的三个东西，有没有任何一个能被别人真正用起来？全都没有，就还停在玩具层面。
  3. 我属于三类学习者中的哪一类？走法是否匹配？
  4. 我会不会拆需求？如果只会接接口不会拆需求，回第一阶段第 2 章补课。
  5. 我的设计稿和最终页面能对得上吗？对不上就补前端那五章。
  6. 我有没有把应用真正部署到公网过？没有就补 Git 工作流与部署那一章。
  7. 我做的东西有没有人愿意付费？这决定了你要不要学支付集成那一章。
  8. 我有没有验证过需求是真的？没验证过就补附录那四块方法论。
  9. 我是否知道自己现在站在三阶段里的哪一段？不知道就先回来看学习地图。
  10. 我学完的章节和能交付的东西，哪个更多？如果章节远多于交付物，进度其实被高估了。

这十条不必一次全答。优先回答第 1、第 5 和第 9 条：能不能说清从原型到上线的步骤、设计稿和页面是否对得上、以及自己站在哪一段。这三条决定了你该往哪走，其余七条决定的是走得扎不扎实。

十二、约束与边界

第一，状态标记会变。 地图上标着「建设中」的章节随时可能更新甚至重构，不要把它当成稳定承诺。遇到冲突以仓库实际内容为准。

第二，工具会过时。 教程里提到的 lovart、MasterGo、Zeabur、Trae、Dify 都是具体产品，它们的形态和定价会变。真正该带走的是「这类工具解决什么问题」，而不是某个产品的操作步骤。

第三，别指望跳阶段。 三阶段是循序渐进设计的，跳阶段省下的时间，通常会在后面以「反复返工」的形式还回来。

第四，这份教程的承诺有前提。 「一个人成为全能开发者」这句话成立的前提是系统化训练加足够多的项目实战，不是看完就会。这是约束，不是口号。

第五，路线图不是课程表。 你可以也应该在当前阶段做出一个完整交付物之后就开始往下一段摸，遇到卡点再回来补。把三阶段理解成必须串行完成的课程表，反而会让你在某一个阶段耗太久，失去对全局的感知。

第六，别用「学完了多少章」衡量进度。 正确的进度单位是交付物，不是章节数。读完十章但一个能用的东西都没交付，进度其实是零；只认真做完一个大作业，反而可能已经跨过一个阶段。

十三、一句话收束

如果这一整页只能带走一句话，那就带走这句：把「从原型到上线」中间差的那些步骤列出来，你会发现你缺的不是某个工具，而是其中某一段你从来没走过。

这段话反过来也成立——你不需要学会所有工具，你只需要把那条线上你没走过的一段补上。剩下的，AI 已经替你解决了大半。

最后补一句关于这一页本身的话。它是整份教程里唯一一页不含任何代码的页面，也正因为如此，它最容易被跳过。但如果你已经在 AI 编程上花了一段时间，却始终说不清自己还差哪一步，那么你要补的很可能不是又一个新的工具，而是回来把这一页认真读一遍。

定位这件事，看起来最不技术，却往往决定了你后面所有技术投入的效率。方向对了，每一章学起来都会很快；方向错了，学得越多的工具，越容易变成另一次原地打转。

提示1 · 先判断你卡在三个卡点中的哪一个

卡住的时候先别急着找新工具。对照原文的三件事：是流程不会组织、工具不会选、还是不知道从原型到上线差什么。只有第二种值得去搜工具，另外两种都得回到路线图上来解决。

提示2 · 建立手感这一步不能省

完全没有基础的话，先做两个小游戏再谈方法。你需要反复体验「说出来它真的长出来」这件事，后面的流程讲解才接得住。直接跳到方法论章节，通常会学得很虚。

提示3 · 先会拆需求，再谈接 AI 能力

很多人跳过第一阶段的第 2 章直接学接接口，结果做出来的东西没有清晰的用户路径。顺序应该是：会用工具、会拆需求、会接能力、最后在真实项目里串起来。

提示4 · 把附录那四块方法论当必修课

找点子、双钻模型、JTBD、Mom Test 这四块看起来偏软，但它们决定的是有没有人要，而不是能不能跑。初中级开发者尤其容易缺这一块，建议补上。

提示5 · 用「能不能被别人用起来」检验自己是否脱离玩具阶段

给自己一个硬标准：最近做的东西里，有没有任何一个能被别人真正用起来。如果全都是自己跑着玩的 demo，那就还停在玩具层面，需要往部署和全栈那段走。

提示6 · 状态标建设中的章节，以仓库实际内容为准

地图上标着「建设中」的章节还在更新，可能和你看到的页面不一致。遇到冲突不要怀疑自己，直接去仓库看实际内容。

提示7 · 别把具体工具当成能力本身

lovart、Zeabur、Trae、Dify 这些都会过时。真正该带走的是「这类工具解决什么问题」——素材生成、部署上线、CLI 加速开发、工作流编排。工具换了，这个判断依然成立。

这份教程的最终承诺只有一句：掌握 Vibe Coding 并配合系统化训练，你一个人就能成为集前后端开发、AI 能力集成、产品设计于一身的全能开发者。
