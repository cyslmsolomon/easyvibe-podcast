三、逐节解读

3.1 创建仓库时的五个字段

原文逐一说明了新建仓库页面上的字段，其中三个值得重点留意：

  • 可见性（Choose visibility）：个人仓库私有则只有你和受邀者可见，公开则所有人可见。原文建议新手先设为私有。
  • README：原文称其为「仓库的完整介绍」，并给出惯例建议——每个仓库都应该有。
  • .gitignore 与 license：前者告诉 Git 忽略指定文件，一旦指定就不再被跟踪，适合临时测试文件、依赖包与大文件；后者规定他人能否商用及附加条款。

原文给出的新手初始设置是：勾选 Add README + 可见性设 Private + 自定义名称描述 → Create repository。

3.2 为什么必须用 SSH，而不是省事与否的问题

原文此处有一句极容易被读漏的话：

"SSH 协议绑定"是启用 GitHub SSH 认证的前提步骤——只有将本地 SSH 公钥"绑定"到 GitHub 账号后，GitHub 才能识别你的设备并允许对仓库进行 SSH 操作。

这句话意味着：没有绑定，SSH 通道根本不存在，而不是「不绑会麻烦一点」。

两种协议的差异：

协议验证方式体验
HTTPS每次操作需输入账号密码或个人访问令牌（PAT）繁琐，且有密码泄露风险
SSH通过密钥对完成身份验证无需重复输密码，加密传输更安全

3.3 密钥对：把「锁与钥匙」的比喻讲准

原文的比喻是：私钥是你的专属钥匙（留在本地，绝不分享），公钥是可以公开分享的锁（复制到平台的 SSH keys list）。

整个验证过程是三步：

  1. 本地设备用私钥加密操作请求后发出；
  2. 平台用你之前绑定的公钥尝试解密；
  3. 解密成功 → 确认为授权设备，允许操作；失败 → 拒绝。

由这三步可以直接推出两条结论：私钥泄露等同于身份被盗；换设备必须重新生成并重新绑定。

3.4 绑定的两条路径

原文给了两种获取公钥的方式：

  • 推荐给零基础：让 AI IDE 代生成。提示词的要点是「帮我在某某平台登录用的 SSH 密钥生成一下，我的邮箱是某某，请把公钥返回给我复制」。特别提醒：输入后需在左侧终端按 Enter，否则命令会一直等待。
  • 手动方式：在本地终端执行生成命令，把示例邮箱替换为注册账号所用邮箱，按 Enter 接受默认值，随后在用户目录下的 .ssh 中得到私钥与 .pub 公钥两个文件。

随后是统一的三步：复制公钥全文 → 平台 Settings → SSH and GPG keys → New SSH key → 粘贴保存 → 终端执行测试命令验证。

原文给出的常见失败原因是：公钥复制不完整、私钥权限过高（本地 .ssh 目录应仅本人可读写）。

3.5 三条被单独列出的注意事项

  1. 多设备各绑各的 —— 每台设备生成各自的密钥对，公钥可绑到同一账号；
  2. 私钥绝不分享 —— 泄露后立即删除对应公钥并重新生成；
  3. 用 SSH 格式地址 —— 若此前用 HTTPS 克隆，可用 git remote set-url 切换协议。

演绎方补一条高频误解：很多人绑好了密钥却仍用 HTTPS 地址克隆，于是每次推送照样要密码，最后得出「SSH 没用」的错误结论。 不是 SSH 没用，是走的根本不是那条通道。

3.6 CLI AI 工具与 AI IDE 的定位差异

原文的类比很清晰：CLI AI 工具 ≈ 一种特殊的网页端 AI 编程平台（同样只要一个对话入口就自动执行），也 ≈ AI IDE 中的 Agent 模块（侧边那块对话区域）。

差异在于：不同 AI IDE 对 Agent 的实现差异很大，效果不稳定，因此 CLI AI 工具多由大厂直接开发。

原文给出的对照表（以 Claude Code 与 Cursor 为例）可压缩成一句话：CLI AI 工具赢在能干重活（自动任务、多文件、长上下文、一体化提交），AI IDE 赢在好用（原生编辑器、实时补全、上手简单）。

四、审查清单

  • 仓库可见性已按需要设置（新手建议 Private）
  • 仓库已有 README
  • 已添加 .gitignore，依赖包与大文件未被跟踪
  • 已明确选择的 license 及其商用条款
  • 本地已生成 SSH 密钥对，且私钥未分享、未上传
  • 公钥已完整复制并绑定到平台账号
  • 已通过测试命令确认平台能识别本机
  • 每台开发机各自持有独立密钥对
  • 仓库远程地址使用的是 SSH 格式，而非 HTTPS
  • 开工前先 pull，再改再 commit，最后 push
  • 拉取 / 推送提示词中写清了文件夹相对或绝对路径
  • CLI AI 工具已按实际项目亲自测试过，而非仅凭口碑选型

五、实践提示

提示1 · 绑完立刻换地址

SSH 绑定只是拿到了门禁卡，走的门还得选对。绑定成功后，请检查仓库的远程地址是否为 SSH 格式。若此前用 HTTPS 克隆，用 git remote set-url 切过去。这一步漏掉，前面所有努力都白费。

提示2 · 开工先拉取，不要跳过

多人维护的仓库，pull 不是可选项。跳过 pull 直接 push，最常见的结果不是报错，而是悄悄覆盖别人的改动——这类问题往往几天后才被发现，排查成本极高。

提示3 · 私钥权限要收紧

原文点出了「私钥权限过高」这个失败原因。检查本地 .ssh 目录是否为仅本人可读写。权限设置不是洁癖，它直接决定 SSH 是否愿意使用你的密钥。

提示4 · 工具选型先亲手测试

原文反复强调「哪一个在实际项目中更好用，只能通过亲自测试来判断」。做法是：同一个小任务，用两个工具各跑一遍，比较完成度和返工次数。由于模型版本更新快，建议优先选性价比最高的那个，而不是名气最大的那个。

七、这一集在整条链路上的位置

这一集看似是「基础操作」，实际承担的是从本地到云端的连接建立：

  • 前面的所有产出（一个能跑的应用）目前只存在于你的电脑上；
  • 有了仓库与 SSH，你的代码才第一次有了远程副本与版本历史；
  • 有了 pull / commit / push 的节奏，协作才成为可能。

而引入 CLI AI 工具，则把这套流程进一步简化：你不再需要记住命令，只需要说清楚你想做什么。 这和整篇教程一贯的方法论是一致的——能用对话解决的事，不要先去记语法。
