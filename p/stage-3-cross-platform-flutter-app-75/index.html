如何开发 Flutter 跨平台应用 · 从 Nubank 的选型到门店费用簿

一、这篇在讲什么

这一节出自 Easy-Vibe 第三阶段「高级开发：多平台与 AI 进阶」的跨平台章节，主题是怎么用 Flutter 开发一个跨平台应用。全篇用一个具体应用「门店费用簿」把十三步链路完整走了一遍，并用 Nubank 的选型案例作为工程决策的样板。

核心结论只有一句：Flutter 省下的是重复实现，不是产品判断、平台适配、测试和发布流程。

模块内容回答的问题
Nubank 案例十一项标准比较、一小时任务验证、逐步迁移跨端框架该怎么选、怎么迁

三、Nubank 案例：先比较，再验证，再扩大

Nubank 是巴西数字银行。它没有因为 Flutter 热门就直接迁移，而是先用十一项标准比较 Kotlin Native、React Native 和 Flutter，并让不同经验的开发者分别完成一小时任务、收集反馈。选定 Flutter 后，新功能逐步采用、旧功能按计划迁移，随后建立自己的设计系统，把单元测试、组件测试和端到端测试纳入日常开发。官方案例还记录了合并成功率、合并时间和新人上手速度等实际指标。

这个案例给费用簿的直接借鉴是工程做法而非界面风格：整页颜色由主题统一；汇总卡、预算、费用行和同步提示拆成小组件；表单规则有单独的可见反馈；最常用的「打开首页和录入表单」写成组件测试。项目开始多人维护时，再按官方可扩展应用架构建议调整目录和测试边界。

三个大厂案例（My BMW、Google Pay、Nubank）放在一起，方向很明确：跨端框架省下的是重复实现，产品判断、平台适配、测试和发布流程一项都省不掉。

提示一 · 选型先过「一小时任务」关

评估跨端框架时，不要只比参数表。让团队里不同经验水平的开发者各自用候选框架完成同一个一小时任务，记录完成时间、卡点和代码 review 结论。一小时任务暴露的是真实学习成本和工程摩擦，比任何对比文档都直接。

四、门店费用簿：六件小事定义的业务原型

成品定义：店长打开首页能看到本月已记录金额和备用金，点「记一笔」新增一笔临时费用；网络不好时先存本机，并明确显示哪些记录还没有同步。

这个题目装着企业应用经常遇到的六件小事：

  1. 首页先回答「现在是什么状态」；
  2. 金额和费用说明必须校验；
  3. 保存后要告诉用户结果；
  4. 关闭或刷新以后，刚才的记录不能丢；
  5. 离线记录和服务器同步要分成两个状态；
  6. 同一个页面要能适应窄屏手机和较宽窗口。

选这个小题目做教学是有道理的：企业应用的难点从来不在功能多，而在这六件小事每一件都做到位。demo 能跑起来很容易，把这六件事都做对，才是一个同事真正敢用的工具。门店场景信号未必稳定，仓库角落、地下库房都可能没网，离线可用不是加分项，是基本功。

提示二 · 用「六问」检验原型是否可用

接手任何小工具原型时，用这六问过一遍：打开第一眼能否看到状态？关键字段是否有校验？保存是否有明确结果？刷新后数据是否还在？离线与在线是否分成两个状态？窄屏宽屏是否都可用。六问全过，原型才算具备交付给真实用户试用的资格。

五、十三步链路的关键决策

5.1 环境与空白页：先归因，再动手

安装 Flutter 后运行环境检查命令，逐项确认框架本身、Android 工具链、iOS 工具链和编辑器状态；把结果交给智能编程工具，一次只修第一个必须修的问题。常见陷阱是「检查通过不代表全绿」：Web 旁出现对勾，不代表 Android 与 iOS 环境就绪。教程实测环境为 Flutter 3.44.9、Dart 3.12.2、Chrome 151，当时本机缺 Android SDK，Xcode 已装但没有可用的 iOS Simulator Runtime，CocoaPods 也未安装，因此后续演示全部使用实际运行的 Flutter Web 构建，不冒充模拟器或真机截图。

创建项目后先跑空白计数器模板，确认能运行再写业务。这样出错时能区分「业务修改的问题」和「环境配置的问题」。启动失败时只把第一段有效错误交给工具，要求只修启动、不加功能。

5.2 首页顺序与状态：先产品，后技术

第一轮只用演示数据：本月金额、备用金、最近费用加一个「记一笔」按钮。信息顺序的原则是店长打开就能看见总额、预算和最近几笔，主要按钮只有一个；颜色字号可调，但不要用五六种卡片抢注意力。太挤时就删到只剩总额、预算、最近记录和新增按钮。

离线和同步状态要摆到页面上：首页顶部显示最后同步时间和待同步数量，费用行也标记待同步，而不是只在控制台打印日志。「待同步数量」回答的是用户心里最不安的问题——我刚记的这笔到底存下来没有。必须说明：当前版本没有真实服务器，「待同步」只是产品状态的清晰表达，不等于云端同步已完成。接服务器前要先决定读取以本机还是远端为准、失败怎样重试、何时改变同步状态。

5.3 表单、反馈与持久化

最小表单从底部弹出，只填费用说明和金额。底部弹层适合短任务，因为用户还能看见原页面；字段变多、要拍照或审批时换完整页面。校验规则：费用说明不能为空，金额必须大于零，失败时把原因写在对应字段下面——写在出错字段旁是告诉用户改哪里，统一弹一个马上消失的提示是让用户自己找。

实测数据：输入「打印纸」和 56 后，本月金额从 890.50 元变为 946.50 元，待同步数量从 1 变为 2，列表顶部出现新记录，底部提示「已保存在本机，联网后再同步」。保存反馈能避免用户因不确定连续点五次；接真实后端后还要让服务端识别重复提交，因为连点、网络重试、页面重复加载都可能让同一笔费用出现两次。

持久化第一步用键值存储（序列化费用列表存本机），验证方式是重新加载整个 Web 应用后记录仍在。但这种存储只适合设置和少量简单值，不适合大量费用、附件、查询和事务；产品扩大后应换数据库，并把数据层放进 Repository。

5.4 结构拆分、自适应与平台能力

原型跑通后再拆结构：View 负责显示和交互，ViewModel 保存界面状态与操作，Repository 作为数据来源入口，Service 封装本机数据库、REST API 或平台能力。拆分的信号是职责真的产生了差异，不是目录看起来专业——不要一开始创建几十个空目录。先让工具只提拆分方案，确认后再拆第一项，功能和界面保持不变。分层的好处是测试费用计算不必打开页面，测试页面时可以替换掉服务器。

自适应不等于把手机页面横向拉长：宽窗口限制内容宽度，避免汇总卡和表单从屏幕左边拉到右边；窄屏不能横向溢出。官方自适应三步法是先抽出共用信息、再测量当前可用空间、最后选择布局；不要按「这是手机还是平板」写死页面。平板要同屏列表和明细时，再把底部导航改成侧边导航或双栏。

平台能力分别接入：先查维护正常、支持目标平台的插件，用最小原型验证权限、异常和生命周期；插件覆盖不了的，用平台通道调用 Kotlin、Java、Swift 或 Objective-C。跨平台不是禁止原生代码，而是把原生代码控制在真正需要的位置。

5.5 测试、双端验证与发布

测试用户真正会走的路径：先跑静态分析和现有测试，再补一条组件测试——打开首页、点击「记一笔」、确认费用说明、金额和保存按钮出现；表单稳定后再测空表单不能保存且能看到两个错误提示。教程实测 flutter analyze 无问题、组件测试通过 1 项；空表单提示和本机恢复经浏览器实际操作验证，但未写成完整自动化测试，教程明确不冒充已覆盖。项目扩大后：费用计算与 ViewModel 适合单元测试，页面状态适合组件测试，登录、上传、离线恢复和同步适合集成测试——单元测试查算得对不对，组件测试查点不点得动，集成测试查整条路走不走得通。

双端六项检查：中文、金额和大字体是否溢出；底部表单是否被软键盘遮住；返回手势能否正常关闭表单；彻底关闭再打开后本机记录是否恢复；相机、照片和通知权限被拒绝时会发生什么；断网、恢复网络和重复重试会不会丢单或生成重复记录。教程如实记录该步当时未完成（缺 Android SDK、无可用 iOS Simulator Runtime），移动端截图不能用 Web 截图替代。

构建发布是两条独立流水线：Web 生产构建生成于 build/web，需经本地静态服务器打开复验（不双击 HTML）；Android 上架一般生成 App Bundle，需 SDK、应用编号、版本号、发布签名和 Play Console 配置，并至少在无开发环境的手机上安装测试；iOS 在 Mac 上生成 IPA 只是开始，后续还有 Validate、TestFlight、提交审核。两个商店的隐私说明、截图、审核规则、账号及推送、内购、登录政策都不同——一套 Dart 代码不会生成同时提交两个商店的万能安装包。

提示三 · 把「待同步数量」当成信任指标运营

待同步数量、最后同步时间这类状态字段，是离线功能用户信任的来源。建议为它们设定验收标准：任何一笔记录从保存到出现在列表，用户不需要猜；待同步数量在恢复网络后必须归零，归零前用户能看到进度。宁可多做一步状态展示，也不要用一个转圈图标代替所有状态。

提示四 · 保存反馈的三件套

一个可靠的保存动作要同时给出三样东西：结果（成功或失败）、位置（新记录去哪了）、后续（已存本机还是已同步）。教程实测的「关闭表单、新记录置顶、底部提示已保存在本机，联网后再同步」就是三件套齐备的样板。缺任何一件，用户就会用连续点击来消除不确定。

提示五 · 错误提示写在出事现场

字段级错误提示的原则：提示出现在出错的字段旁边，说明缺什么、怎么改。不要只写「参数错误」，也不要弹一个马上消失的统一提示。需要自己实现时，可对照官方表单校验示例。

六、审查清单

  • 已用多标准加一小时任务的方式评估过跨端框架，而非只看热度
  • 迁移策略是新功能逐步采用、旧功能按计划迁移，不是一次性切换
  • 首页第一屏能回答「现在是什么状态」，主要按钮只有一个
  • 已区分「存在本机」与「到达服务器」两种状态，并有最后同步时间与待同步数量
  • 接服务器前已决定读取以本机还是远端为准、失败怎样重试、何时改变同步状态
  • 金额与说明字段有校验，错误提示写在对应字段下方
  • 保存成功有明确反馈，新记录立即可见
  • 已评估键值存储的数据量边界，扩大时换数据库并分层 Repository
  • 项目结构按 View、ViewModel、Repository、Service 拆分，且拆分时机以职责差异为准
  • 宽屏限制内容宽度，窄屏无横向溢出，未按设备类型写死页面
  • 平台能力先查插件再走平台通道，原生代码控制在真正需要的位置
  • 有覆盖主路径的组件测试，且不把手动验证冒充成自动化覆盖
  • Android 与 iOS 分别完成六项检查，不用 Web 截图替代移动端验证
  • 发布流水线区分 Web、Android、iOS 三条，未幻想一个万能安装包
