一、这一集到底在解决什么问题

这一集回答一个非常具体的问题：原型已经能演示了，怎样把其中一个核心动作接到真实的 AI 服务上？

上一章交付了一个能点击、能操作的电商内容工作台，页面结构和操作流程已经可以验证，但生成结果仍然来自模拟数据。本章的任务，是让生成文案这个按钮真正工作起来。原文把这件事拆成一个通用方法加五种能力，通用方法讲三件事，怎样描述任务、怎样读懂官方文档、怎样把调用安全地放进产品流程，五种能力是文本、图片理解、图片生成、语音和视频。

如果只用一句话概括这一集：接入 AI 不是复制一段接口代码，是先想清楚要什么能力，再读懂文档，最后小步验证；模型会更新，套路不变。

原文有一句重要的免责说明，模型名称和控制台界面会持续更新，因此文中的示例只用来说明结构，实际接入时应从对应服务的当前文档中复制模型 ID 和参数。本集音频与本文同样遵循这一原则，不绑定任何具体版本号。

三、确定能力，先看页面的两端

原文第一节先把问题锚定，上一章做出的电商内容工作台，已经有了商品信息和生成文案按钮，只是结果还来自模拟数据。现在先让这个按钮真正工作起来。这个过程是，用户填写商品名称、材质和卖点，点击按钮，页面返回一段商品文案，输入和结果都是文字，因此要找一个能够生成文本的模型。

如果页面上的功能不同，需要的能力也跟着变化，原文列了五种情况。上传商品照片让系统识别颜色和款式，用到图片理解。根据商品资料制作海报，用到图片生成。把一段录音整理成会议纪要，要先把语音转成文字，再让文本模型整理。把文章做成可以播放的音频，用到文字转语音。让一张商品图动起来，用到图片生成视频的能力。

原文给出的判断方法只有一句话，接入前先看一遍页面，用户会提交什么，最后希望在页面上看到什么，把这两件事说清楚，通常就能判断该去找文本、图片、语音还是视频模型。

一个功能有时需要分成几步

原文提醒，并不是每个功能都能交给一个模型一次完成。上传商品照片并生成卖点，要先读懂照片中的商品，再根据识别结果写文案。根据公司资料回答问题，也要先从文档中找到相关内容，再组织答案。

拆解时不用从模型名称出发，只要顺着用户的操作往下看，哪一步是在理解现有内容，哪一步是在生成新内容，哪一步只是查找资料，需要时可以把两三种能力依次接起来。这里有一条边界，AI 只负责其中适合它的部分，登录、支付、保存文件和页面跳转都有明确规则，仍然使用普通程序来完成。演接入的解读是，能画出用户操作路径图的功能，才能拆；画不出来的，先回去补流程。

四、服务台首访，只看四样东西

确定要做文本生成以后，就可以打开 DeepSeek、SiliconFlow、火山方舟或 MiniMax 等服务平台。原文先分清了一个关系，平台负责账号、计费和调用入口，真正处理这次请求的是我们选择的模型。

第一次接入不用看完服务台里的所有菜单，先找到四样，创建一个用于调用接口的 API Key，记下准备使用的 Model ID，在官方文档中找到一段最小的 curl 或 JavaScript 示例，看清接口的额度、价格和调用限制。

应用通过 API 把商品资料发给模型。文档如果提供了 JavaScript 或 Python 的 SDK，也可以直接使用，它只是把请求代码封装得更方便。请求中那段请根据商品信息生成标题和卖点的文字，就是交给模型的提示词。

原文特别强调，服务平台的名称、模型 ID 和 API 地址不是一回事，填写代码时以官方示例中的地址和 Model ID 为准，不要把在线体验页面的网址复制进去。

服务台中还可能出现 Embedding、Rerank、Function Calling、OCR 和内容审核等接口。做知识库时会用到 Embedding 和 Rerank，读取 PDF 或票据时会用到 OCR，让模型调用搜索、数据库等外部工具时，会用到 Function Calling。原文的态度是，这一阶段不需要一次学完，先接通一个和页面功能直接相关的 API，等产品需要新的能力时，再回来查对应的接口。

五、先在体验页面把格式试出来

在写接口代码之前，可以先到服务平台的在线体验页面试一试。原文点明了这一步的目的，我们要确认的不是模型会不会写文案，而是它能不能按照页面需要的格式返回结果。

在在线体验页面中，可以先像真实用户一样输入。真正做成页面以后，用户可能连这段话也不用自己组织，他只需填写商品名称、材质和颜色，再点击生成文案。程序会读取这些字段，并在请求中补上固定要求，不要编造价格和销量、标题不要太长、结果按照指定格式返回。

这些规则不应该交给每位用户重复填写。比如页面需要分别显示标题、简介和卖点时，可以由程序要求模型返回三个固定字段。这样用户输入仍然自然，页面也能稳定读取结果。

第一次测试时，可以换几组商品资料，再故意少填一个字段，看看模型会不会擅自补充信息。如果返回格式不稳定，再去调整程序附加的固定要求，而不是让用户学习怎样写提示词。原文这条边界很重要，格式问题是产品的责任，不是用户的作业。

六、跟着官方示例发出第一次请求

提示词试好以后，下一步是让它从代码中发出去。打开官方文档，先找 Quick Start 或 API Reference。不同平台的文档虽然长得不一样，但第一次调用只需要看清四件事，请求发到哪个地址、API Key 放在哪里、model 填什么，以及官方的最小示例怎样写。

先复制官方提供的示例，只替换模型 ID 和测试内容。能在终端中得到一次正常响应以后，再把代码放进项目。原文给出了理由，这样如果接入页面后报错，我们至少知道账号、Key 和模型本身是可用的。这是一个简单的二分法排错顺序，先证明环境没问题，再证明代码没问题。

还要看一眼返回结果。文本通常藏在某个 JSON 字段里，图片可能返回 URL，语音可能直接返回二进制内容，视频则常常先返回一个任务编号。页面后面怎样写，取决于接口实际返回了什么。

官方文档通常会给出一段示例代码，我们可以把这段示例连同要实现的功能一起交给 AI IDE，让它帮我们接到现有页面中。有了页面位置和官方示例，AI IDE 就不必自己猜接口格式。先确认一次请求能够正常返回，以后接入图片、语音或视频时，换掉功能描述和官方示例就可以了。原文这一句点出了这套方法的复用性，接入的骨架只有一副，换能力就是换描述和换示例。

七、服务台操作，密钥、模型与额度

创建 Key、选择模型和查看用量，通常都在服务台中完成，各家的菜单名称会有差别，但要做的事情大致相同。

创建 Key，并确认请求有没有到达平台

API Key 是应用调用模型时使用的凭证。创建以后，把它放进本地环境变量，不要贴进截图、聊天记录或前端代码。如果怀疑已经泄露，应立即到服务台撤销并重新创建。

发出第一次请求后，可以打开 Usage 或 Billing 页面看看是否出现了新的调用记录，这里还会显示余额和 Quota。遇到请求失败时，先确认是代码没有发出去、平台拒绝了请求，还是账号已经没有可用额度。原文给了一个排错顺序，先定位失败发生在哪一段，再谈修复。

如果错误信息中带有 Request ID 或 Trace ID，也把它记下来。同一时间可能有很多请求，这个编号可以帮助我们在日志里找到刚才失败的那一次。

选择模型，并复制准确的调用名称

模型广场或 Models 页面用来查看平台当前提供哪些文本、图片、语音和视频模型。点进详情页以后，注意复制代码中使用的 Model ID，它可能和页面上显示的中文名称不同。

有些平台还要求先选择 Region，或者创建一个 Deployment，然后才会给出 Base URL 和 Endpoint。遇到这种情况，直接跟着平台的快速接入向导完成，不要把控制台页面的网址当成 API 地址。

用量限制和长任务

文本接口通常会标出 RPM 和 TPM，分别表示每分钟允许的请求数和 Token 数。图片、语音和视频还可能限制 Concurrency，即同时生成的任务数。超过限制时，接口通常会返回 429，这时应该稍后重试，而不是不断重复点击。

视频等耗时较长的任务不会马上返回文件，而是先给出一个 Task ID。程序可以使用它查询进度，也可以提供 Callback 或 Webhook，让平台在完成后主动通知。最后拿到的 File ID 或临时下载地址可能会过期，准备正式上线时需要考虑是否把文件保存到自己的存储中。

文档里还会出现 max_tokens、temperature、stream 等参数。第一版先沿用官方示例，只有输出被截断时再调整 max_tokens，需要边生成边显示时再打开 stream。不确定某个参数的作用时，查对应模型的文档，不必一次全部修改。演接入把这条理解为参数卫生，一次只动一个参数，改完记一笔，否则出错时无法归因。

八、从官方示例接到页面

终端中的最小示例能够返回结果以后，再把它接进原型，原文给了五步顺序。第一，把 Key 写进 .env.local 等不会提交到 Git 的环境文件。第二，在服务端或 Serverless Function 中调用模型。第三，让页面调用自己的 /api/ 接口，而不是直接携带第三方 Key。第四，给按钮补上等待、成功和失败状态。第五，回到 Usage 页面，确认这次操作产生了真实调用。

原文用一段加粗划了红线，不要把 API Key 写进 Vue、React 或普通 HTML 的前端代码，即使变量名称带有 VITE_、NEXT_PUBLIC_ 前缀，它仍可能被打包进浏览器。准备公开部署时，应由后端、Serverless Function 或受保护的网关调用模型。演接入补一句实操判断，凡是用户能打开开发者工具看到的东西，都不算私密，密钥的位置只有一条标准，它有没有离开你的服务器。

有些接口不会马上返回结果

短文本、图片理解和短音频识别通常会在一次请求中直接返回结果，页面显示生成中即可。对话或实时语音可能采用流式返回，内容会一段一段到达，页面可以边接收边展示。

图片和视频生成则常常是异步任务，第一次请求只得到 task_id，随后还要查询任务是排队中、生成中、成功还是失败。这类功能可能要等待几十秒，页面不能一直停在一个没有变化的加载中。

九、先接通文本生成，再做两组验收

DeepSeek API 文档提供兼容常见 SDK 的文本接口。模型会持续更新，接入前应从模型列表复制当前 ID。原文先用 curl 发出一次请求，使用的商品资料和前面在线体验中的内容相同，这样更容易比较两边的结果。

先把环境变量中的 Key 配好，再在终端运行这段命令。得到正常结果后，把同一段官方示例和体验页试好的提示词交给 AI IDE。第一版只保留一个按钮和一组固定的商品资料，确认能从页面得到结果以后，再接入完整表单。

验收分三步。换一组商品名称、材质和颜色，再点击一次生成，如果两次结果都对应各自的输入，并且能被页面正确显示，说明最小接入已经跑通。接着删掉一个字段，检查模型是否会编造价格、功效或销量，也可以暂时填错 Key，看看页面有没有给出失败提示。最后到 Usage 页面确认出现了这几次调用。原文在这一节点出了全章最重要的一句提醒，页面显示了文字，并不一定代表它真的来自 API，原型中残留的模拟数据也可能产生相似效果。演接入的建议是，把 Usage 页面的调用记录截图存进项目文档，它是唯一可信的接入证据。

十、其他能力，同一套路的换用

图片理解

视觉模型接收一张图片和一个问题。页面需要什么信息，就直接问什么，如果只问这张图里有什么，得到的往往是一段很宽泛的描述。原文以 SiliconFlow 模型广场中筛选的视觉模型为例说明输入结构，运行前仍要确认当前 Model ID。原文还给了一个流程建议，先让用户确认模型识别出的商品信息，再生成文案，通常比直接从图片生成最终文案更容易发现错误。这是把第七章的验证思想搬到了接入环节，中间多一次人工确认，错误就少往前传一级。

生成和修改商品图片

Seedream 可以根据文字生成图片，也可以在参考图的基础上进行修改。商品图片最怕看起来很好，但商品本身变了，因此除了描述背景、构图和光线，还要明确哪些地方不能改变。原文示例的描述交代了图片用途、商品位置、画面风格和需要保留的结构。第一次生成后，先检查商品本身有没有变形，再看背景和构图是否合适，不要一开始就在提示词里堆很多风格词。从火山方舟控制台复制当前图像模型 ID 和最小请求，不要长期照抄教程中的版本号。图片 URL 往往有有效期，原型可以直接展示，准备上线时要根据服务条款决定是否转存，并记录提示词、模型版本和生成时间。

语音，识别与合成是两条接口

接入语音至少包含两个方向，ASR 或 STT 把用户说的话或音频文件变成文字，TTS 把文本变成可以播放的语音。它们的输入、输出和页面交互不同，不要放进一个模糊的语音 API 按钮中。

SiliconFlow 语音转文字文档使用 multipart/form-data 上传文件，它与前面的 JSON 请求不同，把官方示例交给 AI IDE 时，要一并说明页面功能。

MiniMax 的同步语音合成接口，当前文档示例使用 speech-2.8-hd，实际模型和音色应以平台页面为准。语音合成的提示词主要体现在朗读脚本和声音参数中，先把数字、英文缩写和停顿改成适合朗读的文本，再选择音色、语速、音量、情绪和输出格式，不要直接把页面上的 Markdown、URL 和按钮文字整段送去朗读。语音页面通常还要提供试听、停止、重新生成和下载，流式 TTS 需要 WebSocket 或流式 HTTP，并在音频到达时逐段播放。合规两条线，上传录音前要告诉用户用途、保存时间和删除方式，声音克隆必须获得音色拥有者的明确授权，不要使用来源不明的公众人物或他人录音。

视频生成，先创建任务，再等待结果

视频生成通常是异步接口。MiniMax 视频生成文档把流程分成三步，创建任务得到 task_id，查询状态得到 file_id，最后获取下载地址。创建与查询是两个请求，页面至少需要显示 Preparing、Queueing、Processing、Success 和 Fail 五种状态。轮询要设置间隔和停止条件，正式产品可以使用文档提供的 callback_url，由平台在任务状态变化时通知服务端。最后是合规，使用真人照片、声音、商标或版权素材生成视频时，要确认授权范围和平台规则，有些服务还要求人脸验证、素材资产登记或内容审核，这不是可以从前端绕过的技术步骤。

十三、实践提示

提示1 · 给你页面的每个按钮写一张能力卡

打开你正在做的原型，给每个会触发 AI 的按钮写一张卡，四栏，用户提交什么，页面显示什么，中间分几步，每步是理解还是生成。写不出四栏的按钮，就是还没想清楚的按钮，先补流程再开服务台。这张卡以后每次接入新能力都能复用，它是你和 AI IDE 之间最短的说明文档。

提示2 · 做一次服务台首访，只找四样东西

选一个平台，注册或登录后严格按原文的四件事走一遍，创建密钥、复制模型编号、找到最小请求示例、看清额度价格和限制，计时二十分钟，到点就停，不逛别的菜单。走完把这四样贴进一个本地密码管理工具或环境文件，再打开用量页面截一张图。第一次走这四步会慢，第二次就是肌肉记忆。

提示3 · 在终端里完成第一次请求，再碰页面

不要直接把示例代码贴进项目。先在终端跑通一次，然后故意做三次破坏，把密钥改错一个字符、把模型编号删掉一位、把地址换成体验页网址，分别看错误信息长什么样。这三个错误覆盖了大多数新手第一次接入的失败原因，认识它们比记住正确姿势更省时间。

提示4 · 给按钮做一次带证据的验收

按原文方法验收，换两组资料各点一次，删掉一个字段看模型是否编造，填错密钥看失败提示。关键动作是最后一步，验收通过后把 Usage 页面的调用记录截图，连同两组输入和输出一起存进项目文档。下次有人问这功能是不是真的接了 AI，你有三样证据，输入、输出、平台账单。

提示5 · 给你的接入流程画一张五步安全卡

按原文五步顺序，给你自己的项目画一张卡，密钥放在哪个文件、调用发生在哪一层、页面调的是哪个接口、按钮有哪三种状态、用量在哪核对。每接一个新能力，对照卡片走一遍。接得越多你越会发现，变的只有功能描述和官方示例，安全这五步一次都不用改。
