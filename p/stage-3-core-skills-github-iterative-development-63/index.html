收尾与边界 · 两遍审查、最终交付，以及什么时候可以放手让它连着跑

本内容改编自开源项目 Easy-Vibe，为二次演绎配音版。配套音频由文本转语音生成，本文是音频的图文解读稿，可独立阅读。

一、这一集讲了什么

前面把流程从需求讨论讲到任务拆分，再讲到逐张自动实现。到这一集，所有任务卡都关闭、测试也全绿——但还差最后一件最关键的事：检查。

本集两个问题：

  1. 收尾质量：为什么任务卡全关掉不等于做完？该怎么检查，分几遍，每遍看什么？
  2. 使用边界：这套流程适合什么项目？什么时候可以放手让它连续跑，什么时候必须亲自盯？

一句话概括：真正可靠的自动开发，不是把所有决定都交出去，而是你负责目标、边界和最终验收，AI 负责把已经确认的事情稳定地执行下去。

二、核心概念拆解

概念一 · 为什么任务卡全关掉还不算完

第一次实现时，智能体的注意力主要在「把当前这张任务做通」——它盯着的是一个点，不是整个面。所以容易留下两类问题：

  1. 代码越来越难维护，能跑但不好改；
  2. 有些需求表面上做了，实际还有缺口。

人性上的阻力：任务卡全绿、测试全过时，心理上已经觉得完成，再检查总觉得浪费时间；而且检查会查出问题，查出问题就要返工。但事实相反——越到后面，改一个问题的成本越高。早期改一个需求可能只是改几行，做完了再改就要动测试、动文档、动依赖它的模块。

概念二 · 第一遍审查：代码是否健康

只看代码本身，不重新讨论产品需求。检查五件事：

#检查项为什么难改
1文件和类型的名字是否容易理解改名牵一发动全身
2同一段逻辑是否在多个地方重复修一个错误要修多处，漏一处留隐患
3一个界面文件是否承担了太多工作改动冲突概率高，难定位
4修改一个小功能是否要动很多无关位置模块边界划错，架构层面的债
5是否遵守仓库约定文件仓库风格越来越散

本例发现：主界面文件过大；「跟进天数」只是普通整数，容易绕过最小一天校验 → 拆分界面职责，把跟进周期改成会主动校验的数据类型。

落地建议：不要一次改完所有问题。按影响面从大到小排序，一次处理一类，每处理完一类跑一次测试，便于定位。

概念三 · 第二遍审查：需求是否真的完成

不评价代码漂不漂亮，而是重新打开需求文档和所有任务卡，逐条核对四件事：

  1. 有没有遗漏的要求；
  2. 有没有只做了一半的功能；
  3. 界面看起来存在，但实际行为是否正确；
  4. 有没有擅自增加不在第一版范围内的功能（多做出来同样是问题——不在验收范围里，没人测过，也没人负责）。

本例查出的五个真实问题：

#问题为什么测试没抓到
1表格文件出现两个同名表头时报运行时错误，而非安全提示测试里没有这个用例
2没有邮箱的联系人，无法通过「姓名+组织」识别为同一人测试用的是带邮箱的数据
3待跟进列表没有使用与主列表相同的筛选条件测试只测了主列表
4数据能保存，下次启动却不会自动恢复根本没有这条测试
5详情页没有明确显示计算出的下一次跟进日期测试不检查界面上的数字

共性：它们不是代码写错，而是需求里写了但实现时漏掉。这类问题只有一种办法能抓到——拿着需求文档一条一条对。

概念四 · 最该记住的一句话

测试全部通过，只能证明「已经写进测试的行为」没有出错，不能自动证明最初的需求一条都没有漏。

测试用例覆盖的是当时想到的情况；需求文档里的要求如果没被写成测试，做没做测试根本管不着。

正确的修复顺序：先补测试 → 再改代码 → 重新跑两遍检查。先补测试等于把问题固化成可复现的检查，改完才能确认真的修好了，而不是看起来修好了。修改本身还可能引入新问题，所以两遍检查要重跑。

提示1 · 把需求变成「是/否问题」，做实需求覆盖率

把需求文档里的每一条要求，都变成一句可以回答是或否的问题。例如「数据要在下次启动时恢复」→「关掉应用再打开，之前的数据还在不在？」

这样第二遍审查就不是凭感觉看，而是在一张清单上打勾，全部打完才算真的做完。

额外好处：它会暴露需求文档里含糊的地方。一条要求如果没法变成是/否问题，说明这条需求本身就写得不够清楚，该回去改文档，而不是靠猜去实现。

提示2 · 指令的约束比目标更重要

四条关键指令的共同结构：开头交代背景与目标，结尾加一段约束。约束各不相同，但性质相同——防止它自作主张。

指令约束防的是什么
需求讨论在你明确确认之前不要开始写代码防止抢跑
生成 Spec不要重新问已经确认的问题防止已收敛的讨论被重新打开
拆分任务卡不要把数据、界面和测试完全分开防止按技术分层拆任务
自动实现每次只处理一张当前可以开始的任务防止同时开工多件、最后都没做完

写指令时，花在约束上的心思应该跟花在目标上的一样多：目标决定它往哪走，约束决定它会不会走偏。

提示3 · 功能增加 = 重新划定边界

第一版用固定的 6 个假联系人而非真实通讯录，是因为读取系统通讯录要申请敏感权限，一旦涉及权限就要解释为什么需要、数据怎么用、会不会上传。

源文档特别写明：真实产品若增加云同步、联系人权限、加密或 AI 分析，需要重新讨论隐私边界，并记录新的架构决定。

记住：增加功能不只是加代码，更是重新划定边界。

提示4 · 连续跑的三个对策

放手让它连续跑，最大的风险不是做错，而是做错了你不知道。

  1. 任务粒度要小——每张任务卡都是能独立验证的小功能，跑偏也只影响一张；
  2. 每张任务单独提交——提交就是回滚点，可精确退到某一步；
  3. 经常运行测试和完整构建——相当于给连续跑装了检查站，过了才继续。

共同思路：把长跑切成一段段短跑，每段之间有个明确的确认点。

提示5 · 能被自动验证是前提

如果你的项目根本没有测试也没有构建命令，那这套流程就失去了它的刹车。判断方法很简单：这件事做错了，能不能一键回到做之前的状态？ 能，就可以放手；不能，就老实盯着。

五、审查清单（收尾前逐条过）

  1. 所有任务卡都关闭了吗？——关闭不等于做完，继续往下。
  2. 第一遍代码检查做过了吗？五项检查逐条看过？
  3. 发现的问题是否按影响面排序、分批修、每批跑测试？
  4. 第二遍需求核对做过了吗？需求文档逐条打勾了？
  5. 是否检查了「多做出来的东西」而不只是「漏掉的东西」？
  6. 修复顺序是否为「先补测试 → 再改代码 → 重跑两遍」？
  7. 需求文档里含糊的条目是否已回去改清，而不是靠猜实现？
  8. 四个必须亲自确认的节点是否都确认过？
  9. 是否亲眼打开了真实界面，而不只是看它的总结？
  10. 涉及付费、部署、删数据、权限、隐私的操作是否逐项确认？

六、常见误区与纠正

误区实际情况纠正办法
任务卡全关 = 做完了只是点上做通，面上还有缺口两遍检查缺一不可
测试全绿 = 需求没漏只证明写进测试的行为没错回需求文档逐条核对
发现问题直接改代码无法确认是否真修好先补测试，再改代码
只盯着漏了什么多做出来同样是问题同时检查范围外功能
一次改完所有问题出问题无法定位按影响面分批，每批跑测试
验收看它的总结就行它说做完了不算数亲自打开真实界面

七、能力自测（五问）

  1. 任务卡全部关闭之后，为什么还要做两遍检查？
  2. 第一遍检查的五件事分别是什么？
  3. 「测试全部通过」这句话的边界在哪里？
  4. 发现需求缺口的正确修复顺序是什么？
  5. 四个必须亲自确认的节点是哪些？

参考答案：1）它只盯着当前任务这个点，面上会留下难维护或缺口两类问题。2）命名、重复逻辑、界面文件过大、改小功能要动多处、是否遵守约定。3）只证明写进测试的行为没错，不能证明需求没漏。4）先补测试 → 再改代码 → 重跑两遍。5）需求讨论结束时、创建任务卡前、涉及敏感外部操作时、完成后打开真实界面。

八、常见疑问三问

疑问一：第一次走这套流程太慢，值得吗？

第一次一定觉得啰嗦——要写文档、要拆任务、要检查两遍，远不如直接让它写代码快。但价值在第二次、第三次继续开发时才显现：前面留下的需求文档、任务卡、依赖、提交和测试，会让它不必从头猜测。判断值不值，看的是项目会不会有第二版，而不是第一版快不快。

疑问二：小项目也要两遍检查吗？

可以按比例缩减，但不要整个跳过。小项目建议至少做一次「需求逐条打勾」，因为小项目的需求文档通常更短，打勾成本很低，收益却不低。第一遍代码检查在小项目里可以简化为「有没有明显重复和大文件」这两项。

疑问三：它说完成了但我打开发现不对，怎么办？

这正是「完成后亲自打开真实界面」这个节点存在的意义。发现不对就走标准流程：先把问题写成一条可复现的检查（测试或明确的是/否问题），再修，修完重跑。同时回头看，这个问题是需求文档写得含糊，还是实现时的疏忽——前者改文档，后者补检查，两者的处理方式不同。

九、三十分钟上手练习

  1. （5 分钟） 打开你最近做完的一个小项目，列出它的三条核心需求。
  2. （10 分钟） 把每条需求改写成一句「是/否问题」，共三句。
  3. （5 分钟） 按这三句逐个实测，记录哪些能通过、哪些不能。
  4. （5 分钟） 对不能通过的，先把它写成一条测试或明确的检查步骤，再修。
  5. （5 分钟） 修完重跑一遍三句检查，确认全部通过。

走完这五步，你会亲身体会到「需求覆盖率」和「代码覆盖率」的差别——很多问题不是代码错，而是根本没被检查过。

场景推荐做法说明
一次性小工具只做需求逐条打勾，跳过代码检查用完即弃，难维护不是问题

十一、时间不够时怎么砍

保留项可砍项说明
需求逐条打勾代码健康五项全查前者直接发现漏项，后者是长期债

十二、一页纸总结

一句话记住：测试全部通过，只证明写进测试的行为没错，不能证明需求没漏。

两遍检查：第一遍看代码健不健康（五项）；第二遍看需求有没有真做完（四条 + 打勾）。

修复顺序：先补测试 → 再改代码 → 重跑两遍。

适合连续跑：范围可收敛的最小可用版本；有明确验收标准；能被测试或构建验证；需要跨会话持续工作。

不适合：需求每小时在变；无法自动验证；直接操作生产数据。

四个亲自确认的节点：需求讨论结束时、创建任务卡前、涉及敏感外部操作时、完成后打开真实界面。

一句话记牢：你负责目标、边界和最终验收，AI 负责把已经确认的事情稳定地执行下去。

十三、一分钟复盘

这套方法最重要的不是记住几个命令，而是把开发过程变成一条随时可以查看、暂停和继续的路线。

当一段聊天结束之后，需求文档、任务卡、依赖关系、提交和测试仍然留在代码托管平台里。下一次继续开发时，它不需要从头猜你想做什么，而是可以沿着这些记录继续往前走。

迁移建议有三条：先选一个范围不大的真实需求完整走通一次；把验收标准提前准备好；接受前几次会比较慢。第二次、第三次继续开发时的速度，是闷头写一小时代码换不来的。
