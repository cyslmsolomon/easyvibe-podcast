一、这一集在解决什么问题

上一集引入了「CLI AI 编程工具」这个概念，本集正式落地到具体产品，并解决三个很现实的问题：

  1. 它到底是什么、能干什么 —— 与 AI IDE 中的 Agent 有什么不同；
  2. 官方太贵怎么办 —— 如何在不动工具本身的前提下，把背后的模型换成更便宜的；
  3. 怎么在多个模型之间调度 —— 路由工具的定位、安装与配置。

三、逐节解读

3.1 为什么它比普通 IDE Agent 更适合氛围编程

原文给出的四条优势中，「可以主动澄清模糊需求」这一条尤其关键。普通补全类工具倾向于硬着头皮猜测，而它会先反问确认——这一步把大量返工挡在了写代码之前。

配合「极长上下文（可处理完整文件甚至小型项目）」与「对整个代码库的深度理解」，它就具备了接手端到端任务的前提：看得全 + 会追问 + 能规划。

3.2 成本问题的解耦思路

原文的处理非常务实：工具本身不动，只替换背后的模型接口。

这在架构上叫「关注点分离」，落到具体操作上就是两条路线：

路线做法复杂度原文建议
方案一直接使用兼容 Anthropic 接口的国产模型 API低先入手这条
方案二使用 Claude Code Router 做智能分发中高跑通方案一后再尝试

费用方面原文给出了明确的量级参考：GLM 月度套餐约 20 元/月；想试水可先充值 10 元做小规模试验。同时提醒：该工具通常会消耗大量 token，这是预算必须提前考虑的事实。

3.3 环境变量：只需要理解两件事

原文的科普很长，但可以压缩成两件事：

  1. 它是键值对的外部配置 —— 程序读取即可，不必写进代码，因此密钥存这里最安全；
  2. PATH 决定命令能否被找到 —— 之所以输入 claude 就能启动工具，是因为 PATH 里记录了可执行文件所在目录。装完命令行工具却提示「找不到」，八成是它的目录没进 PATH。

操作上的硬性提醒：若是通过 AI IDE 配置永久环境变量，配置完成后必须重启该 IDE，否则其内置终端的环境变量不更新，可能导致登录失败或网络连接错误。

后端招牌能力适合谁

演绎方提炼一个通用判据：看任何模型介绍，先抓「上下文长度、中文理解、性价比」这三项，其余多为次要指标。

3.5 路由工具解决的两个具体问题

原文把它解决的问题说得很直白：

  1. 单一模型无法覆盖所有场景；
  2. 频繁切换平台很麻烦。

它的机制是「按场景路由 + 转换器适配不同平台的接口格式」。原文的例子极具启发性：后台任务交给本地 Ollama 省成本，长文本交给擅长长上下文的模型，代码讲解交给性价比高的那个。

演绎方的理解：这本质上是团队分工模型 —— 不追求万能成员，而是让专长者在合适的环节上场。

3.6 进阶用法里最值得养成的三个习惯

原文列出的命令很多，其中三个习惯性价比最高：

  • /clear 与 /compact —— 长时间会话后清理或压缩上下文，防止信息过载让工具「跑不动」；
  • /cost —— 随时查看当前消费，配合前面提到的 token 消耗量，这是最直接的预算护栏；
  • 维护 CLAUDE.md —— 把常用命令、核心文件、代码风格、测试方式、协作规范、环境配置、已知坑点沉淀进去。原文强调它没有强制格式，只要简洁、便于人类阅读即可。

3.8 CLAUDE.md 应该写什么

原文给出的建议清单很完整，可以直接当作模板使用：

  • 常用终端命令 —— 省去每次重复说明；
  • 核心文件与工具函数 —— 让工具第一次就能找对地方；
  • 代码风格约定 —— 命名、格式、注释偏好；
  • 测试方式说明 —— 怎么跑测试、跑哪些；
  • 仓库协作规范 —— 分支命名、用 merge 还是 rebase；
  • 开发环境配置说明 —— 是否用 pyenv、推荐哪个编译器；
  • 项目中需要特别注意的坑点 —— 那些踩过一次就忘不掉的地方；
  • 任何你希望它记住的信息。

原文强调的格式要求是「没有强制格式，只要简洁、便于人类阅读即可」。演绎方补一句检验标准：写完之后假装自己是个刚接手项目的新人，看能不能照着它立刻开工。

四、审查清单

  • 已理解工具定位是执行者，而非聊天窗口
  • 已选定一条低成本接入路线（推荐先走兼容 API）
  • 已获取目标后端的 API Key 并妥善保存
  • 环境变量配置完成，且已重启 AI IDE 使配置生效
  • 终端能正常启动工具（若提示找不到，检查 PATH）
  • 已用 /cost 查看过一次消费，建立了预算感知
  • 长会话后已使用 /clear 或 /compact 清理上下文
  • 项目根目录已有 CLAUDE.md 并记录了核心约定
  • 若使用路由工具，已指定默认模型并保存重启
  • 对比过至少两个后端的实际效果，而非仅凭口碑选型

五、实践提示

提示1 · 先跑通简单方案，再折腾复杂方案

原文明确建议「先从第一种方案入手」。原因是复杂的中间层会掩盖底层问题：一旦配置出错，你分不清是模型不行、密钥不对，还是路由层的锅。先把最简单的链路跑通，再往上加抽象层。

提示2 · 用 /cost 建立预算直觉

这类工具 token 消耗量大，账单往往是事后才发现。养成习惯：每次长任务结束都看一眼消费。连续记录几次之后，你就能估算出「一件大约多大的活要花多少钱」，这是控制成本最有效的方式。

提示3 · 把 CLAUDE.md 当成团队的入职文档写

不要把它写给自己看，要写给「一个刚接手项目、什么都不认识的人」看。检验标准很简单：一个陌生人照着这份文件，能不能立刻开始干活？ 能，就写对了。

提示4 · 换模型前先明确你到底要换什么

如果是因为贵 → 换性价比更高的底座；如果是因为慢 → 换响应速度快的；如果是因为长文件读不全 → 换上下文更长的。这三个问题是不同的，答案也不同。 盲目换模型，常常是花同样的钱买到同样的困扰。
