一、这一集在解决什么问题

到这一集为止，账号体系已经能完成「邮箱注册 → 邮箱登录 → 退出登录」的闭环。但一个真实产品会立刻被用户追问三个问题：

  1. 为什么要我再记一个密码？ —— 第三方登录诉求；
  2. 密码忘了怎么办？ —— 密码重置诉求；
  3. 我传的头像、商品图放哪？别人发的东西我为什么看不到？ —— 文件存储与实时性诉求。

原文用一个连续的编号序列回答了这三个问题：5.2.3 到 5.2.5 解决前两个，5.3 解决实时，5.4 解决文件。这四个小节在原文中属于同一页的连续内容，因此本集把它们合并为一集，主题统一为「让应用从单机展示页，变成一个多用户、能联动、能承载个人文件的产品雏形」。

三、逐节解读

3.1 第三方登录：为什么一定分成两半

原文把配置拆成 5.2.3（去 GitHub 登记）和 5.2.4（回 Supabase 填 Provider），这个拆分不是随意的，它对应 OAuth 授权码模式的本质——信任是双向的。

  • 你向 GitHub 声明：我的站叫这个名字，主页在这个地址，授权成功后请把用户送回这个回调地址；
  • GitHub 给你一对凭证（Client ID + Client Secret）作为你在 GitHub 侧的身份证；
  • 你把这对凭证交给 Supabase，Supabase 才被允许代表你去和 GitHub 对话。

所以顺序不能反：没有 Client ID 和 Secret，5.2.4 的输入框无从填起。

回调地址这一栏最容易填错。原文明确指出它的格式是 https://<项目>.supabase.co/auth/v1/callback，并且可以在 Supabase Dashboard 的 Authentication → Providers → GitHub 页面直接复制。不要凭记忆手敲，项目域名部分每个项目都不一样。

3.2 密码重置：四步流程里的安全边界

原文给出的四步是：前端调用 resetPasswordForEmail() 并指定 redirectTo → Supabase 发送含唯一重置链接的邮件 → 用户点击链接被重定向到应用内重置页 → 前端调用 updateUser() 提交新密码。

这里有一个值得单独拎出来的架构判断：整个流程中前端不做身份判定。前端只负责「代用户提交一个请求」和「代用户提交一个新密码」，真正的合法性校验由后端那条一次性链接承担。因此 redirectTo 必须指向你自己应用内的页面——一旦指向别处，链接的效力就被转移了。

3.3 实时功能：三条能力，三种关心

原文用三个小节讲了三种实时能力，初学时最容易把它们混为一谈。一个有效的区分方式是看「它关心什么」：

  • Postgres Changes 关心「发生了什么事」——数据真的落库了，并且被推送出去，是持久化的；
  • Presence 关心「谁在这儿」——维护的是一份在线名单，是共享状态；
  • Broadcast 关心「此刻在传什么话」——高频、临时、不落库，直接走 WebSocket 绕过数据库。

一句话使用规则：要留痕的用数据库变更，要名单的用 Presence，要高频临时的用 Broadcast。

3.4 存储：为什么文件不能放进业务服务器

原文给出两条理由：体积差异大、数量可能极多。演绎方补充一层理解——这两条理由共同指向一个结论：文件的增长曲线和结构化数据的增长曲线完全不同。用户表可能几千行，但商品图可能几万到几十万张，把它们放在同一个存储引擎里，读写性能会互相拖累。

访问方式上的观念转变同样重要：你不是去对象存储的「底层仓库」里翻文件，而是拿一个唯一 URL。这个 URL 对前端来说就是一个可以直接加载的资源地址，业务服务器不需要中转，既快又减压。

3.5 三种能力怎么组合使用

单独理解三种能力之后，还需要知道它们怎么配合。原文给出的实时聊天室示例本身就是一个组合范例：聊天消息走 Postgres Changes，在线名单走 Presence，「正在输入」或光标位置走 Broadcast。

  • 聊天消息必须留痕：刷新页面后历史消息还在，所以它必须落库，变更再通过监听推送给所有人。
  • 在线名单不需要留痕：它描述的是「此刻」，人走了就该消失，所以交给 Presence，断线由服务器自动清理。
  • 正在输入、光标位置这类信号，既不需要留痕，频率又极高：走 Broadcast 直接绕过数据库，延迟最低。

把这三句话连起来，就得到了一条可复用的设计规则：先问这条数据要不要留痕，再问它出现的频率高不高，答案确定之后，用哪种能力就自然确定了。 不需要凭感觉挑。

3.6 关于「让 AI 参考示例项目」

原文在 5.2.4 和 5.2.5 两处都给出了同一个建议：直接让 AI 参考配套示例项目，在自己项目基础上复刻对应功能。这个建议值得认真对待，因为它体现了这一整套教程的核心方法论——通用能力不自己从零写，而是借助 AI 去复用一份已经跑通的参考实现。

但复用有前提。你至少要知道三件事：这个功能分几步（比如密码重置的四步）、每一步谁负责（前端还是后端）、以及哪个环节是安全边界（那条一次性链接）。知道这三件事，你才判断得出 AI 生成的代码对不对。这也是本集把流程拆开讲一遍的原因：先听懂，再复刻。

四、审查清单

这一集的成果是否真的可用，按下面逐条打勾：

  • OAuth 应用的 Callback URL 是从 Supabase 控制台复制的，不是手敲的
  • Client Secret 在生成后当场复制并保存，且没有提交进代码仓库
  • Google 与 GitHub 两个 Provider 都已启用并保存，不是只填了一半
  • 密码重置的 redirectTo 指向应用内页面
  • 已实际收到并点开过一封重置邮件，确认链接可用
  • 若改动过邮件模板，确认链接变量没有被误删
  • 需要监听的表已加入 supabase_realtime publication（或在 Table Editor 启用 Realtime）
  • 订阅代码里事件范围收窄到指定表与指定事件类型，而不是监听整库
  • 频道命名有业务含义，不同功能用不同频道隔离
  • Presence 的 channel 配置里指定了唯一标识当前用户的 key
  • Broadcast 的事件名在发送端与接收端完全一致
  • 上传端点指向的是可续传接口，而不是普通上传接口
  • 前端渲染图片用的是对象存储返回的 URL，不经业务服务器中转

五、实践提示

提示1 · 凭证只出现一次，把它当成一次性用品

Client Secret 生成后只显示一次，刷新页面就再也看不到，只能重新生成。实践上的做法是：生成 → 立刻复制 → 粘贴进 Supabase 的配置框 → 随后才关页面。不要先关页面再想起来没保存。同样重要的是，这对凭证不要写进前端代码、不要提交到公开仓库。

提示2 · 订阅范围宁窄勿宽

Postgres Changes 允许你监听整张表的所有事件，也允许你只监听 INSERT。默认请选后者。监听范围越宽，前端收到的无用推送越多，处理逻辑越容易失控，而大多数业务场景只需要其中一种事件。

提示3 · 判断什么该落库，什么该走广播

一个简单的判据：这条数据在页面刷新后还需要存在吗？ 需要 → 走数据库变更监听；不需要（光标位置、正在输入的提示、临时表情）→ 走 Broadcast。把光标位置写进数据库是最典型的误用，会产生大量无意义的写操作。

提示4 · Presence 的 key 必须是稳定且唯一的

Presence 用一个 key 标识当前用户，通常用用户 ID。不要用随机值或会话 ID——否则同一个人开两个标签页会被算成两个人，在线名单立刻失真。
