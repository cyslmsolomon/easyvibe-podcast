一、这一集在解决什么问题

很多用 AI 写代码的人停留在「聊天式问答」：问一句、答一句，项目一大就乱，昨天聊的方向今天忘了，需求变了无处追溯。这一集用一个完整案例回答一个问题：怎么把一次性对话，变成可累积、可追溯、可验证的工程过程。

案例是「关系指南针」（Relationship Compass），一个 macOS 原生的私人关系维护工具。主角不懂 SwiftUI、数据库、测试框架，只负责把使用体验讲清楚。原文展示了四步流程：

  1. 需求讨论 —— 和 AI 多轮对话，把模糊想法收敛成明确的第一版范围；
  2. to-spec —— 把确认过的内容写成规格文档，仓库文件与总 Issue 双落地；
  3. to-tickets —— 纵向切片拆成有顺序的任务卡，带优先级、验收标准与阻塞依赖；
  4. implement —— 逐张任务卡实现，每张卡先证明「现在还不行」，再写到测试通过。

音频稿按四步流程重排，并把原文的对话实录压缩为「三轮收敛」的叙事。

三、逐节解读

3.1 三轮对话怎么把方向聊清楚

原文的对话实录是本节的骨架。演绎方把它压缩成三轮，每轮只做一件事：

轮次AI 的动作用户的行为收敛结果
第一轮建议技术底座，问三个范围问题做选择题：原生、只导表格、不联网砍掉账号、服务器、通讯录
第二轮指出产品定性（私人关系工具而非销售漏斗）补关系信息：强度、圈子、备注、互动定义最小闭环的构成
第三轮给出具体首版范围并用提问收尾确认范围，明确三个「不做」达成共识，进入规格

值得学的是用户的说话方式：全程只说使用体验，不说任何技术词。「我想看到哪些人该联系了」是需求，「按最近互动和跟进周期计算」是用户自己提出的验收逻辑——这两句话比任何技术描述都更有信息量。

第一轮三个问题（通讯录、云同步、导入方式）都在做同一件事：砍首版负担。首版范围越小，验证越快。

3.2 项目语言与 ADR：两件最容易被跳过的小事

原文把这两件事放在讨论阶段末尾，位置很讲究——它们不是文档任务，是防返工地基。

项目语言解决的是歧义。Contact 可以是联系人也可以是销售线索，Follow-up 可以是任务、提醒或通知。写进 CONTEXT.md 后，代码、测试、任务卡共用一套说法，AI 不会这次写 Contact、下次改 Lead。演绎方的经验：这类术语表在多人项目里价值更大，它是成本最低的「防精神分裂」机制。

ADR（架构决策记录）解决的是「为什么」。原文只记两条：本地优先不读通讯录、用原生 SwiftUI 不用 Electron 或 Web 壳。判据原文说得很清楚：以后很难改、且存在明显取舍，才值得单独记。演绎方补一条验收标准：三十秒能看完一条，看完能明白当时为什么这么选。 写太长的后果和写太多一样——没人看，等于没写。

3.3 共识暂停：看起来最慢，实则最快

原文强调 AI 会主动询问「是否已达成共识」，确认后才进下一步。这个暂停的经济学一目了然：此时改一句话几秒钟；等二十个文件写完再发现方向错，返工成本是天量。

确认共识时手上有五样东西：功能范围、「不做什么」清单、统一用词、少量技术决定、一次明确确认。原文特别点出：此时还没开始实现任何功能，是正常的。

演绎方补一层机制解释：聊天记录是易碎品，窗口一关、上下文一压缩，昨天的讨论就模糊了；提交进仓库的文件才稳定。所以确认后的结果必须落库——CONTEXT.md 存用词，docs/adr/ 存决策，提交到 GitHub。这一步做完，仓库的角色是「已确认上下文的保存者」，还不是任务看板。

3.4 好规格的判据：描述行为，而不是描述文件

原文给出的规格四问（解决什么问题、用户能做什么、什么不在范围、怎么判断做好）可以直接当检查清单用。两个演绎方重点展开的点：

第一，用户故事三要素。 原文的例子——「作为用户，我希望从未记录过互动的联系人也出现在待跟进列表中，这样刚导入的人不会被悄悄忘掉」——包含谁需要它、希望发生什么、为什么有价值。它不规定 Swift 文件叫什么，所以将来重构代码，这条需求依然成立。规格对抗的是时间，不是代码。

第二，验证入口提前定。 本项目把 RelationshipStore 对外功能当主要测试入口，自动检查七类行为（样例初始化、搜索筛选、导入校验去重、保存恢复、档案编辑、互动时序、跟进日期计算）。关键在「只关心用户最终能观察到的结果，不关心内部函数被调用几次」——这是测试不会因重构批量失效的原因。

同一份需求双落地：仓库 Markdown 管版本管理与代码审查，总 Issue #1 管项目入口与状态跟踪。需求变更先改 Spec 留提交，「为什么变、何时变」才有据可查。

3.5 纵向切片与依赖：任务拆解的两个关键决策

原文对拆任务的论述可以浓缩成两句话：按技术层横拆是陷阱，按功能纵切是正解。

拆法每张票的内容做完能看到什么
横向（反例）一张只建模型、一张只写界面、一张只补测试前几张做完，用户什么都用不上
纵向（正例）数据、界面、测试打包进同一张关一张票，多一个可演示的小功能

原文的五张票是纵切的范本：#2 浏览样例联系人（P0，无前置）→ #3 导入保存（P0，等 #2）→ #4 关系档案（P1，等 #2）→ #5 互动跟进（P1，等 #4）→ #6 打磨验证（P2，等 #3 和 #5）。每张都有完成标准，关一张就多一个完整小功能。

两个概念原文做了区分，演绎方认为这是本节最容易被混淆的地方：

  • 优先级（P0/P1/P2）表示重要程度；
  • 阻塞依赖（Blocked by）表示现在能不能做。

一张 P0 的任务，如果前置没完成，照样得等。「任务前沿」的白话解释就是「当前没被卡住的票」——流程刚开始只有 #2 能动手，#2 完成后 #3、#4 解锁，#5 等 #4，#6 等两条线汇合。

3.6 逐张实现：把进度交给 Issue 状态

implement 的选票逻辑三项过滤：ready-for-agent 标记（人已审核）+ 优先级 + 阻塞关系。三项一过，当前该做哪张没有悬念——这一步的价值不只是效率，更是消除 AI 的随意性：它不会挑一个顺眼的功能开工。

每张任务完成后做四件事：留下一个主要提交、把提交与测试结果写回 Issue、移除 ready-for-agent 加 completed-by-agent、关闭后领取下一张。原文的原话值得引用：GitHub 上的 Issue 状态就是项目的真实进度，而不是一份需要手动维护、很快就会过期的旁观清单。

演绎方补一个对个人开发者的意义：任务卡写清状态后，人离开几天回来，看板即进度，不必翻聊天记录回忆——项目管理从脑子里挪到了仓库里。

3.7 TDD：每张任务先证明「现在还不行」

原文以 CSV 导入票为例给了六步序列，是整套流程里最「反直觉」也最值钱的一步：

  1. 先写测试：同一份 CSV 导入两次，联系人数量不能翻倍；
  2. 运行，确认当前确实做不到；
  3. 实现读取与去重，让测试通过；
  4. 再补测试：表头错误时原联系人不能被破坏；
  5. 修正实现，重跑本组测试与完整构建；
  6. 提交、关闭 Issue、领取下一张未被阻塞任务。

人的本能是先写实现再看结果，TDD 是先立标准再看实现。标准立不住，实现就是空中楼阁。本项目最终 13 项行为测试，swift build 与 swift test 全部通过——这 13 项测试此后每次改动自动跑，改坏立刻知道。

四、审查清单

  • 已完成至少三轮需求对话，每轮只收敛一个问题
  • 首版范围用「做什么 + 不做什么」双清单写清
  • 关键歧义术语已写进 CONTEXT.md（或同类上下文文件）并提交
  • 只记录了少数真正难改且有取舍的 ADR，每条三十秒能读完
  • AI 询问共识时做了明确确认，未在未确认时进入下一步
  • 确认结果已提交进仓库，而非只留在聊天记录里
  • Spec 四问可逐条回答：解决什么问题、用户能做什么、不在范围、怎么算完成
  • Spec 描述的是行为，未过早规定文件名与目录
  • 验证方式已在规格中提前说明，且测行为不测内部实现
  • 同一份需求已双落地：仓库文档 + 总 Issue 入口
  • 任务为纵向切片，每张票关闭后可演示一个完整小功能
  • 每张票有优先级、完成标准、前置依赖（用 Blocked by 表达）
  • 能区分「优先级高」与「现在可做」，未让高优先级跳过依赖空等
  • implement 只从 ready-for-agent 中按优先级与依赖选票
  • 每张任务一个主要提交，出错可定位到具体任务
  • Issue 状态已回写（标记切换 + 结果写回），看板即真实进度
  • 每张任务先写测试并确认失败，再补实现
  • 完整构建与全部测试通过后才关闭任务

五、实践提示

提示1 · 把「确认共识」当成硬门槛，不确认不动手

原文中 AI 会主动暂停询问，这个暂停要当成流程硬门槛。判断标准很简单：你能否脱口说出首版做什么、不做什么、怎么算完成。 三个问题有一个答不上，就继续聊。省下的返工时间，比多聊的几轮值钱得多。

提示2 · 术语表是成本最低的防返工地基

Contact、Follow-up 这类词的歧义，平时不显眼，一旦 AI 开始混用，代码里会出现三套命名，测试跟着写三套。开工第一周就把术语表定下来，写进上下文文件。统一语言这件事，做的时候没人感念，不做的时候全员受苦。

提示3 · 验收标准写在拆票时，不要等实现时

每张票的「完成后能看到什么」必须在拆票阶段写死，例如「CSV 导入去重、JSON 打开保存」。写在拆票时的标准是需求，写在实现时的标准是解释。前者能拦住 AI 随意发挥，后者只会给已发生的偏差找理由。

提示4 · 别让 P0 情结架空依赖

优先级回答「多重要」，依赖回答「能不能现在做」。常见失误是盯着 P0 不断加急，结果它在等一个没完成的前置，空转。正确做法是每天只看任务前沿——当前没被卡住的票——从那里开工，被阻塞的再急也帮不上忙。

提示5 · 先证明不行，再动手写

每张任务开工第一件事是写一个会失败的测试。它同时解决两个问题：证明你理解了需求（写不出测试通常是没想清楚），以及给实现立好规矩。跳过这一步的代价，是测试变成事后补作业，规矩永远立在偏差后面。

七、这一集在整条链路上的位置

在「用 AI 做完整项目」这条技能线上，本集是工程化方法的枢纽：

  • 之前的篇目解决「单个功能怎么让 AI 写出来」；
  • 本集解决「一个完整项目怎么让 AI 连续做出来」——靠的不是更长的提示词，而是把上下文、需求、任务、进度全部落到仓库与 Issue；
  • 之后的篇目（多智能体协作）则在本集基础上叠加「并行」：单人单智能体的流水线跑通之后，才谈得上让多个智能体分工。
