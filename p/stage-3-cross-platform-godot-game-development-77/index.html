一、这一集在解决什么问题

上一集讲到三维世界的门口，这一集把门推开，回答三个具体问题：

  1. 怎么搭灰盒——用最简单的几何体做出第一个能跑的三维场景；
  2. 灰盒到成品隔着什么——逐层替换的七层顺序，以及原型与商业产品之间的真实差距；
  3. 怎么判断原型算不算游戏——选一个原型打磨，请真人试玩五分钟，按三条标准记录。

全篇有一条贯穿的判断标准：

可玩的灰盒，比不能移动的精美场景更接近真正的游戏。

这句话反直觉，但它是整集所有建议的锚点。一个能动、能跳、能抵达目标的灰盒子已经验证了游戏最核心的东西；一个精美却不能操作的场景，本质上只是一张效果图。

三、用简单几何体搭灰盒

新建第三个 Godot 项目，然后说：

请创建一个 3D 场景，加入地面、胶囊玩家、摄像机和远处的门。

接下来才是重点——先在编辑器的 3D 视图里检查比例。三维比二维多一个深度维度，肉眼很容易被骗，看着差不多大的两个物体可能差了好几倍。

检查三件事：

  1. 玩家不能埋进地面；
  2. 摄像机要看得到角色和目标门；
  3. 碰撞体大小要和可见模型接近。

第三条最容易被忽略，却直接决定手感：碰撞体大一圈，玩家觉得在隔空撞墙；小一圈，又觉得穿模。

提示1 · 为什么非要用胶囊和方块

因为它们不带任何美术承诺，想改就改，不会因为舍不得画好的素材而将就一个错误的设计。灰盒的本质，是用最低成本换取最大的修改自由。 等正式模型进来，每次调整都要重新导出、重新绑定、重新检查比例，改设计的意愿会直线下降。

如果摄像机里看不到玩家：

运行后看不到玩家，请只调整摄像机位置和朝向。

四、补上灯光、阴影和目标反馈

灰盒不是把所有物体都留成默认灰色。只要目标不清楚，就无法判断空间设计是否有效。

先增加基本光照：

请加入环境光和方向光，并给方向光开启阴影。

为什么要开阴影？ 在三维里判断一个物体离地多高，靠的主要就是影子。没有影子，悬浮平台和地面看起来像贴在一起，跳跃判断会完全失真。

再强调目标：

请让远处的门发青色光，并让玩家一开始就能看到它。

方向光、投影、环境颜色、发光材质和目标门，这些反馈都应该在正式模型进场以前跑通。顺序不能反——等你换上精美模型才发现玩家不知道往哪走，调整成本会高得多。

提示2 · 灰盒阶段就觉得好看，说明灯光做对了

灯光几乎是三维场景里性价比最高的投入：性能负担很小，却能立刻拉开空间层次。反过来，模型精致但灯光全平的场景会像贴纸一样单薄，这是新手三维作品最常见的通病。

五、从灰盒走向正式 3D 游戏的七层顺序

不要把所有工作合并成一句「做得更精美」——那不是需求，是许愿。生产项目的做法是逐层替换：

顺序做什么为什么在这个位置
1锁定移动速度、镜头距离、碰撞和关卡尺度不可逆决定，后面一切都围着它走
2把玩家、目标门、互动道具拆成独立场景复用与解耦的前置条件
3用占位模型验证路径，再从 Blender 导入正式模型先证路径可行，再付美术成本
4为材质建立统一规则不透明、透明、发光、地表分别处理
5用 AnimationTree 管动画，用信号/状态机管互动行为与表现分离
6给目标门加进入检测、声音、粒子和完成反馈反馈先于内容
7用 Profiler 和可见性工具检查 CPU、GPU、阴影和绘制调用性能是测出来的，不是看出来的

提示3 · 先做不可逆的决定，后做可逆的

关卡尺度和碰撞手感一旦定了，后面所有美术和内容都要围着它走，改起来代价极大；而材质、粒子和特效随时可替换。这条原则不只适用于游戏，任何工程排期都能用。

六、原型和成熟产品之间隔着什么

参考的商业三维游戏包含多个区域、武器系统、敌人和任务，而这个练习只取了「用轮廓、色彩和目标引导玩家」这一小点。

原型和成熟产品之间不是一条提示词的距离，而是一轮轮玩法、关卡、美术、音频和性能验证。

游戏开发的绝大部分工作不是写代码，而是反复验证：验证手感、验证关卡节奏、验证玩家能不能看懂。这些验证无法自动化。

所以正确的期待是——让工具帮你快速搭出可验证的原型，然后你用最短时间跑完那一轮轮验证。工具压缩的是搭原型的成本，验证这一环它替不了你。

补充一层区别：原型回答「这样好不好玩」，产品回答「这样能不能长期留住人」。后者要靠留存数据、内容量、平衡性和长期运营，完全不是同一量级。

七、三种原型该从哪一种开始

没有游戏开发经验 → 先做横版或俯视角 2D。 二维坐标更容易理解，能更快学会场景、输入、碰撞和信号这四个基础概念，而这四个在三维里一样要用。

已有 2D 基础，或创意必须依赖空间、镜头和立体关卡 → 再进入 3D。 不要因为 3D 看起来「更像大作」就从复杂角色模型开始。

三句话判断法：

  • 玩法靠跳跃路线、左右推进和平台节奏 → 先做横版；
  • 玩法靠地图探索、资源循环，且要保持像素风 → 先做低分辨率像素原型；
  • 玩法离不开空间深度、镜头和立体路线 → 先做 3D 灰盒。

提示4 · 拿不准时，写一句话检验

把创意用一句话写下来，看里面有没有必须靠三维才能成立的动作。如果没有，就先用二维做。二维做不出来的创意比你想象的少得多——横版、俯视角、卡牌、解谜在二维里都能完整表达。

八、导出前还要做什么

在编辑器里运行通过 ≠ 可以发布。

  1. 在 Editor > Manage Export Templates 安装与当前 Godot 版本完全匹配的导出模板；
  2. 从 Project > Export 添加目标平台预设；
  3. 按平台分别验证。
平台必须做的事
桌面在没有 Godot 编辑器的干净电脑上验证启动、输入、存档和全屏切换
Web通过本地服务器或 HTTPS 访问，不能只双击 HTML
Android / iOS配置各自 SDK、签名、权限和真机测试
Steam / itch.io / 商店上传流程需单独完成

给 AI 的指令仍然保持一次一件事：

请为当前系统配置 Godot 导出预设，不要修改游戏玩法。

导出失败时：

导出失败，错误是【粘贴错误】。请只检查模板和预设。

提示5 · 导出要趁早，不要留到最后一周

整条导出链路涉及模板、SDK、签名和商店后台，任何一环卡住都可能需要好几天，而且问题往往不在你的代码里。建议原型刚能跑时就先完整导出一次，把这条路走通，之后迭代内容就没有后顾之忧。

九、诚实地说明验证边界

原教程实际验证的范围是：在 macOS 上跑通 Godot 4.7.1 编辑器、三个项目的场景加载和调试运行，并取得横版、像素与 3D 的真实运行画面。横版输入与平台碰撞、像素整数缩放与收集计数、3D 移动与灯光阴影均已接入临时验证项目。

但 Windows、Linux、Web、Android、iOS 或主机导出，教程并没有声称「已经通过」。它们需要对应的导出模板、SDK、签名和设备，有目标平台时要在那套环境里实测。

看任何教程都要分清它的验证边界。没验证的部分当待办事项，而不是当已解决的前提。

很多教程里的「翻车」，本质上不是你操作错了，而是那条路作者根本没走过。

十、最后一步：选一个原型继续打磨

三个项目分别练习了不同能力：

  • 横版原型 → 检查移动、跳跃和路线；
  • 像素原型 → 检查分辨率、地图和收集循环；
  • 3D 原型 → 检查空间、镜头、灯光和目标引导。

不要同时扩展三个项目，先选最接近自己想法的一个。

然后请一位没有参与开发的人试玩五分钟，硬性要求是：试玩开始后不要解释操作。一旦开口，你得到的就不是真实反馈，而是对方在你暗示下勉强理解的结果。

只记录三件事：

  1. 他第一次停下来或走错的位置；
  2. 他失败以后是否知道原因；
  3. 他是否愿意马上再玩一次。

第三项是最诚实的指标——愿意再玩一次，说明核心循环真的成立。

改的时候一次只改一项：

试玩者在【位置】不知道该往哪里走。请只加强路线提示，不要增加新关卡。

修改后让同一个人重试。

判断标准：路线和目标已经看得懂 → 再增加下一关、正式美术和声音；仍然需要口头解释 → 继续调整移动、镜头、碰撞和目标提示，不要急着加内容。

完成这一轮试玩与修改，原型才真正进入游戏开发，而不只是编辑器里的演示场景。

十一、审查清单

  • 灰盒里玩家没有埋进地面
  • 摄像机里能同时看到角色和目标门
  • 碰撞体大小与可见模型接近
  • 环境光与方向光已加，方向光已开阴影
  • 目标门发青色光，玩家一开始就能看到
  • 已按七层顺序推进，没有跳去做美术
  • 关卡尺度、移动速度和碰撞手感已锁定
  • 玩家、目标门、互动道具已拆成独立场景
  • 已用 Profiler 而非肉眼检查性能
  • 导出模板版本与编辑器版本完全匹配
  • 桌面版在干净电脑上验证过
  • Web 版通过服务器或 HTTPS 访问过（非双击）
  • 已选出一个原型集中打磨，没有三条线并行
  • 已完成至少一轮真人五分钟试玩，且未解释操作
  • 已记录「停下的位置 / 是否知道原因 / 是否愿意再玩」
  • 每轮修改只改一项

十三、一页纸总结

  • 核心标准：可玩的灰盒 > 不能移动的精美场景。
  • 灰盒三查：不埋地面、摄像机看得到、碰撞体接近模型。
  • 反馈优先：环境光+方向光+阴影+发光目标门，正式模型进场前跑通。
  • 七层顺序：尺度 → 拆场景 → 占位模型 → 材质规则 → 动画与状态机 → 完成反馈 → 性能实测。
  • 不可逆先定：关卡尺度与手感先锁，材质特效可后放。
  • 路线选择：按玩法依赖判断，无经验先做 2D。
  • 导出要早：模板版本必须匹配，各平台分别验证。
  • 验证闭环：真人试玩五分钟不解释，记录三件事，一次只改一项。
