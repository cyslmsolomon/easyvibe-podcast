一、这一集在解决什么问题

前面两集解决的是「项目放哪」：静态站、常驻服务、偶发任务各自该落在什么平台；数据库、缓存、加速又该自建还是上云。这一集往里再走一层，解决两件事。

第一件是数据形态。 关系型数据库把信息拆成多张表再用外键连起来，非关系型数据库把相关信息打包成一个文档。这两种设计思路正好相反，各自适合的场景也不同。搞不清这一点，后面选数据库就只能靠猜。

第二件是平台能力边界。 很多人听说某个后端平台很强，却说不清它到底提供哪几块能力。这一集沿着控制台侧边栏，把表编辑器、语句执行器、数据库管理中心、身份认证、存储、边缘函数、实时引擎、项目设置逐项走一遍，让你脑子里有一张完整的地图。

贯穿全片的暗线是安全与权限：数据放在哪是一回事，谁能看到是另一回事。

三、能力地图

完成本集学习与实践后，你应该能够：

  1. 说清两种设计思路的差异：关系型追求不重复，文档型追求一次取完。
  2. 判断读写比例：读多写少的场景敢于接受冗余；写多读少则要谨慎。
  3. 认出常见数据库产品：看到名字能分出它属于 SQL 还是 NoSQL 阵营。
  4. 独立完成项目创建：填好名称与密码，选对区域，等状态变为可用再操作。
  5. 理解模式的双重作用：避免命名冲突 + 实现权限隔离。
  6. 区分两个默认容器：公共容器放业务表，认证容器不要手动改。
  7. 用语句执行器建表：让大模型生成语句，运行后在表编辑器中验证。
  8. 看懂表间连线：理解外键约束所表达的数据引用关系。
  9. 配置登录方式：开关邮箱确认、设置限流、按需接入第三方认证。
  10. 把文件交给存储服务：区分公开/私有权限与永久/临时链接。
  11. 用边缘函数当安全中间层：密钥只留在服务端，通过环境变量读取。
  12. 选对实时能力：变更订阅 / 广播 / 在线状态三类各司其职。
  13. 守住密钥分界线：前端只能用受行级安全限制的那一把。

四、逐段要点

开场 · 从一张表到一份文档

本集分两段：先用一小段对比两种数据库设计思路，再进入平台控制台逐项巡礼。贯穿主题是安全与权限。建议边听边打开控制台对照。

二 · 非关系数据库

思路与关系型相反：不强调拆分与规范，而是把业务上互相关联的数据打包聚合，以减少查询时的连接操作。

文档数据库（MongoDB 为代表）以「文档」为基本单元，文档指类似通用数据格式的结构而非文章；无需预定义统一结构，字段可灵活增减。

博客示例：关系型把一篇文章的信息分散在五张表；文档型把文章、作者、评论、标签放进同一个文档。查询只需按编号读一次，无需三四次表连接。

取舍：作者用户名被嵌入每篇文章，改名需遍历所有相关文档，存在更新失败与不一致风险。判断标准是读写比例：博客、资讯、商品详情这类读多写少场景，冗余可接受；频繁修改用户信息的写多读少场景需权衡。

一句话总结：关系型追求不重复，文档型追求一次取完。

三 · 两类数据库速查

SQL 阵营：MySQL、PostgreSQL、YugabyteDB、CockroachDB、Oracle Database、Azure SQL Database。

NoSQL 阵营：Redis、CouchDB、MongoDB、Cassandra、Elasticsearch、BigTable、HBase。

用法：看到陌生名字回来查一眼即可判断脾气；初级阶段不必在选型上纠结过久，产品都很成熟，需要认真选时可直接咨询云厂商。

四 · 建项目

流程：官网登录 → 新建项目 → 填项目名称与数据库密码 → 选择离目标用户最近的区域。

两个提醒：数据库密码只在创建时出现一次，务必当场保存；项目初始化需要时间，等状态变为可用再操作，否则会遇到莫名的报错。

创建成功后，左侧侧边栏列出全部核心模块，本集即沿此顺序推进。

五 · 表编辑器与语句执行器

表编辑器 = 可视化数据表编辑器，像操作电子表格一样增删改查，无需写语句。

模式（Schema） 是数据库内的资源容器，作用有二：避免命名冲突（不同容器可有同名表）、实现权限隔离。日常只关注两个容器：

  • public：默认公共资源区，业务表放在这里。
  • auth：认证专属，其中的用户表自动存储注册用户信息，不建议手动修改。

可把模式理解成文件夹：同名文件放不同文件夹互不干扰，还能分别设权限。

语句执行器 = 用代码直接操作数据库。可让大模型生成语句，运行后到表编辑器的公共容器验证；执行过的语句保存在私有栏，可收藏复用。

六 · 数据库管理中心与身份认证

数据库管理中心：可视化查看与管理所有表，并通过表间连线理解关联关系（外键约束）。

身份认证：管理注册、登录与权限，提供开箱即用的注册、登录、密码重置、邮箱验证，支持微信 / GitHub / Google 等第三方登录，所有用户数据自动同步到 auth.users。

两个常用开关：关闭「确认邮箱」可免去注册后的邮件确认；「流量限制」可应对短期注册高峰。也可接入第三方认证服务（如专用认证工具）。

隐藏价值：认证体系与业务库打通，业务表可直接引用认证用户表的用户编号，无需自建用户数据。

节奏建议：只需邮箱登录时不必急着接第三方，先跑通主流程。

七 · 存储与边缘函数

存储：存放任意类型文件（图片 / 视频 / 文档 / 音频），提供公开或私有权限、永久或临时链接，并与认证系统无缝集成实现精细化访问控制。思路与对象存储一致——用户文件不要放应用服务器。

S3 兼容的意义：该协议已存在近二十年，生态成熟，兼容即可直接复用现成工具、SDK 与文档，加速上线。

边缘函数：全球分布式服务端函数，无需自建服务器即可编写并部署后端代码，自动在离用户最近的边缘节点运行。

核心价值是安全中间层：前端直接调用第三方服务会暴露接口密钥；改为前端只与自己的函数通信，密钥通过环境变量在服务端读取，永不进入浏览器。

八 · 边缘函数的典型场景

与认证系统集成：已登录用户调用函数时身份信息一并传入，函数内可识别用户做权限控制；函数操作数据库时自动遵循行级安全策略。

典型用途：监听第三方回调（支付成功、代码提交）并触发数据处理；发送邮件通知；生成报告；封装复杂业务逻辑为自定义接口；任意服务端计算任务。

案例：认证工具只管登录注册，不碰业务库；通过回调触发边缘函数，把认证状态同步进业务库，两端实时对齐，无需独立后端。

成本认知：按请求触发，无调用时不占资源，无需单独维护机器，是小团队成本最低的后端形态。

九 · 实时引擎与项目设置

实时引擎让应用即时接收数据库变化，无需轮询；数据发生增 / 改 / 删时通过长连接推送给已连接客户端。三大能力：

  1. 变更订阅：监听表变化，可精确到表、事件、筛选条件，并与行级安全策略集成。
  2. 广播：客户端间通过频道发送低延迟临时消息，适合聊天室、实时光标、游戏状态同步。
  3. 在线状态：追踪谁在线、当前多少人在看，适合协作类应用。

项目设置入门只需盯两项：

  • 数据接口：形如项目地址的接口端点，是所有增删改查的入口，前端/服务端用它初始化客户端。
  • 密钥：公开匿名密钥受行级安全严格限制，供前端使用；服务端高权限密钥可绕过行级安全，禁止公开，泄露须立即更换。

判断标准：暴露在浏览器里的必须是受限制的那把；能绕过行级安全的只能待在服务端。

五、审查清单

  • 已根据读写比例判断该用关系型还是文档型数据库
  • 文档型场景已确认冗余可接受的边界（哪些字段会被重复存储）
  • 项目创建时已保存数据库密码，且区域选择贴近目标用户
  • 项目状态变为可用后才开始建表操作
  • 业务表建在公共容器，未改动认证容器下的默认表
  • 已理解模式的两重作用，并按资源类型做了分组
  • 建表语句来自可复查的来源，运行后已在表编辑器中验证
  • 表间关联通过外键约束表达，关系视图可正常查看
  • 登录方式按需开启，未一次性接入过多第三方
  • 邮箱确认与限流策略已按业务需要配置
  • 用户上传文件走存储服务，未写入应用服务器
  • 第三方服务的密钥通过边缘函数的环境变量读取，未出现在前端代码
  • 已为需要实时性的功能选定正确的实时能力
  • 服务端高权限密钥未出现在任何前端配置或仓库记录中

六、实践提示

提示一 · 用读写比例给数据库选型定调

别问「哪个数据库更好」，先问「这个数据被读得多还是被改得多」。读远多于写，接受冗余换取一次读全；写远多于读，就要认真评估聚合存储带来的更新成本。这一个变量能帮你砍掉大半的纠结。

提示二 · 把模式当成文件夹来用

模式听起来抽象，但当文件夹理解就通了：同名表放在不同容器里互不打扰，还能分别设置谁能访问。项目早期就养成按资源类型分组的习惯，等项目变大、要给别人开账号时，会省下大量返工。

提示三 · 前端永远只拿受限的那一把钥匙

判断标准只有一句：会暴露在浏览器里的密钥，必须是被行级安全策略限制过的；能绕过行级安全的，只能待在服务端。把这条写成团队规范，比任何事后审计都有效。

提示四 · 调第三方服务前先问一句：密钥会去哪

任何需要在前端调用第三方服务的场景，都先问「密钥会去哪」。如果答案是「会进浏览器」，那就该加一层边缘函数。这层中间件的成本极低，却能挡住一整类安全事故。

提示五 · 先把主流程跑通，再叠加登录方式

认证是容易过度设计的模块。只需要邮箱登录的时候，就别急着接第三方。每多一种登录方式，就多一份要维护的配置和一条可能出错的路径。等真实用户提出需求了再扩展，节奏会舒服很多。

九、常见误区与纠正

误区一：把「非关系」理解成「没有结构」。

非关系数据库不是没有结构，而是结构不必预先统一定义。每个文档仍可以有清晰的字段，只是允许不同文档字段不同。把这点搞清楚，才不会在项目后期误以为可以随意乱塞数据。

误区二：看到冗余就否定文档数据库。

冗余是设计取舍的结果，不是缺陷。读多写少的场景里，用少量重复换取一次读取拿全，往往是更优解。真正该问的是「这个字段多久改一次」，而不是「它重复了几遍」。

误区三：手动去改认证容器里的表。

认证容器下的用户表由系统自动维护，手动修改很容易破坏认证流程。需要扩展用户信息时，正确做法是在公共容器里建一张业务侧的扩展表，用用户编号关联。

误区四：把第三方服务的密钥写进前端。

这是最经典也最致命的一类事故。任何会进入浏览器的凭证，都必须假定它迟早会被看到。加一层服务端函数做中转，成本远低于事后处置。

误区五：用轮询实现实时。

反复请求接口不仅浪费资源，还会带来延迟。实时引擎已经提供了变更订阅、广播、在线状态三类能力，选对能力比多写几行代码有效得多。

误区六：一开始就接入所有登录方式。

每一种第三方登录都是一份需要长期维护的配置和一个潜在的故障点。先跑通主流程，等需求明确再扩展，节奏会舒服得多。

十、一页纸速览

  1. 关系型追求不重复，文档型追求一次取完，选型先看读写比例。
  2. 模式当文件夹用，业务表放公共容器，认证容器不要手动改。
  3. 不会写语句就让模型生成，运行后回表编辑器验证。
  4. 表间连线就是外键约束，它表达的是数据归属。
  5. 认证体系与业务库打通，业务表引用用户编号即可。
  6. 用户文件走存储服务，不进应用服务器。
  7. 第三方密钥只留在服务端，用边缘函数做中间层。
  8. 实时需求先分三类，别一上来就轮询。
  9. 前端只能用受限的那把密钥，高权限密钥一步都不许往外走。
