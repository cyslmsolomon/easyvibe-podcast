一、这一集在解决什么问题

很多人用 AI 做东西时，以为瓶颈在模型不够聪明、工具不够好用。真实的卡点往往更早——你给的那句话太模糊了，模糊到 AI 只能靠猜。猜对了是运气，猜错了要返工，而且返工时你说不清它错在哪，因为你自己也没想清楚。

原文在这一章专门用一大节讲这件事（「用 AI 写需求文档：学会具体化需求」），并给出了一份完整的 PRD 范例——一个叫「Today's Plan」的每日计划应用。

音频稿按「立规矩 → 为什么具体化 → 扩写两步法 → 范本拆解（定位/画像/故事/功能）→ 收尾」重排。一句话概括：这一集不改变你的工具和模型，只改变你交给它的东西——而这一点改变，杠杆率往往比换个更强的模型更高。

三、先立两条规矩（禁止事项）

原文在本章末尾的「禁止事项」小节，核心两条：

  1. 不要使用 any 类型——等于告诉编译器此处不检查，短期省事，长期撤掉了类型系统的保护，问题推迟到运行时才爆。
  2. 不要删除测试文件——测试不是可清理的冗余代码，是项目还能否安全改动的前提。

为什么必须显式写下来：AI 追求的是完成任务，它并不天然知道哪些是你的底线。你不说，它可能判断测试文件「当前没被引用」而在重构时顺手删掉。

演播者补充：

  • 哪些内容该写进约定——回想你最常说、但从没写下来的话：这个目录是历史遗留别动、这个字段看起来没用但下游依赖它、这个文件生成一次就不要重生成。这些话你说过很多遍，AI 一次都没听过。
  • 禁止事项不宜太多——原文只列两条是有道理的。列二十条的结果是没人看，AI 也不会真逐条遵守。挑最不可让步的三到五条，其余靠代码评审与测试兜底。

四、为什么抽象需求必须具体化

原文的比喻：「我很饿」是抽象需求；可以被执行的是「我肚子有点饿，可能需要吃一个红豆面包，再配一杯豆浆」。

为什么自己写不具体：把抽象变具体很花精力。没见过足够多案例，就不知道该从哪些维度拆——先做提醒还是先做统计？日历视图还是时间轴？要不要历史回顾和模板？

为什么 AI 擅长这件事：它见过成千上万份产品文档，知道这类应用通常长什么样、有哪些模块。

关键的认知转变（演播者补充）：在需求环节，AI 更合适的角色是提问者而不是执行者。它不替你做决定，而是把你可能没想到的维度摆在你面前。你做决定的速度，取决于它能不能把选项列全。

五、扩写两步法

第一步——说出最朴素的想法：

Please help me write a daily planning app where I can write my plans each day and get reminders.

第二步——不要让它直接开工，而是让它先扩写：

Based on my needs, please elaborate and provide a more detailed Product Requirement Document for reference. My idea is: …

关键词是「供我参考」：你不是让它定稿，是让它给你素材让你挑。主动权留在你手里。

这份文档真正的作用：把你脑子里模糊的部分逼出来。看到「目标用户」才意识到要给谁用；看到「提醒设置」才意识到还有「提前多久提醒」这个问题。

三个提升扩写质量的技巧（演播者补充）：

  1. 把已确定的约束写进去——只用前端不接后端、必须能在手机上使用等，约束越明确越贴合；
  2. 要多个版本而不是一个——请给出两个不同侧重点的版本（偏轻量 / 偏完整），有对比才容易选择；
  3. 让它标注假设——直接问「这份文档里有哪些是你推测的、需要我确认的」，能快速定位你还没想清楚的地方。
⚠️ 不要做：扩写阶段不要让 AI 开始写代码。需求没定之前写出来的代码几乎必然重写。

六、范本拆解（一）：产品定位与目标用户

产品介绍段：写明产品名、版本、创建日期、作者。这几项看似形式，实则有实际作用——版本号说明是哪一版，日期说明时效，作者让后续的人知道找谁。

产品愿景（范例大意）：一个极简高效的每日计划与提醒工具，帮助用户克服拖延与遗忘，清晰规划每一天，并通过智能提醒确保任务落地，最终让用户对时间获得更强的掌控感与成就感。

写法要点：愿景不是功能列表，是价值主张。它回答「用户为什么要用它」，而不是「它有什么」。这个区别决定后面所有功能能否对齐。

三类目标用户画像（每类都写四件事：特征 / 痛点 / 需求 / 具名人物）

画像特征痛点需求
学生（小明）课程、作业、社团、备考多任务并行易忘小事与截止日期；任务切换时手忙脚乱简单工具列出每日待办，并在课前/自习前提醒
上班族（张伟）会议、报告、项目节点与个人事务交织易忘重要会议；被紧急任务打断后忘记原计划；忙但没效率快速记录排期，并在关键时间点强提醒（如会前 15 分钟）
自由职业者（李娜）时间自由，但对自我管理要求高易拖延、缺外部监督；一天开始没计划导致利用率低建立固定晨间流程，并对当天成果复盘以获得正反馈

共同点：痛点一定是具体场景，不是「效率低」这种抽象词。写得越具体，后面做功能决策时越有依据。

七、范本拆解（二）：用户故事

范例用了标准句式：「作为一个用户，我希望做到 X，以便获得 Y。」 它强制你同时回答「要什么」和「为什么要」。

范例中列出的八条（原文为英文，此处意译）：

  1. 快速创建今日计划列表 → 对当天所有任务有总览
  2. 为每个任务设置起止时间 → 形成可视化时间线
  3. 任务开始前收到推送提醒 → 不错过重要安排
  4. 自定义提醒时间（提前 5/15/60 分钟）→ 更贴合个人习惯
  5. 轻松标记完成 → 获得成就感并看到进度
  6. 每天结束看到已完成总结 → 复盘与自我激励
  7. 方便地编辑与删除任务 → 应对临时变化
  8. 查看往日计划与完成情况 → 回顾效率与习惯

价值：用户故事直接决定功能清单的边界。任何一个不在这些故事里的功能，都应推迟到后续版本——它是砍需求的依据。

技巧：多用「以便」。它逼你把动机写出来，动机一出来，就能分辨哪些是真需求、哪些只是「觉得酷」。

八、范本拆解（三）：MVP 功能拆解

分层原则：核心功能（MVP）必须现在有；后续功能（V1.1 / V2.0）可以下一版再做。没有这个区分，第一个版本永远做不完。

模块一：计划管理

3.1.1 每日计划首页

  • 界面：以「今天」为核心视图，顶部显示当前日期
  • 视图：时间线列表，清晰展示从早到晚的任务；无时间的任务放在顶部或底部「待办」区
  • 交互：右下角「+」快速新建；下拉刷新；左右滑动查看昨天/明天

3.1.2 创建/编辑任务

  • 入口：首页「+」或点击列表中的时间段
  • 字段：任务标题（必填）、任务时间（可选，含「全天」选项）、提醒设置（必填，有默认值）、备注（可选）
  • 操作：保存 / 取消 / 删除

3.1.3 任务交互

  • 标记完成：复选框 → 删除线 + 灰底，可取消
  • 编辑：点击任务进入编辑页
  • 删除：左滑显示删除按钮

模块二：智能提醒系统

3.2.1 触发机制：基于任务开始时间与用户设置的提前量发送推送。必须支持离线触发（本地调度）。

3.2.2 提醒内容：标题为应用名；正文「提醒：[任务名] 将于 [开始时间] 开始」；声音用系统默认或提供几种简单有效的提示音。

3.2.3 提醒设置（两层）

  • 全局（设置页）：默认提前量，新任务默认继承
  • 单任务（创建/编辑页）：可覆盖全局，选「准时 / 提前 5 分钟 / 30 分钟 / 1 小时」或「不提醒」
设计细节：提醒设置被标为「必填」但有默认值——必填保证功能成立，默认值不增加操作负担。

后续功能（V1.1 / V2.0）

功能说明
每日回顾与统计每晚固定时间推送总结；日报展示计划总数、完成数、完成率 + 鼓励语
历史回顾日历视图点击任意过去一天；完成率高的日子特殊颜色标记
模板把成功的一天存为模板；创建明日计划时一键导入再微调

把这四项放到后续版本，是这份文档最清醒的地方——它们都很吸引人，但没有一项影响核心闭环。先让「写计划 → 被提醒 → 标记完成」跑通，再谈锦上添花。

九、约束说明

本集的约束与适用边界：

  1. 顺序约束：需求未定前不要开始写代码，否则几乎必然重写。
  2. 范围约束：MVP 与后续功能必须分层；不分层会导致第一个版本永远做不完。
  3. 约定约束：禁止事项应写入记忆文件且不宜过多（3–5 条），其余靠评审与测试兜底。
  4. 格式约束：PRD 无强制格式，但应至少覆盖定位、画像、故事、功能四段；缺任一段都会导致后续返工。
  5. 时效约束：范例 PRD 的日期与功能描述是 2023 年的示例，仅作结构参考，不代表当前最佳实践。
  6. 内容约束：本文为开源教程的二次演绎配音版，观点与例子由演播者添加，不代表原文作者立场。

十、审查清单

  • 已用一句朴素的话描述了想法，未混入实现细节
  • 已要求 AI 扩写成 PRD，并明确标注「供我参考」
  • 已把已确定的约束（平台、端、技术栈限制）写进扩写指令
  • 已让 AI 标注哪些部分是它的假设，并逐条确认
  • 产品愿景回答的是「为什么要用」，不是「有什么功能」
  • 用户画像的痛点是具体场景，不是抽象形容词
  • 每条用户故事都带「以便…」，动机明确
  • 功能清单已分核心与后续两层
  • 核心功能能跑通一条完整闭环
  • 禁止事项已写入记忆文件，且不超过五条

十一、实践提示

提示1 · 用「我很饿」检验你的需求描述

写下你的需求，然后问自己：这句话能不能直接开干？如果答案是「还得再想想」，就说明它还是抽象的。把它改写成「想吃红豆面包配豆浆」那种粒度再交给 AI。

提示2 · 把「供我参考」写进每一次扩写请求

这四个字把 AI 从「决策者」降级为「素材提供者」。你会更敢删改它的输出，而敢删改，正是需求收敛的开始。

提示3 · 用「以便」批量暴露伪需求

把你的功能清单逐条改写成「作为…我希望…以便…」。凡是「以便」后面写不出来的，多半是你觉得酷、但用户并不需要的功能，优先砍掉。

提示4 · 给 MVP 画一条闭环线

在功能清单上画一条最小的闭环：用户从进入到获得价值的完整路径。只保留这条路径上的功能作为核心，其余全部移到后续版本。这条线画出来，版本规划就不纠结了。

提示5 · 先划掉不同意的段落，再动手

拿到 AI 生成的 PRD 后，不要急着开工。先把你不同意的段落划掉，并在旁边写一句为什么不同意。这个过程会逼你把偏好说出来——而说出来的偏好，才是真正属于你的产品判断。
