这一集在讲什么

上一集搭完了那条餐饮意图分类流水线，这一集做四件事：

  1. 运行测试：用四组真实输入验证分流是否生效，并交代一个隐蔽的内置缺陷。
  2. 2.7 复用模板：导入官方 DeepResearch 工作流，用「先跑再排错」的方式跑通。

  4. 3.1 – 3.2 十个案例：社媒方向五个、职场方向五个，可直接抄作业。

一条主线：从「能跑通一条工作流」到「能把它变成别人可用的服务」。

逐段精讲

1. 四组测试：分流到底生效了吗

源文档给出了四组输入与对应的路径、输出：

输入路径输出要点
点餐：来一份香辣鸡腿堡套餐，大杯可乐buy_food → LLM_BuyFood记录订单，并主动追问薯条是否更换
抱怨：你们也太慢了吧，等一个多小时complain → LLM_Complain先道歉，再说明正在核实，并申请补偿
闲聊：今天吃什么比较健康chitchat → LLM_Complain给出轻食推荐，并追问口味偏好
无关：帮我想个明天开会的笑话other → LLM_Other礼貌说明能力范围，引导回点餐场景

重点看两个细节：

  • 点餐分支主动补全了缺失信息（追问薯条），这正是下单助手人格设计的目标。
  • 闲聊分支给出的输出来自 LLM_Complain（源文档原文如此），这提示我们：分类正确不等于路由一定正确，条件分支的连线要逐一核对。

2. 那个隐藏的内置缺陷

源文档用引用块专门标注了一个坑：

若遇到与 aggregation group 相关的奇怪问题，大概率是 Dify 的内置 bug。若曾开启又关闭过 AGGREGATION GROUP，系统可能生成过 group 配置并残留异常参数；即便开关现已关闭，残留配置仍可能导致问题（如 any 相关参数报错）。解决方式：删除该节点并重新创建。

调试的两种通用方法：

  1. 把每个环节的 output 记录为变量，在最终输出时打印所有中间变量。
  2. 查看 Process 运行过程，点击可查看每个环节的细节。

3. 复用模板：DeepResearch

源文档的策略非常实在：导入后第一步直接运行，根据每一步的报错解决问题。

典型排错链路：

  • 点右上角 Preview 运行，直到报错出现
  • 打开报错节点，发现未配置 Tavily 的 API Token
  • Tavily 搜索 API 是专为 AI 设计的搜索引擎，提供实时、准确、事实性的结果
  • 配置后搜索引擎正常工作，继续修正模型调用问题
  • 最终得到结合大模型理解的详细搜索结果，并在末尾看到参考文档地址

「答案可溯源」是深度研究类工作流最有价值的部分。

4. 把 Dify 变成后端

核心思路与「通过 API 调用模型」一致：准备 Key + Request 示例 + Response 示例，交给大模型生成调用代码并解析字段。

获取步骤：

  1. 点击右上角 Publish → Publish Update → Access API Reference
  2. 找到 Send Chat Message，复制右侧的 Request 与 Response 示例
  3. 在文档右上角点击 Create new Secret key 生成 API Key

三样原料的分工：Key 证明你是谁，Request 示例告诉模型该怎么发，Response 示例告诉模型能拿回什么。 缺任何一样，模型就只能靠猜。

5. Trae 与它的两种模式

源文档对 Trae 的介绍要点：

  • 右侧区域是 Copilot / Agent 交互窗口，看不到时点右上角侧边栏图标打开
  • Builder 即 Agent 模式，可操作本地环境、安装依赖、打开网页
  • Builder 下分两种：Chat 模式（与当前文件夹交互 / 自然语言对话）与 Builder with MCP（为 Agent 提供更多外部工具）
  • MCP 可理解为「让大模型更方便调用各种外部工具的能力集合」
  • 模型下拉列表可选 Kimi、GLM；国际版另有其他选项。源文档观点：Kimi、Qwen、GLM 的综合能力已基本接近 Claude 3.5 / 3.7，日常开发完全够用

6. 生成前端，以及为什么必须多轮测试

把 Key + 两个示例交给 Trae Builder，注意把接口地址占位符替换为实际地址。

源文档对失败的预案很务实：

  • 切换另一个大语言模型再试
  • 把错误信息完整复制，详细描述问题，让模型继续迭代
  • 提供更多上下文：除了错误信息，还可以复制更完整的文档内容一并交给模型

两个易忽略的提醒：

  1. 浏览器嵌在 Trae 内部，可点顶部指南针图标在外部浏览器全屏打开。
  2. 大模型具有随机性，单轮顺利不代表多轮稳定，务必做多轮对话测试。

审查清单

  • 四组典型输入是否都跑过了？分类结果与路由分支是否逐一核对？
  • 条件分支的连线是否检查过，有没有「分类对了但走错分支」的情况？
  • 是否用至少五组不同类型的输入验证过分类器稳定性？
  • 遇到聚合分组类报错时，是否尝试过删除节点重建？
  • 是否用「打印中间变量」或「查看运行过程」定位过至少一个 bug？
  • 导入他人模板时，是否先直接跑一遍再按报错逐项修复？
  • Tavily 等外部工具的密钥是否已配置？
  • 发布应用后，API Key 是否已创建并妥善保存（不外泄）？
  • Request 与 Response 示例是否都复制给了代码助手？
  • 接口地址占位符是否已替换为实际地址？
  • 生成的前端是否做过多轮对话测试，而不只是单轮？
  • 报错时是否尝试过换模型 / 提供更多上下文？

实践提示

提示一 · 先跑再改，别先读再跑

导入他人工作流时，最省时间的顺序是：直接运行 → 看报错 → 定点修。源文档明确说「刚进入感觉十分复杂，没关系，点击 Preview 运行直到报错出现」。报错是最好的路线图，它直接告诉你下一步该看哪个节点。

提示二 · 把中间变量打印出来，调试效率翻倍

这是源文档给出的两个调试方法里更管用那个。把每个环节的输出存成变量，最后统一打印，数据在哪一步变形一眼可见。比起逐个节点点开看，这种「全链路透视」能省掉大量来回点击。

提示三 · 聚合分组报错就删节点重建

这是本集唯一一个明确标注为「内置缺陷」的问题。记住它的触发条件：曾经开启又关闭过分组聚合开关。遇到 any 相关参数报错时，不要去调参数，直接删除该节点重建，一步解决。

提示四 · 交给大模型前，先凑齐三样原料

Key、Request 示例、Response 示例。这三样缺一不可。很多人只丢一个 Key 就让模型写代码，结果模型只能凭印象编接口，生成的代码必然跑不通。提供给模型的上下文越完整，它给你的代码越接近可用。

提示五 · 单轮能跑不等于多轮能跑

源文档特别提醒：大模型本身具有随机性，有时单轮对话一切顺利，多轮对话却出现异常。验收标准应该是多轮对话稳定，而不是第一次看到页面有反应就收工。

提示六 · 十个案例挑一个做，不要全部读完

案例的价值在于结构，不在于数量。挑一个跟你手头工作最接近的，照着节点结构搭一遍，收获远大于把十个全部浏览一遍。动手搭一个，比读懂十个更有用。

常见疑问

问：为什么要先看四组测试，而不是直接讲新功能？

因为分流类工作流最危险的失败不是报错，而是「看起来正常但走错了分支」。源文档那组闲聊测试就暴露了这一点，分类标签是对的，路由却指向了另一个模型节点。只有逐组核对输入输出，才能发现这类静默错误。

问：模板导入后一片报错，是我太笨吗？

不是。源文档给出的预期就是「根据每一步报错的地方和原因解决具体问题」，缺 Tavily 密钥这类情况属于导入后的常规操作。报错是正常的起点，不是失败的标志。

问：十个案例要先从哪个开始？

从复杂度标注为「简单」的多语言邮件翻译回复开始。它主要依赖模型的序列调用，不涉及外部接口和文档解析，能让你完整体验一遍从起点到输出的手感，再往上挑战复杂案例会顺很多。

一句话收尾

先让它跑起来，再让它可被别人调用——从一条能跑通的工作流，到一个能被你的程序调用的服务，中间只差「发布、取 Key、把示例交给代码助手」这三步。
