三、非功能性需求（上）：性能与易用性

概念：非功能性需求回答的不是「做什么」，而是「做到什么程度」。功能需求说「要有提醒」，非功能性需求说「提醒必须准点到什么程度」。

4.1 性能（范例）

  • 响应时间：应用启动 < 2 秒；添加/编辑任务流畅无卡顿。
  • 资源占用：后台低电量、低内存；等待提醒的过程中不过度消耗资源。
为什么必须写：只写「要有提醒功能」，AI 完全可以用每分钟轮询一次的粗暴方案实现——功能照样成立，但电量一下午就没了。写了「后台低耗电」，它才会考虑系统级本地调度。约束不写，实现就会往最简单粗暴的方向滑。

4.2 易用性（范例）

  • 极简直观：UI 必须极简，主要功能在 3 次点击之内可达，新用户无需教程。
  • 容错性：提供撤销（如误删任务后有一段短暂的撤销窗口）。
价值：把「简洁」从形容词变成可验收的指标（3 次点击是可以测的）；「误删可撤销」保护的是用户最脆弱的那个瞬间。

四、非功能性需求（下）：可靠性与兼容性

4.3 可靠性（范例）

  • 提醒可靠：提醒功能是产品的生命线，须保证 99.99% 准时准确送达。
  • 数据不丢失：计划必须可靠地存本地；未来版本可支持云同步以防换机丢失。
要点一：措辞强度本身就是优先级信号。一个每日计划应用若提醒不准，其余功能全部失去意义——这条约束的优先级实际高于所有功能需求。
要点二：「未来版本可以支持云同步」是在给需求划边界。当前只做本地存储，云同步留后续。这种写法能防止范围蔓延。

4.4 兼容性（范例）

  • 平台：支持两大移动系统的最近 3–4 个版本。
  • 屏幕：布局适配各种手机屏幕尺寸。
兼容性看起来最没技术含量，却是上线后问题率最高的原因之一。宁可写得啰嗦，别指望对方脑补。

为什么这部分最容易被跳过（演播者补充）：功能需求你可以自己验证——按钮点了有没有反应，一看就知道。但性能、可靠性、兼容性在自己的开发环境里几乎永远是好的，它们只在别人的设备上、长时间运行后、极端情况下才暴露。很多项目「自己用挺好，一给别人就出问题」，根子就在这里。

五、路线图：三个版本怎么排

版本目标范围
V1.0（MVP）验证核心价值——计划与提醒完成全部核心功能（计划管理 + 智能提醒）
V1.1（快速优化）提升留存与成就感每日回顾与统计、历史回顾
V2.0（增强体验）提升效率与个性化模板、主题与个性化，并开始开发云同步

内在逻辑：这不是功能清单的流水账，而是一条价值递进曲线——先验证有没有人需要，再让用的人留下来，最后让留下来的人用得更舒服。

顺序反了会怎样：一上来就做模板和主题，而用户连第一次提醒都没收到过，那些锦上添花根本没人会用到。

V1.0 的目标用词是「验证核心价值」——这意味着 V1.0 可以粗糙、可以没有统计/历史/主题，只需把那条闭环跑通。允许第一版不完美，是能把它做完的前提。

实用排期法（演播者补充）：把想做的所有功能写下来，问一句「如果这一版只能保留三个，我留哪三个」。留下的三个就是 V1.0，其余往后排。做一次这个动作，你会发现大部分功能其实都可以晚一点。

六、把需求文档沉淀成一个文件

原文建议：如果觉得这类需求提示词太长，非常自然的做法是把它单独写进一个文档，作为你的需求文档 / 开发文档 / PRD。之后每次让 AI 写项目时，只需让它「参考这份文档」，而不是每次重打一遍长提示。你还可以在迭代中不断完善它，让后续项目直接受益。

这条建议的分量比看起来重得多（演播者补充）：

  • 工作方式从「每次重新描述」变成「累积一份资产」。第一次写可能花一小时，之后每次对话只需一句话。
  • 文档可以分叉：一份通用的开发规范（所有项目适用）+ 每项目专属的需求文档。让 AI 同时参考两份——一份管风格，一份管内容。这个结构一旦建立，产出稳定性会有肉眼可见的提升。
  • 文档是要改的：对不确定的模块，可以让 AI 提供更多备选方案，你再挑选合并成最终版本。它不是一次定稿的契约，而是会跟着你一起变好的东西。
原文总结：通过这种方式，我们可以很轻松地把抽象想法变成具体描述。对 AI 开发来说，「具体」就是生产力——需求越具体，越容易得到结构稳定、质量较高的项目。

七、日常用法一：管理文件夹

原文示例指令：

Please help me organize the contents of the current folder. I want to group files with the same content together & I want to group files from the same time period together.

价值：把「逐个看文件名 → 逐个判断 → 逐个拖拽」变成一句话；且按内容而非仅按名字分组，结果往往比手动分更合理。

安全建议（演播者补充）：先让它给出方案，你确认后再执行——加一句「请先告诉我你打算怎么分，不要直接移动」。这一步确认能挡住绝大多数误操作。

延伸用法：整理完让它顺手写一份说明，记录文件夹结构与每类文件的用途。下次回来只看这份说明就够了。

可照抄的其他场景：按月份归组去年的截图；找出内容重复的文件并列出可删清单；把文档标题统一成一种命名格式。共同特点是规则清楚但工作量巨大——人做要一下午，它做只要一条指令。

⚠️ 边界：涉及删除与覆盖的任务，务必先让它列出计划再执行，且重要资料提前备份。整理文件一旦做错，恢复比做的时候麻烦十倍。

八、日常用法二、三：从零开发与部署开源项目

从零开发新项目：与集成环境中的用法几乎完全一样。原文强调——最好提前准备好一份需求文档，需求文档越细致最终效果越好；可根据不断变化的想法对文档做多轮优化，文档越完善代码实现越稳定成熟。

关键词是多轮。不要指望一次性写到完美。第一版写个大概 → 跑一遍 → 发现不对回来改文档 → 再跑。这个循环本身就是需求具体化的过程。

部署开源项目（以 Dify 为例）：

I want to deploy this GitHub project https://github.com/langgenius/dify. Please help me clone the project and run it.

它会自动完成拉取代码、配置运行环境、启动项目等操作；中间某步出错时你再根据提示做少量人工处理。原文形容为——「你只需要一个对话框，再加上喝一杯咖啡的时间」。

两点补充（演播者补充）：

  1. 能外包的是操作，不是理解。你仍应大致知道它在做什么，否则出错时连该把哪段报错发给它都不知道。建议让它每一步都简单说明在干什么——既省时间，又不放弃理解。
  2. 为什么部署类任务特别适合它：这类工作反馈极其明确——命令成功与否、服务起没起来、端口通不通，全是硬结果。而它最擅长的正是这种「有明确反馈、可根据结果不断调整」的循环。所以部署、装环境、跑测试三类任务的成功率通常远高于写业务逻辑。

九、日常用法四：讲解代码与撰写文档

原文给了四个可直接照抄的提问模板：

  1. 请帮我解释这个项目：如何运行、如何使用、后续如何修改和继续开发？
  2. 请帮我说明这个项目的整体流程：程序是怎样运行的？用户在界面中可以做哪些操作？
  3. 请帮我为这个项目写一份完整的文档，包括开发文档和运行文档等。
  4. 请基于我当前文件夹里的所有内容，写一份详细说明，并保存到指定的文档中。

四个模板对应四种需求：怎么用 / 怎么跑 / 要产出物 / 结果落盘。第四个尤其推荐——它把一次性的解释变成了可以长期查阅的资料。

原文最后的定位升级：

不要只把它当作「写代码工具」，而是把它看作一个具有独立行动能力的智能 Agent。你可以让它帮你管理和整理本地文件、写日记写总结、分析和修复系统错误、执行各种重复性命令行任务。

十二、实践提示

提示1 · 用「三选一」法排出 V1.0

把想做的所有功能列出来，问自己：这一版只能留三个的话留哪三个。这个动作会立刻暴露哪些功能是「觉得酷」，哪些是「闭环必需」。

提示2 · 给每个非功能性指标配一个数字

把「要快」改成「启动 < 2 秒」，把「要简洁」改成「3 次点击可达」。不能写成数字的约束，等于没有约束——AI 无法验证，你也无法验收。

提示3 · 让工具整理文件前先要方案

在指令末尾加一句「请先告诉我你打算怎么分，不要直接移动」。多一轮对话，换来的可能是避免一次不可逆的误操作。

提示4 · 把「参考这份文档」设为你的默认开场白

建一份通用的开发规范文档，之后所有项目都以「请参考这份文档」开场。三次之后你会发现，产出的风格稳定性完全不同。

提示5 · 挑一个不敢碰的开源项目，让它跑一遍

找一个你一直想试但怕装不上的项目，把链接丢给它说「帮我跑起来」，然后去倒杯咖啡。无论成败你都有收获——成功多一个工具，失败拿到一份完整报错，那是下一轮对话最好的素材。
