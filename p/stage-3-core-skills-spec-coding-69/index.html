一、这一集在解决什么问题

规格驱动开发（Spec Coding）最常见的误解有两个：一是「又要写文档了，太麻烦」；二是「推倒重来，把氛围编程（Vibe Coding）全扔掉」。这一集把两个误解一次拆掉。

原文的核心论点只有一句：从 Vibe Coding 到 Spec Coding，真正改变的不是 Markdown 文件数量，而是意图如何进入开发流程。 音频稿围绕这句话展开四件事：

  1. 七种情况七种组合 —— 选型没有银弹，且只能有一个主流程；
  2. 需求变化纪律 —— 先改 Spec 再改代码的四步顺序；
  3. 轻量与完整 —— 按风险选力度，附一个「换人测试」判断法；
  4. 三十分钟练习 —— 今天就能做的四步入门。

三、逐节解读

3.1 七种组合与「主流程唯一」原则

原文的组合表覆盖七类处境，音频中逐个讲过。演绎方把七行压缩成三条记忆线：

  • 探索线：快速试验 = 氛围原型 + 3 到 5 条验收标准（轻到极简，但标准不能省）；
  • 落地线：中小功能 = OpenSpec + Given/When/Then + 自动化测试；新项目完整工件 = GitHub Spec Kit + Analyze + 人工确认；
  • 规模化线：Agent 连续开发 = Matt Pocock Skills + ADR + Code Review；大型产品 = BMAD + 轻量 Spec 分层。

比表格本身更重要的是紧随其后的一条原则：不要同时让多个工具各自维护 spec.md、tasks.md 和完成状态。 演绎方把原因说得更直白——多份规格 = 多份互相矛盾的真相，AI 这次读这份、下次读那份，行为飘忽不是它随机发挥，是它在矛盾文档之间迷路。正确姿势是选一个主流程，其他方法降级为零件库（EARS 写法、ADR、TDD、审查关卡随取随用）。

3.2 需求变化：四步顺序与「过时 Spec 更危险」

原文的通知中心案例给出了标准四步：

  1. 在 spec.md 中增加安全提醒的保留规则和验收标准；
  2. 检查 plan.md 和 tasks.md 是否需要新增任务；
  3. 修改代码和测试；
  4. 再次对照完整 Spec 验证旧行为没有被破坏。

演绎方补两点。其一，顺序本身就是纪律：先改规格再改代码，每次代码变动才有据可查；反过来先改代码、规格滞后，下次 AI 读着旧规格，可能把你新加的逻辑当 bug 改回去——真实项目里这类事故的根子都是顺序倒了。其二，原文那句「过时的 Spec 比没有文档更危险」值得放大：没有文档，AI 至少会问你；拿着错文档，它会坚定不移地做错。所以每次发现需求与实现不一致，都要明确判断一次：是实现偏离了规格（改代码），还是规格落后于真实需求（改规格），别搞反，更别两头都将就。

3.3 轻重取舍：按风险选力度

原文的五档表（一次性原型 / 小型局部功能 / 跨模块功能 / 支付权限隐私 / 多人或多 Agent）传达的规律是：力度跟风险走，不跟仪式感走。

演绎方在两个位置加了批注。第一，小型功能的「3 到 5 条验收标准」是全份规格的脊柱——有它，AI 自己知道写到什么程度算完；没它，一个改按钮颜色的小活它能重构半个项目。验收标准写没写，直接决定你是监工还是甩手掌柜。第二，支付、权限、隐私三场景的共同点不是「重要」，而是出错代价是事故不是返工，所以这三档要的不是文档齐全，是审查留痕：威胁场景想过、失败场景列过、审计要求写明、验证证据留下，且要指定谁来审——自己审自己，多半看成习惯性通过。

3.4 换人测试：规格好坏的可执行实验

原文给了一个极其漂亮的判断方法：如果换一个完全没看过当前聊天的人，只读仓库里的文档，能不能继续开发并判断完成？

答案肯定，规格到位；答案否定，关键意图还锁在聊天记录里。演绎方认为这个方法的价值在于它把「规格写得好不好」这个虚问题，变成了一个马上能做的实验，且不看字数只看一件事：离开你和当前聊天，项目还能不能被第三个人接走。场景化一点说——你出差一周，同事打开仓库就能上手，这就是通过；他每做一步都来问你，你就成了项目里不可替代的人肉接口。规格编程本质上是在把知识从人脑搬到仓库。

3.5 三十分钟练习：四步与两个实操经验

原文设计的练习选一个「一天内可实现」的小功能，走四步：澄清提示词让 AI 问不超过 8 个问题 → 生成一页 spec.md 并亲自删除所有未经确认的假设 → 把「好用、快速、安全」改成可观察或可测试的标准 → 开新会话只读 Spec 复述实现范围。

演绎方补两个实操经验：

  • 八问的边界：低于八个通常没问透，高于八个说明需求没想清或范围选大了，八是个有用的压强值；
  • 删假设的常见对象：AI 默认脑补技术栈、界面风格、数据量级，每删一条规格干净一分；「虚词改标准」的公式是虚词加数字——「快」不行，「两秒内响应」才行。

验收标准只有一条：新会话的复述与你的想法一致，规格才算开始发挥作用；还有偏差，别写代码，回去修规格。

四、审查清单

  • 能复述核心论点：变的不是文件数量，是意图如何进入开发流程
  • 已按自己的情况，从七种组合里选定一个主流程工具
  • 其他方法只作零件借用，没有多工具各自维护规格与任务文件
  • 遇到需求变化，走完四步：改 Spec → 查 plan/tasks → 改代码测试 → 对照验证
  • 每次发现需求与实现不一致，明确判断过「谁对听谁的」
  • 规格文件保持更新，没有留着已知过时的版本
  • 已按五档风险表为当前任务选定轻量或完整力度
  • 小型功能也写了 3 到 5 条验收标准
  • 高风险场景（支付/权限/隐私）有审查留痕与指定审查人
  • 用「换人测试」验证过一次规格质量
  • 完成了三十分钟练习，包括删假设与虚词改标准两步
  • 新会话复述与想法一致后才进入编码

五、实践提示

提示1 · 主流程只能有一个，其余降级为零件

多工具各写各的规格，必然出现多份矛盾的真相，AI 的行为飘忽八成源于此。选一个主流程焊死，EARS、ADR、TDD、审查关卡当零件随取随用。工具是拿来用的，不是拿来供的。

提示2 · 变更四步的顺序就是纪律

先改规格再改代码，每次变动才有据可查。顺序倒过来的典型事故是：代码改了、规格没改，下次 AI 拿着旧规格把你新加的逻辑当 bug 回滚。改之前先问自己，规格这一笔落了没有。

提示3 · 用换人测试验收规格，别看字数

「陌生人只读仓库文档能不能继续开发并判断完成」——这一个问题顶十份规格规范。它把虚的「写得好不好」变成可执行实验，且直指要害：规格是写给下一个人的，不是写给自己的。

提示4 · 验收标准是脊柱，宁可短不可无

小型功能的三到五条验收标准，是全份规格里性价比最高的部分。有了它，AI 知道什么算完，你知道怎么验收，双方都不用猜。虚词一律加数字，快就是两秒，安全就是未登录不可见。

提示5 · 方法升级一级级来，从下一条验收标准开始

不要推倒重来。从下一个功能开始，先写三到五条验收标准再动手，就这一步已经超过大多数用户。等这成了习惯，再往上加规格文件、计划文件。一步到位的方法，通常一步也到不了位。
