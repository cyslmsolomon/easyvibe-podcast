三、评测基准：三个核心特征

原文的切入点是一个扎心的观察：很多团队搭检索增强生成系统，只靠少量人工编写的测试问题就匆忙开始评估，上线后实际效果与测试表现差距显著。 根源在于缺乏有代表性、有系统性的评测数据。

一套能有效支撑系统迭代的评测基准，通常具备三个核心特征：

  1. 代表性——测试数据要全面覆盖真实业务中的各种场景，高频常见问题、复杂边界情况、异常输入都要测。只测好答的，分数一定虚高。
  2. 标准化——问题和答案的格式、难度系数、评分标准要统一规范，确保评测结果具有可比性和可重复性。
  3. 可演化性——基准应随系统能力提升和业务需求变化持续更新，避免固化的「应试」数据导致评测失真。

对大多数企业而言，由于业务场景存在独特性，最终往往需要构建自己的评测数据集。

提示一 · 把评测基准当成一个需要运营的系统，而不是一份文件

三个特征里最容易被忽视的是可演化性。基准一旦固化，团队就会不自觉地向题库优化，分数上涨但体验下降。运营动作至少要包括：定期补充线上答得不好的问题、按业务变化调整分层采样比例、每季度复审难度标注。

四、自建评测集三步与公开基准选择

第一步，从业务日志提取真实用户问题，依据类型、频率和难度进行分层采样，保证数据代表性。标注采用「机器生成加人工校准」：简单问题由领域专家直接标注，复杂问题先用高质量大模型生成候选答案，再由专家审核修改，显著降低标注成本。

第二步，建立标注质量体系：除答案本身，标注相关文档、答案类型、难度等级等元信息；建立标注规范，进行多人交叉验证，计算标注一致性（如 Kappa 系数）。

第三步，持续补充新用例：定期从线上反馈中补充新的测试用例，尤其是系统回答不好的问题，让评测数据与系统能力同步演进。

资源有限或想快速建基线时，可参考业界成熟的公开评测基准。选择时先明确评测目的（建能力基线，还是上线最终验证）；其次评估基准数据是否覆盖所关心的场景、问题类型和难度；最后权衡标注成本。时效性强的场景（新闻、金融）必须考察基准是否包含实时数据测试；历史知识处理，静态基准可能已足够。

结论：自建数据与公开基准结合使用，既贴近业务实际，又能借公共标准横向比对，是构建稳健评测体系的务实路径。

五、案例一 · 语义缓存

背景：教程级系统只适合单用户测试；生产环境面对几十到几千次重复查询（如客服场景反复询问「如何退款」），每次都要执行向量数据库检索和大模型调用，响应时间明显增加，成本快速上升。

双层检索架构：

  • 基础层：Chroma 向量数据库存储原始知识库（以 MedQuad 医疗问答数据集为例），每条数据加唯一 ID 方便精确引用；
  • 缓存层：基于 FAISS 构建，选择 FlatL2 索引处理小数据集和高维向量。

最关键的设计决策：语义缓存放在用户查询与 Chroma 之间，而不是缓存大模型的最终回答。因为直接缓存回答会导致用户的个性化要求失效（如「用简单语言解释」）。缓存查询则保留原始检索材料，回答可现场生成。

实现细节：SentenceTransformer 的 all-mpnet-base-v2 模型生成查询向量，欧氏距离阈值 0.35 判断相似；缓存满时先进先出；缓存数据保存到 JSON 文件支持跨会话。

实测数据：首次查询从 Chroma 获取耗时 0.057 秒，相似查询从缓存获取仅需 0.016 秒；大规模生产环境可实现 90%–95% 的性能优化。

提示二 · 上线前先统计高频问题占比

这个优化的投入产出比取决于重复查询的比例。做法很简单：把业务日志里的用户问题按语义聚类，算出 top 问题覆盖的查询占比。占比高的业务（客服、常见操作咨询）优先上缓存；长尾占比高的业务，缓存的收益会小很多。

六、案例二 · 企业级文档问答

赛制（Enterprise RAG Challenge 冠军方案）：两个半小时内解析 100 份真实企业年度报告 PDF（每份最多 1000 页，含复杂财务表格、多栏布局、图表），回答 100 个精确业务问题（是否判断、公司名称、数值指标、高管职位），必须给出答案来源的页码引用。

关键技术决策：

  • 解析：选用 IBM 开源 Docling（跨页表格、嵌套表格、多列文本表现最好），改进代码修复单元格合并、表头识别等表格结构问题；
  • 算力：租用 RTX 4090 GPU，40 分钟完成 100 份报告解析；
  • 分块：300 token 长度、重叠 50 token，递归分割保持语义完整；
  • 每家公司单独构建 FAISS 向量库（IndexFlatIP 不压缩保精度），从架构上避免跨公司信息混淆；
  • 检索三步走：向量检索召回 Top 30 文本块 → 提取父页面去重 → GPT-4o-mini 重排；向量分数与重排分数按 0.3:0.7 混合；
  • 生成：按答案类型使用不同提示词模板；数字类问题设计 5 步分析流程（识别指标类型、定位表格、提取数值、验证单位一致性、交叉验证）；多公司比较问题拆分为单公司子查询；
  • 输出：结构化格式，包含分析过程与相关页码，确保可追溯。

成绩：双奖项及排行榜第一。值得注意的是小模型也能超过 80% 的参与者，Llama 3.3 70B 仅比 GPT-4o-mini 稍差——工程细节比堆模型更值钱。

提示三 · 「可追溯」要当硬需求，不要当加分项

这个赛制最值得学的是把页码引用设为必答项。落地到企业项目，可以在评测集里直接规定：凡涉及数值、结论类答案，无引用即判错。倒逼系统在架构上支持追溯，而不是上线后再补。

七、案例三 · 多源数据融合

赛制（KDD Cup 2024 Meta RAG 冠军方案）：任务一基于 5 个网页做检索摘要；任务二增加 Mock API 模拟访问结构化知识图谱（电影数据库、人物关系）；任务三基于 50 个网页加 Mock API 处理复杂查询（如「哪些由某导演执导的电影票房超过 5 亿美元」），每个查询 30 秒内完成。

核心创新：优先使用知识图谱。规范化 API 调用机制（get_person、get_movie 等接口，支持条件过滤与排序）；执行时先调用知识图谱 API，只有图谱结果无效时才回退到 Web 检索。确定性答案直接输出不经过生成步骤，从源头减少幻觉；需要 Web 检索时通过严格文档引用和分步推理确保可验证。

网页数据处理：BeautifulSoup 提取文本；ParentDocumentRetriever 管理父子块关系（子块 200 token 用于检索、父块 500–2000 token 用于生成），兼顾检索准确性与生成完整性。最终三个任务均获第一。

提示四 · 先盘点企业里「已经结构化」的数据

多数企业的知识并非纯文本：产品参数表、组织架构、库存记录都是结构化数据。凡是能结构化的优先走结构化通道，把大模型生成留给真正需要语言组织的部分——这是本案例对企业场景最直接的迁移。

八、案例四与案例五速览

案例四 · 多格式文档解析：企业知识分散在 PDF、PowerPoint、EPUB、HTML 等格式中，传统预处理要么只能处理单一格式，要么转换中丢失表格、标题层级等结构化内容。方案使用 Unstructured 库统一解析（ProcessorConfig 指定输出目录与并行进程数，PartitionConfig 可选 API 分区模式，SimpleLocalConfig 定义输入路径），解析结果转 JSON；chunk_by_title 分块，最大 512 字符，200 字符以下连续片段合并保持语义完整；嵌入模型采用 BAAI/bge-base-en-v1.5，配合 4bit 量化的 Llama-3-8B-Instruct 与 RetrievalQA 链构成完整系统。

案例五 · 图文混合数据处理（AIOps 场景）：运维文档含监控图表、架构图、性能曲线，传统系统读不懂图。方案先用 PaddleOCR 提取图中文字（标题、坐标轴标签），再调用 GLM-4V-9B 多模态模型生成图片的自然语言描述，文字与描述一起入库实现图文统一检索；索引按 1024 token 分块、重叠 200 token，为每个文本块添加知识库路径等元信息（召回率提升 2%）；检索采用 BM25 加向量双路召回；重排序选用 bge-reranker-v2-minicpm-layerwise（28 层配置效果最好）；答案生成两步走（先基于 Top 6 生成初步结果，再结合 Top 1 二次优化）；长文本场景实现基于 BM25 的句子级上下文压缩，50% 压缩率下耗时 7.7 秒、准确率 86.48%，优于 LLMLingua 等现有工具。

九、审查清单

  • 上线前有用例集，且用例来自真实业务日志而非想象
  • 评测数据覆盖高频问题、边界情况、异常输入三类
  • 有统一的问题格式、难度系数与评分标准
  • 标注有多人交叉验证与一致性指标
  • 有定期从线上反馈补充新用例的机制
  • 统计过高频重复查询占比，评估是否值得上语义缓存
  • 缓存层位于「查询与向量库之间」，而非缓存最终回答
  • 数值类、结论类答案强制带来源引用，无引用判错
  • 多实体数据按实体分库，避免跨实体串答案
  • 已盘点企业内可结构化数据，优先走结构化通道
  • 检索为混合检索加重排序，而非单一向量检索
  • 长文档有上下文压缩或父子块机制

十一、常见误区与纠正

误区表现纠正
少量测试题就上线测试全绿、线上翻车从业务日志取样，分层覆盖
评测集写成即归档系统变强但基准不变定期补充答得不好的用例
缓存最终回答个性化要求失效缓存放查询与向量库之间
单一向量检索关键词与语义两头漏混合检索加重排序标配
多实体混在一个库查询 A 返回 B 的信息按实体分库，架构级隔离
答案不带引用无法验证、不敢采信引用设为硬需求，无引用判错
一切交给大模型生成幻觉多、不可追溯结构化数据优先，生成做补充
堆大模型提精度成本涨、收益薄工程细节的收益往往更大
