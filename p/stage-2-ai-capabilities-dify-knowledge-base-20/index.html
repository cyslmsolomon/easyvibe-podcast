逐段精讲

1. 学习方法比节点清单更重要

源文档开篇就给了三条学习建议，值得单独拎出来：

  • 不必一次全掌握，先留印象，用时再查。
  • 在现有模板里替换节点，通过他人的使用方式反推最佳实践。
  • 截图问大模型，直接询问节点用法与所需参数。

画布操作：右键 Add Node 添加，左侧节点面板查看全部，另有工具选择面板。

2. 推理类节点：五个岗位

节点职责配置重点
LLM核心计算单元，调用大模型提示词工程与参数调优
Knowledge Retrieval从知识库 / 外部数据源检索检索源与相关性
Answer把结果整理成最终成果形式输出格式定义（话术模板、排版规范）
Agent多步骤规划 + 自主调用工具工具集与决策边界
Question Classifier按意图 / 领域归类标签定义与描述示例

理解它们的关系，可以借用一条流水线：模型节点是干活的，知识检索是查资料的，回答节点是包装成品的，智能体节点是能自己拿主意的高级工，分类器则是前台接待。

3. 逻辑类节点：分支、并行、递归

三个节点，三种完全不同的时间结构：

  • 条件节点：布尔判断实现分支。设计关键是条件表达式要严谨，覆盖所有业务场景。
  • Iteration 节点：无状态批量并行。适合子任务间无数据依赖的场景（批量翻译、并行审核、同时生成多份报告）。接收数组、自动分片、并行执行，输出自动聚合为数组。配置重点是并行度、重试策略与失败处理。
  • Loop 节点：有状态递归迭代。适合结果依赖前一轮输出的场景（多轮调优、递归式内容优化、链式计算）。核心是状态变量，需先初始化再逐轮更新。

源文档特别强调了循环的终止条件设计，给出三类写法：

  1. 基于计数器：最多循环 10 次
  2. 基于结果判定：满意度评分 > 9
  3. 基于外部信号：检测到「停止」输入

并提醒要设置循环超时、规划异常处理路径（跳出循环 / 重置状态后重试）。这一段是新手最容易忽略、也最容易写出死循环的地方。

4. 数据类节点：八个搬运工

Code（自定义代码）、Template（模板填充）、Variable Aggregator（变量聚合）、Doc Extractor（文档提取）、Variable Assigner（变量赋值）、Parameter Extractor（参数提取）、HTTP Request（外部接口）、List Operator（列表操作）。

这一批看着多，其实永远只问两个问题：数据现在是什么形状，我需要它变成什么形状。 想清楚这两句，选节点就不会犹豫。

HTTP Request 节点是打通外部系统的关键，配置重点在请求地址、请求方法与 headers。Parameter Extractor 则是把非结构化输入转成结构化数据的入口，配置重点在提取规则（正则 / JSON 路径）。

5. 工具节点：能省下大量时间的三条建议

源文档强调，大部分工具都可以直接作为节点放在画布上，像其他节点一样被上下游连线，只要输入符合参数规范即可执行。

三类常见工具：

  • 网络搜索（Tavily Search 为代表）：返回结构化的标题、摘要、链接，可直接作为提示词的一部分，用于最新资讯或需权威依据的问题。
  • 数据处理（JSON Process 插件）：查询、筛选、转换、合并，处理复杂 API 响应或多层嵌套数据，省掉在 Code 节点里手写解析代码。
  • 格式处理（Markdown Exporter）：按指定格式导出，便于展示、汇报或集成。

三条实操建议：

  1. 初期优先尝试「Featured / 推荐」里的工具，覆盖最常见场景。
  2. 工具列表里能看到安装量和简介，可作为选择参考。
  3. 先搜「官方推荐工作流 DSL 案例」直接导入，比自己搭建天然节约很多时间。

6. 为什么要分流：一个模型硬扛的两个毛病

源文档用餐饮场景说明了「一个 LLM 处理所有输入」的代价：

问题一，回复风格不稳定。 同样是抱怨，有时能道歉安抚，有时却像在解释原因；同样是点餐，有时追问缺失信息，有时直接编造订单细节。

问题二，业务逻辑不可控。 你希望「抱怨必须先道歉」，模型未必每次都遵守；你希望「非业务问题引导回主线」，模型可能兴致勃勃聊起段子。

工程化的解法是三段式流水线：先分类（用户到底想干什么）→ 再分流（不同场景用不同提示词与角色）→ 最后统一封装输出（便于前端或系统集成）。

四种意图与四个人格：

意图人格核心任务
buy_food 下单购买下单助手确认订单细节，主动补全缺失信息
complain 抱怨投诉客服专家安抚情绪，提供清晰解决方案
chitchat 闲聊咨询聊天伙伴个性化推荐，引导潜在消费
other 其他意图礼貌门卫把偏离主题的对话引导回核心业务

7. 编排设计：七个节点

  • Start 起点：数据入口，接收原始输入 user_text
  • Question Classifier 意图分类器：大脑与调度中心，从四类标签中选最匹配的
  • Condition 条件分支：分流阀，按标签决定导向哪条路径
  • 四个并行 LLM 节点：独立专家处理单元，各自不同的 System Prompt
  • Variable Aggregator 变量聚合器：把唯一被激活分支的回复收束为统一变量
  • Output 终点：以结构化形式（如 JSON）输出意图标签、原始问题、最终回复

源文档在这里给了一个很坦诚的建议：新手很难凭空想到该用哪些节点，用大模型给编排建议通常是最快最好的选择。

8. 实现步骤与那个最容易踩的坑

实现顺序：选 Workflow（非 Chatflow）→ 定义 User Input 变量 user_text → Test Run 验证 → 添加 Question Classifier 并配置四类标签（含描述与示例）→ 在 ADVANCED SETTING 写入分类提示词 → 用节点右上角播放键单测 → 接四个 LLM 节点并设置不同 System Prompt → 用 Variable Aggregator 聚合 → 用 Template 节点做结构化输出 → 添加 Output 节点。

最容易踩的坑：每个 LLM 节点填完 SYSTEM 提示词后，还要启用 USER 提示词参数。需点击插入变量符号选择 user_text，并在前面加上 user input: 标识。漏掉这一步，模型就收不到用户的原始输入，只会按内置提示词自说自话。

Template 节点承担最终结构化输出，映射关系为：intent ← class_name，original_text ← user_text，final_reply ← variable_aggregator。

审查清单

搭完一条工作流之后，用这张清单逐项过一遍：

  • 条件分支是否覆盖了所有可能的输入，有没有「谁都不匹配」的漏网分支？
  • 用到循环时，终止条件是否明确？有没有计数器 / 结果判定 / 外部信号三重保险？
  • 循环是否设置了超时与异常处理路径？
  • 迭代节点的并行度是否合理？失败时是否有重试或默认值兜底？
  • 每个 LLM 节点除了 SYSTEM 提示词，USER 提示词参数是否已启用并绑定输入变量？
  • 并行分支的输出是否都汇入了变量聚合器？有没有分支结果被丢弃？
  • 最终输出是否为结构化格式（如 JSON），字段是否完整？
  • 分类器是否用至少五组不同类型的输入做过稳定性测试？
  • 外部工具的输入是否符合其参数规范？是否先用官方 DSL 案例验证过？
  • HTTP Request 节点的请求地址、方法与 headers 是否配置正确？
  • 换个用户输入重跑一次，结果是否仍然稳定可控？

实践提示

提示一 · 先用模板，再谈原创

源文档反复强调这一点：直接在现有模板里替换节点，通过他人的使用方式推测最佳实践。对新手来说，从空白画布开始的每一次犹豫，都是在重复别人已经走过的弯路。先抄懂，再改进，最后才谈原创。

提示二 · 用「是否无状态」来区分迭代与循环

这是最容易混淆的一对节点。判断标准很干净：子任务之间有没有数据依赖。 各干各的（批量翻译、并行审核）用 Iteration；下一轮要用到上一轮结果（递归优化、多轮调优）用 Loop。选错了要么跑不动，要么结果不对。

提示三 · 循环一定要写终止条件，而且要写三遍

源文档给了三类终止条件，建议至少叠加两层：计数器兜底（最多十次）+ 结果判定（满意度达标）。只靠结果判定的循环，一旦模型输出不稳定就会空转。只靠计数器的循环，则可能在大功告成前一刻被硬生生掐断。

提示四 · 遇到陌生工具，先搜官方 DSL 案例

工具用起来通常比较复杂。与其自己从零搭建，不如先搜该工具的「官方推荐工作流 DSL 案例」直接导入。这一步能省下的时间，往往比后面所有优化加起来还多。

提示五 · 别让一个模型硬扛所有意图

餐饮场景那两个毛病（风格不稳定、逻辑不可控）不是 Dify 特有的，而是「单一模型处理混合意图」的通用症状。一旦你的系统开始出现「有时这样有时那样」的评价，就是该上分类分流流水线的信号了。
