让智能体持续工作到真正完成 · 任务描述、循环机制、适用边界与成本控制

本内容改编自开源项目 Easy-Vibe，为二次演绎配音版。配套音频由文本转语音生成，本文是音频的图文解读稿，可独立阅读。

一、这一集讲了什么

你有没有遇到过：让它重构一个项目，它改了几个文件就说做完了；让它修一个错误，它跑一次就停下来，其实根本没修好。

这不是它偷懒，而是工作方式决定的：做完一轮就输出一个结果然后停下。它判断有没有做完，靠的是「感觉」而非客观标准——可能觉得差不多了就停，可能觉得输出够多了就停，也可能不知道接下来干什么而停。

人类的完成标准是客观的（测试全过、功能完整、质量达标），它的标准是模糊的。所以需要一个外部系统来判断任务是否真的完成。

本集四件事：任务描述怎么写 → 真实案例 → 什么活适合/不适合 → 怎么盯着、怎么防账单失控。

二、核心概念拆解

概念一 · 任务描述的三段式

不好的写法好的写法
结构一句话：「写一个待办事项接口」分阶段 + 验收标准 + 完成标记
结果写完基础框架就说完成，没有测试、没有验证、没有文档明确知道做什么、何时算完成

三段式模板：

  1. 分阶段描述任务（示例）
  • 阶段 1 基础功能：列出所有增删改查接口（创建 / 获取列表 / 获取单个 / 更新 / 删除）
  • 阶段 2 输入校验：标题不能为空，完成状态必须是布尔值
  • 阶段 3 测试：为每个接口写测试，覆盖率大于 80%
  1. 列出验收标准：所有测试通过、代码通过检查工具、说明文档包含接口说明
  2. 指定唯一完成标记：一串足够特别的文字

关键细节：验收标准要用客观可判定的话（「所有测试通过」），而不是「代码质量良好」这种没法衡量的说法；完成标记要足够特别，避免它在别处也输出同样内容造成误判。

五个现成模板：测试迁移、界面体验优化、批量添加类型、测试驱动的功能开发、代码风格统一——结构都遵循三段式。

概念二 · 停止钩子：把判断权交给外部

核心机制叫停止钩子：

  1. 它想退出时，钩子拦截退出信号；
  2. 检查：输出了那个特定的完成标记吗？
  3. 没找到 → 重新注入原始任务，开始下一轮；
  4. 找到了 → 才允许退出。

这个朴素设计解决的是根本问题：把「完成」的判断权，从它自己的感觉，转移到客观的外部检查上。也解释了为什么完成标记如此重要——它是整个判定机制的唯一依据。

概念三 · 三个真实案例

案例规模成本关键前提
黑客松一夜6 个产品需求 → 6 个可演示项目，设 200 次迭代约 $297每完成一个输出特定标记
负责人 30 天259 个合并请求、497 次提交，新增 4 万行、删除 3.8 万行，100% 由 AI 完成—有明确可验证的流程
一门编程语言3 个月自主构建，含编译器实现、标准库、部分编辑器支持—目标清晰且长期稳定
遗留项目重构一整个周末，47 次提交，覆盖率 75%，文档齐全约 $12测试通过即标准

三点解读：

  1. 成本可以非常低（$12 / $297 与人力成本不在一个数量级）；
  2. 规模可以非常大（3 个月一门语言）；
  3. 共同前提是清晰的完成标准——没有这个前提，跑再多轮也只是原地打转。
提醒：这些是极端案例。第一次用不要按这个规模期待，从一两个小时能跑完的小任务开始。

概念四 · 三条哲学

哲学含义关键转变
迭代大于完美第一次写框架，第二次修错误，第三次优化，第四次补测试把「完美」从前提变成结果
失败是数据每次测试失败都是改进机会失败不是终点，是输入
持续尝试一直试到跑通为止一次性交付 → 可自我修正的过程

概念五 · 适用与不适用场景

✅ 适合（8 类）：测试迁移、大规模重构、框架迁移、批量添加类型、测试覆盖率提升、文档生成、界面体验统一改进、带复现步骤的错误修复。

❌ 不适合（6 类）：架构设计决策、安全相关代码、需求模糊的任务、探索性工作、创意性设计、简单一次性任务。

三个判断问题：

  1. 我能定义明确的完成标准吗？——关键在「明确」，不是大概。代码写得好不好不算，测试通过才算。
  2. 有客观的验证方法吗？——客观 = 不需要人来判断结果。测试、构建、类型检查给的是/否答案；「代码是否优雅」不算。
  3. 这个任务需要我持续反馈吗？——需要你在旁边不断给意见，说明还没收敛到可自动执行的程度。

三个都是否定 → 放手让它去做。

误用的典型后果不是做错，而是空转：一直跑一直跑，每轮改一点，却始终达不到那个根本不存在的完成标准。

概念六 · 四种方法对比

方法特点适用
简单循环5 行代码就能跑，功能有限，无完成检测，只能靠迭代次数限制快速实验、原型验证
通用循环插件完整停止钩子，支持完成标记检测，有官方支持大部分场景（通用推荐）
增强版双重退出条件、速率限制、智能熔断器、实时仪表盘生产环境
后台任务按一个键推送后台，非阻塞，但无循环机制不想干等的一次性任务

任务大到单个实例不够用时，还有多代理并行这条路。

五、审查清单（放手之前逐条过）

  1. 任务描述是否包含分阶段 + 验收标准 + 完成标记三部分？
  2. 验收标准是否都是客观可判定的（而非「质量良好」）？
  3. 完成标记是否足够唯一，不会在别处误触发？
  4. 三个判断问题是否都是「否」？
  5. 最大迭代次数设了吗？（必设底线）
  6. 时间限制设了吗？（双保险）
  7. 预算警告设了吗？（10 / 50 / 100 美元等阈值）
  8. 第一轮跑完是否看过方向对不对？
  9. 后台任务是否会修改你正在改的文件？
  10. 完成后是否安排了人工验收（尤其安全相关功能）？

提示1 · 装保险的顺序不能乱

先设最大迭代次数（底线）→ 再设时间限制（双保险）→ 然后设预算警告（事态恶化前收到通知）→ 最后养成看仪表盘的习惯。

尤其第一轮跑完时要看方向对不对，方向不对立刻停，别等它跑完一百轮。

提示2 · 完成标记要够特别

完成标记是判定机制的唯一依据。如果它是一句普通的话（比如「完成了」），很可能出现在正常输出里，导致循环提前退出、任务其实没做完。用一串明确唯一的标识。

提示3 · 五条实战提醒

  1. 任务描述越详细结果越好——模糊的描述需要更多轮次来修正；
  2. 设置合理的迭代次数——复杂项目建议至少 100 次；
  3. 推荐测试驱动——先写测试可大幅减少调试时间；
  4. 最终仍需人工验证——它可能遗漏边界情况，特别是安全相关功能；
  5. 数据库设计要仔细——它可能需要几轮才能设计出合理结构。

提示4 · 后台任务的正确配合方式

把重头戏交给循环，同时用后台任务处理零散的一次性事务（跑一次完整测试、做一次批量格式化）。这样主线程始终空闲，可随时处理新想法。

注意：推送前确认该任务不会修改你正在改的文件，否则两边同时改容易冲突。

提示5 · 循环的四种安全增强

特性作用
双重退出条件需同时满足完成标记与显式退出信号才真正停止
速率限制默认每小时 100 次，防故障时账单爆炸
智能熔断器连续 5 次检测到完成标记则强制退出
实时仪表盘显示迭代次数、任务进度、预估成本

配置项可写入配置文件：最大迭代次数、每小时速率限制、完成标记文本、退出信号、成本预警阈值。

八、常见疑问三问

疑问一：最大迭代次数设多少合适？

没有通用值，取决于任务复杂度和单轮耗时。文档给出的参考是复杂项目至少 100 次。实操建议是：先按你手动做这件事的步骤数乘几倍来估，跑一轮看看单轮耗时与推进速度，再回头调整。宁可先设小一点，跑不完再加，也不要一上来就设个很大的数字。

疑问二：为什么重构这种「没标准答案」的活也适合？

关键在于你要把标准显式定义出来。重构本身确实没有标准答案，但「为现有代码补充测试」「每次重构后确保测试通过」「更新文档」这三条是可判定的。所以不是重构适合，而是被你定义清楚标准之后的那个重构任务适合。这也印证了三个判断问题的第一问有多重要。

疑问三：成本真的可控吗？

可控，但前提是装好保险。文档里低成本的案例（$12、$297）都是任务清晰、验证客观的情况；真正烧钱的通常是任务模糊、标准不存在的空转。换句话说，成本失控往往不是循环的问题，是任务定义的问题。把任务描述写清楚，是最有效也最便宜的成本控制手段。

九、三十分钟上手练习

  1. （5 分钟） 挑一个你手头的小任务，先用一句话写下它（这是「不好的写法」）。
  2. （10 分钟） 把它改写成三段式：分阶段、验收标准、完成标记。
  3. （5 分钟） 用三个判断问题自测：能定义明确标准吗？有客观验证方法吗？需要持续反馈吗？
  4. （5 分钟） 按「迭代次数 → 时间限制 → 预算警告」的顺序，把三个保护值写下来。
  5. （5 分钟） 跑第一轮，只看方向对不对，不追求跑完。

走完这五步，你就完整体验了一次「把完成标准说清楚」的过程——这也是整套方法真正的门槛所在。

十二、一页纸总结

核心思想：不要让它一次完成，而是让它持续尝试，直到真正完成。

所有方法本质相同：给任务 → 让它工作 → 检查是否真完成 → 没完成就下一轮。

任务描述三段式：分阶段 + 客观验收标准 + 唯一完成标记。

三个判断问题：能定义明确标准吗？有客观验证方法吗？需要我持续反馈吗？三个都否 → 放手。

保险顺序：最大迭代次数 → 时间限制 → 预算警告 → 看仪表盘。

分工：它负责持续尝试与自我修正；你负责定义目标、设定边界、以及最后那一次人工验收。

一句话记牢：让智能体长时间干活，靠的不是更好的模型，而是一套把完成标准说清楚的工程方法。
