一、这一集在解决什么问题

前面数集一直在讲「怎么用某一个平台」，本集换了一个更高的视角：如果用户不想用这套方案，还有哪些工具可选，各自适合谁。

原文在此处一口气给出四张对比表，覆盖后端技术栈的四个关键组件：

  1. 对象存储 —— 非结构化文件放哪；
  2. 边缘函数 —— 服务端逻辑在哪跑；
  3. 实时通信 —— 推送能力怎么来；
  4. 数据库 —— 结构化数据存哪。

这四张表共同构成一张后端组件选型地图。音频稿按「存储上 → 存储下 → 边缘函数上 → 边缘函数下 → 实时 → 数据库上 → 数据库下 → 收尾总纲」的顺序重排，把表格语言转成口语，并补充了原文未明说、但对选型至关重要的判断规则。

三、逐节解读

3.1 对象存储：一条从「省心」到「可控」的光谱

原文列出的五种方案，实际排成了一条光谱：

  • 最省心：腾讯云 COS、阿里云 OSS —— 面向国内市场，文档完善，按量付费；
  • 最标准：Amazon S3 —— 原文称其为行业标准，可靠性高、全球多区域部署，但定价复杂；
  • 最易集成：Firebase Storage —— 与 Firebase / Google Cloud 紧密集成，支持 CDN 加速与细粒度安全规则；
  • 最可控：MinIO —— 开源、兼容 S3 接口，可自建，代价是基础设施自己维护；
  • 最专业：Cloudinary / Imgix —— 针对图片视频优化的云存储加 CDN，功能专一，当通用存储用则成本偏高。

演绎方强调一个容易被忽略的点：S3 的接口规范已经成为行业通用语言，很多其他存储产品会主动兼容它。选一个接口被广泛兼容的服务，等于给未来留了一条迁移退路。

3.2 边缘函数：先看绑定，再看额度

四家候选的差异，本质上不是「谁更快」，而是你愿意被谁绑定：

候选绑定对象免费额度要点主要限制
Cloudflare WorkersCloudflare 边缘网络免费计划每天 100k 请求运行时限制，调试工具有限
Vercel Edge FunctionsVercel 平台与前端框架Hobby 免费每月 100 万函数调用与边缘请求默认运行时 10s，可提升至 60s；免费版团队协作受限
Netlify Edge / FunctionsNetlify 平台免费 300 代币 / 月，约合 1M 请求构建、函数、带宽共用一份额度，需要精打细算
AWS Lambda@Edge / CloudFront FunctionsAWS 生态与 AWS 免费额度叠加配置复杂，延迟略高于 Cloudflare / Vercel

演绎方补充一条看额度的技巧：不要只看请求次数，还要看单次运行时长上限。 若函数常跑十几秒，时长限制会比次数更早触顶。

3.3 实时通信：自建是一道人力采购题

原文给出的四选一，可以压缩成一句判据：

  • 要简单起步 + 生态集成 → Firebase Realtime Database / Firestore（短板是文档型结构，复杂查询弱）；
  • 要高并发 + 大消息量 → Ably（免费可达每月 600 万条消息）；
  • 要快速做聊天与通知 → Pusher Channels（免费每日 200k 消息、100 并发连接）；
  • 要完全定制 → 自建 WebSocket / Socket.IO（灵活度最高，但可用性、扩展、跨域全部自理）。

自建不是技术选择，是人力采购决策。 原文明确列出自建的代价：需自行处理可用性、扩展和跨域等问题。

3.4 数据库：看主打功能，反推它解决的问题

同为关系型数据库还能分出多家，原因是各家解决的痛点不同：

候选主打能力免费额度要点
NeonServerless PostgreSQL，支持分支（fork 测试）0.5GB 存储，主分支永久在线，每月 20h 分支计算
Aiven托管关系型，支持跨云多区域迁移1GB 存储、1 vCPU、1GB 内存
CockroachDB Cloud分布式 SQL，兼容 PostgreSQL，自动分片10GB 存储
TiDB Cloud分布式关系型，兼容 MySQL 协议每节点 5GB，总计最多 25GB
MongoDB Atlas文档型（NoSQL）M0 集群 0.5GB 存储
SQLPub多数据库一站式每小时 36,000 请求、30 并发、500MB 存储

看主打功能就能反推它当初想解决的问题：Neon 针对「改库结构太危险」，Aiven 针对「不想被一朵云绑死」，CockroachDB 与 TiDB 针对「数据量大到单机装不下」。

3.5 原文给出的总纲

原文在四张表之后的总结段，是整份选型内容的收束，几乎可以原样作为决策起点：

开源更灵活可控（Keycloak、MinIO、Socket.IO、Neon、CockroachDB 等），云托管服务更易上手（Firebase、Auth0、Cloudflare、Vercel、Netlify、AWS、Aiven、MongoDB Atlas 等）。

四个权衡维度：项目需求、团队技术栈、预算、社区生态。

两类典型结论：

  • 个人项目 → 优先选免费配额充足、易集成的服务；
  • 企业级或有特定安全需求 → 考虑功能更丰富但收费较高的方案。

原文最后一句特别值得记住：你可以在实际应用中不断尝试，直到选择出最适合的后端开发工具组件。 选型这件事，看十张表不如亲手跑一个小项目。

五、实践提示

提示1 · 用「未来规模」倒推，而不是用「当前规模」

免费额度看的是现在，选型看的是未来。看额度时请把用户量乘以十再算一遍，问自己：明年这个时候我还在免费额度里吗？如果答案是否定的，就要同时看清楚超出之后的计费规则。

提示2 · 优先选接口被广泛兼容的方案

对象存储选兼容 S3 接口的产品，数据库选兼容 PostgreSQL 或 MySQL 协议的产品。这类「事实标准」的兼容性，是你在未来换供应商时唯一的议价筹码。

提示3 · 自建前先折算人力成本

自建方案把成本从账单转移到了人的时间上。个人项目和小团队通常不划算。只有当存在数据不出机房的合规要求，或者规模大到云账单明显超过自运维成本时，才值得认真考虑。

提示4 · 记录你放弃了什么

选型最容易犯的错，是只记录选了什么、不记录放弃了什么。请在决策时写下被放弃方案的主要短板——半年后当新方案踩到同样的坑时，这份记录会告诉你当初的判断错在哪。
