一、这一集在解决什么问题

这一集拆的是一份完整且贴近真实项目的产品需求文档：一个现代化 AI 生图 SaaS 网站。

产品体验参考 Midjourney、Leonardo、Playground 这类平台，但后端不训练自己的模型，而是对接第三方图像生成模型服务——这个取舍意味着项目重心不在算法，而在产品闭环。

量级：三套入口、十九个大页面、九个后端模块、三十多个接口、四档套餐、十三条待确认项。

音频稿按「定位 → 技术选型 → 用户与目标 → 做与不做 → 页面架构 → 后端模块 → 套餐积分 → 非功能/顺序/待确认 → 收尾」重排，重点不是念文档，而是看一份能落地的 PRD 是怎么一层一层搭起来的。

一句话概括：第一版要做的不是一个展示页，而是一套最小可用的产品闭环。

三、逐段拆解

3.1 定位：不是展示页，是闭环

展示页的目标是让人看懂，产品闭环的目标是让人用起来并且回得来。 前者只需要页面，后者需要注册、状态、记录、付费、回访的理由。

第一版范围被明确列成九项：官网落地页、注册登录、提示词输入与生成、历史记录与结果管理、套餐/额度体系、积分体系、分享与公开展示、点赞评论转发、管理后台。

三个入口分开的理由：游客在官网是被说服的人，用户在工作台是干活的人，管理员在后台是排查问题的人——塞进同一个界面，三边都难受。

常见错误：把第一版写成功能集合，却忘了回答「用户第一次来，走完哪几步才算真的用上了」。这份文档的答案很明确：三分钟内完成注册并生成第一张图。

3.2 技术选型与它背后的取舍

默认方案：前端用带路由的框架；鉴权、数据库、文件存储交给同一个后端平台；支付用成熟支付服务；图像生成通过统一后端适配层对接第三方模型。

原文罕见地写了一段「默认原因」，三条：

  1. 适合第一版 SaaS 快速落地
  2. 用户系统、数据库、对象存储一起解决
  3. 对两套前端都友好，后续拆独立服务也留了空间

把选型理由一起写下来，是区分资深和新手最好的一条线——理由会在两个月后被重新拿出来讨论，那时如果没人记得当初为什么这么选，团队就会重新吵一遍。

鉴权设计四个要点：普通用户支持邮箱密码 + 第三方登录；管理员用同一套登录系统但在用户表标记角色；后台管理台必须校验管理员权限；用户前台与后台接口分开鉴权。

最后一条是很多项目出事故的地方：前后台共用一个接口、只靠前端判断权限，等于把门锁装在窗帘上。

数据库：主业务库用一套关系型数据库，六类数据先放一起，分析型查询先基于主库聚合，数据量大后再拆。先跑起来，别一上来就做分布式。

3.3 用户、目标与北极星指标

四类目标用户：想快速出图的普通用户 / 批量试提示词的设计师与创作者 / 浏览并互动的社区用户 / 管理用户与额度的管理员。四类人对应三套入口。

四条核心目标：3 分钟内完成注册并生成第一张图 / 清晰看到生成结果、积分消耗与历史 / 可以分享作品并获得互动反馈 / 支持积分购买消耗、失败重试、内容互动和后台管理。

注意第三条——分享与互动被写进核心目标，而不是可选增强。 这说明产品从第一天就不打算只做工具，它想做社区。

北极星指标（8 个）：

指标说明
新用户首图生成成功率排在第一位
日活跃生成用户数—
人均生成次数—
生成任务成功率—
付费转化率—
分享图片数—
点赞/评论互动率—
日活跃积分用户数—

首位是「新用户首图生成成功率」而不是注册数或收入——这个排序本身就是产品判断。 对这类产品，第一次就生成失败的用户大概率不会来第二次。

用法：把这八个指标当检查表，问自己每一个在当前系统里能不能被算出来。算不出来的那几个，就是数据表还缺的地方。

3.4 范围：做什么与不做什么

必须包含 12 项：官网首页、注册登录、生图工作台、图片历史页、套餐/积分页、积分页、支付订阅、公开分享页、点赞评论转发、图片生成接口、任务状态查询、后台查看用户/任务/积分/互动。

明确不做 5 项：自训练模型、多模型工作流编排、图片编辑器、团队协作、多语言。

不做清单比做清单更重要——做清单大家都能想到，而不做清单才是真正防止项目失控的东西。尤其第一项和第三项：自训练模型会把重心从产品拽到算法，图片编辑器几乎是一个独立产品的工作量。

三类角色权限：

角色权限
游客浏览官网、查看介绍、注册登录
注册用户创建任务、查看历史、管理积分与结果、查看明细、分享、点赞评论转发
管理员查看用户/任务状态/失败日志/套餐与积分消耗，管理积分规则、公开内容与互动数据

写权限的技巧：不要只写谁能做什么，要写清谁不能做什么。 边界写在哪一侧，决定了实现时会不会漏。

3.5 三套入口与十九个页面

总量：官网 1 + 工作台 9 + 后台 9 = 19 个大页面。

  • 官网首页：Hero、作品展示、功能介绍、价格方案、FAQ、CTA
  • 用户工作台：登录、注册、生成工作台、历史图库、套餐页、积分页、社区广场、作品详情页、个人中心
  • 后台管理台：首页概览、用户管理、任务管理、内容管理、套餐管理、支付订单、运营配置、指标看板、系统监控

生成工作台：正向/反向提示词、模型/比例/数量/质量参数、提交任务、三种状态（生成中/成功/失败）、再次生成/收藏/发布。

作品详情页：大图、作者与发布时间、完整提示词与参数、互动数据、复制提示词/再次生成/点赞/评论/转发。

两个后台页面值得单独提：

  • 指标看板：新增用户、DAU/WAU/MAU、注册与付费转化、次日/7 日/30 日留存、套餐分布与续费、积分发消耗余、社区分享点赞评论转发率
  • 系统监控页：API 调用量/成功率/错误率/耗时、第三方模型调用、数据库连接与慢查询、支付回调、任务队列积压与重试、告警与异常日志

为什么要专门做监控页：这类产品最致命的不是崩掉，而是悄悄变慢、悄悄涨价、悄悄失败——没有监控页，你只能等用户在评论区告诉你。

前端核心组件 19 项中，最容易被新手忽略的是空态、加载、失败重试这三个——它们恰恰决定了产品给人的是粗制滥造还是专业可靠。

3.6 后端模块与接口清单

九个模块：auth（注册登录鉴权）/ generation（创建任务、查状态、失败重试）/ images（历史、删除、收藏、详情）/ points（购买、累计、扣减、奖励、兑换记录）/ billing（套餐、支付记录、升级）/ social（公开发布、点赞、评论、转发）/ analytics（留存、转化、订阅、积分、社区活跃）/ observability（API、模型、数据库、告警）/ admin（查看用户任务错误日志、审核内容、运营配置）。

划分方式值得学：按业务能力切，而不是按技术层切。 好处是每个模块都能对应到某类用户的一个具体动作，责任清楚，不会出现谁都不管的地带。

接口约 37 个，三个观察：

  1. 积分接口被单独拆出（查余额、查明细、签到、兑换四个）——说明积分是一等公民，不是支付模块的一个字段。
  2. 后台接口统一前缀，管理动作用修改类方法——权限校验可集中在中间件，不用每个接口各写一遍。
  3. 审核接口用修改类方法而非删除——保留恢复可能，是内容型产品的标准做法。

3.7 套餐与积分设计

套餐逻辑：积分型订阅套餐；月付/年付两种，年付默认优惠 20%；按月发放积分；生成图片、生成视频、高清能力、并发能力由套餐共同决定。

套餐月付年付折后每月积分图片并发视频并发其他权益
Basic$10$82,00031基础生图、可补购积分
Standard$30$248,00033高清视频、无限慢速图像生成
Pro$60$4818,000126隐身生成、更多并发
Mega$120$9640,0001212更高上限，适合高频创作

设计重点：套餐之间拉开的不只是积分数量，还有并发路数和功能开关。只靠积分数量拉不开差异时，重度用户会全挤在最低档；并发与专属功能才能真正区分付费意愿。

六条 FAQ 建议：买了套餐没生效怎么办 / 月付年付差别 / 积分用完怎么办 / 积分会不会过期 / 能否绑定多个登录方式 / 哪些内容支持公开分享。

其中前两条与第四、第五条，是上线第一天最容易收到工单的问题——提前写好答案，等于提前省掉一批客服成本。

3.8 非功能要求、开发顺序与待确认项

非功能要求 11 条（摘要）：生成过程有明确状态反馈 / 失败任务能提示原因 / 移动端至少可查看浏览历史结果 / 首页具备现代 SaaS 视觉质量 / 用户只能访问自己的图片和任务 / 积分扣减稳定可追踪 / 积分发放与扣减可审计 / 公开内容有最小审核或风控预留 / 互动接口预留防刷限流 / 后台指标支持日周月维度 / 日志、数据库、模型调用可追踪。

其中 3 条关于积分、2 条关于可追踪——这不是凑数，是吃过亏之后才会写出来的东西。钱和账，是这类产品最容易出问题的地方。

开发顺序九步：官网首页与登录注册 → 用户鉴权 → 生成工作台 UI → 生图任务接口 → 历史图库 → 支付/套餐/积分/FAQ → 分享点赞评论转发 → 独立后台与各管理页 → 指标看板与系统监控。

特点：先打通一条最短的可用路径，再往两边长，而不是按模块顺序从鉴权一路做到监控。

十三条待确认项（摘要）：第三方模型优先接哪家 / 图片是否允许公开分享 / 后台是否必须独立二级域名 / 积分是否含邀请奖励 / 积分是否只用于生成消耗 / 年付优惠是否固定 20% / 是否需要单独积分包 / 是否接受默认鉴权与数据库方案 / 留存与监控是否先做基础报表 / 评论是否允许二级回复 / 转发是站内还是带外链 / 第一版是否需人工审核。

意义：它诚实地承认这份文档还没想完。把没想完的部分显式列出来，比假装想完了安全得多。

四、约束

约束一：第一版必须跑通闭环，不是做展示页。 判断标准是「用户能否在三分钟内完成注册并生成第一张图」。

约束二：不做清单必须写，且必须被遵守。 自训练模型和图片编辑器尤其会拖垮第一版。

约束三：前后台接口必须分开鉴权。 后台校验必须在服务端，不能只靠前端判断。

约束四：积分相关逻辑必须可追踪、可审计。 三条非功能要求都指向这一点。

约束五：开发顺序先打通最短路径。 不要按模块顺序从鉴权一路做到监控。

约束六：待确认项要显式列出。 没想完的部分写清楚，比含糊过去安全。

五、与 Easy-Vibe 其他章节的关系

在 Easy-Vibe 的脉络里，这一集是「把需求写清楚」这条线的集大成者。

前面几集讲的是需求文档的组成部分——定位、画像、用户故事、MVP 功能、非功能性需求、路线图；这一集给出的是一份把这些部分全部装配起来的完整样本。

和上一集的平台选型连起来看，两集正好互补：上一集决定容器，这一集决定内容。 上一集说「先做最短入口」，这一集演示了什么叫最短入口——不是页面少，而是闭环短。

还有一个可迁移的点：这份文档把「为什么这么选」也写了进去。 无论是平台选型、技术选型还是风格选型，留下理由，都是给两个月后的自己省一次争论。

六、审查清单

写自己的 PRD 时逐条打勾：

  • 已用一句话说清「这是什么、给谁、不做什么」
  • 已明确第一版是闭环而不是展示页，并给出最短路径
  • 技术选型已附带理由
  • 前后台鉴权已分开，后台校验在服务端
  • 目标用户按使用场景分类，而非按人口统计分类
  • 北极星指标已列出，并确认每个都能被算出来
  • 已有明确的「不做清单」
  • 三类角色的权限边界（尤其「不能做什么」）已写清
  • 页面清单已按入口分组，并覆盖空态/加载/失败三种状态
  • 后端模块按业务能力切分，每个模块对应一类用户动作
  • 套餐差异不只靠数量，还靠并发与功能开关
  • 积分的扣减与发放逻辑已要求可追踪、可审计
  • 待确认项已显式列出

七、实践提示

提示1 · 用「三分钟能否出第一张图」检验闭环

不要问功能齐不齐，要问用户第一次来走完哪几步才算真的用上了。答不上来，说明你写的是展示页。

提示2 · 写选型时把理由一起写下来

理由会在两个月后被重新讨论。留下理由，就是给未来的自己省一次争论。

提示3 · 不做清单至少列五项，并挑出最危险的两项

这份文档里最危险的是自训练模型和图片编辑器——一个拽走重心，一个是独立产品的工作量。

提示4 · 后台一定要有监控页，不只是管理页

这类产品最致命的不是崩掉，而是悄悄变慢、悄悄失败。没有监控页，你只能等用户在评论区告诉你。

提示5 · 套餐差异别只堆数量

只靠积分数量拉不开差异时，重度用户会全挤在最低档。用并发路数和功能开关来真正区分付费意愿。

八、收尾
