为什么长文配图总翻车 · 用「理解层 + 执行层」搭一个素材生产智能体

本内容改编自开源项目 Easy-Vibe，为二次演绎配音版。本篇对应源文档 stage-2/frontend/lovart-assets/index.md 的「局部参考 / 多图整合」及第三章「思考层」部分，配套音频为本目录下的 stage-2-frontend-lovart-assets-47-播客.mp3。

一、这篇要解决什么问题

一句话概括：当你把一整篇文章丢给画图模型，为什么出不来好图，以及怎么修。

很多人遇到这个问题的第一反应是「模型不行」或者「我提示词写得不好」，于是开始堆形容词。这一节给出的诊断完全不同：

原因并不在于模型「画得不行」，而在于它并不擅长理解长文本。

图像生成模型适合处理简短、明确的视觉描述；当输入变成一段包含结构、重点和上下文关系的文章时，模型无法判断哪些内容才是画面中真正需要表达的部分。结果是两种典型失败：

  • 偏离主题：抓住了一个你觉得不重要的词，把整张图都画成了那个词。
  • 零散堆砌：画面里有文章中出现过的元素，但拼在一起说不出文章在讲什么，缺乏整体概括能力。

本质判断：图像模型只有「执行」的能力，却缺少对文本进行分析和取舍的过程。

二、能力地图

完成这一节后，你应该具备：

  1. 问题归因能力：能把「画得不好」这种模糊抱怨，翻译成「中间少了一层」这种结构问题。
  2. 分层设计能力：能识别一个任务里哪部分是理解、哪部分是执行，并把它们拆到不同的模块里。
  3. 意图分流能力：知道为什么要先对输入分类，再走不同的处理路径。
  4. 角色分工能力：能为一个多模型系统定义清楚「谁决策、谁执行、谁介入、谁承载」。
  5. 提示词工程能力：能写出一段「带判断标准、带版式暗示、带输出约束」的生图提示词生成指令。
  6. 可控性设计能力：知道把关键参数（系统提示词、最终提示词）暴露到界面上可编辑，是工具能否真正用起来的分水岭。

三、核心机制 · 四步链路与四种角色

主链路


长文本输入
    │
    ▼
语言模型：理解与判断（思考层）
    │
    ├── 无效输入 ──────► 拦截，不再往下走
    ├── 直接绘图指令 ──► 跳过理解，直接生图
    └── 长文本 ────────► 生成视觉提示词
                              │
                              ▼
                        图像模型：执行生成
                              │
                              ▼
                            输出图片

四种角色分工

角色职责关键约束
语言模型理解文章内容、判断意图、分发路径、生成生图提示词系统中唯一需要动脑的部分
图像模型接收已整理好的视觉指令，专注渲染不参与理解与判断
用户输入文本、手动调整提示词、加入参考图始终握着最后的方向盘
界面 + 后端接口串联界面、模型调用、结果展示让整条链路可观察

提示一 · 为什么「界面层」不是可选项

很多新手觉得做界面是额外的活，能省则省。但在这个智能体里，界面承担的是调试工具的角色。

如果你的智能体只有一个输入框和一张输出图，结果不对时你根本无从下手——不知道是意图判错了、提示词写偏了，还是模型画歪了。而当你把中间产物（识别出的意图类别、生成的提示词原文）都摆到界面上，问题在哪一步是一眼的事。

做界面在这里是省时间，不是花时间。

提示二 · 三种意图要按「成本」而不是「类型」来理解

意图特征处理方式不处理的代价
无效输入无法对应到任何画面的问候与寒暄拦截每次寒暄都在烧调用额度
直接绘图指令已包含明确主体和动作的一句话跳过理解，直接生图模型把你已经说清楚的要求重新概括成走样的话
长文本需要概括才能成图的多句内容走完整链路——

先分流再处理，既省钱又准确。先堵住不该走的路，再优化该走的路。

四、生图提示词生成模块

意图识别之后，对长文本还需要把「理解结果」翻译成「视觉指令」。文档预设的系统提示词可以拆成四个部分：

部分内容作用
角色设定你现在是一个创建画图提示词的助手锁定任务边界
判断标准这张图要能说明这一段在说什么，并体现上下结构给模型一把取舍的尺子
版式暗示类似演示文稿，左上角展示核心观点，右下角展示数据让图带上信息结构，而不只是好看
输出约束直接返回可用的英文提示词，不要解释、前缀或废话下游可直接消费，无需清洗

提示三 · 这一段里最值钱的是「输出约束」

「请直接返回……不要返回任何解释、前缀或多余的废话」这句话，解决的不是文风问题，是工程问题。

因为这一段提示词的输出不是给人看的，是要直接喂给下一个模型的。只要它多说一句「好的，以下是提示词」，下游就得再写一段清洗逻辑，而且这段逻辑永远洗不干净。把约束写在源头，比在下游打补丁便宜得多。

同理，这个系统提示词本身也被设计成可在网页上编辑的——文档演示了在里面加一句前缀，生成的提示词就真的带上了。这样做的目的是快速切换风格，而不用去改底层代码。

提示四 · 「以最终点击按钮时的提示词为准」

文档特别说明：前面步骤生成的提示词可以在网页上编辑，系统以你最终点击按钮时的提示词为准。哪怕你把框里的内容换成「一只可爱的猫」，最终生成的也只会是可爱的猫。

这条规则看着简单，但它消灭了一个真实的困惑：中间改了半天，机器到底听的是哪一次的话？ 答案明确——听你最后点的那一下。

在搭任何多步流程时，都要明确「以哪个时刻的状态为准」，否则用户会陷入「我明明改了为什么没变」的泥潭。

五、两个实用技巧 · 局部参考与多图整合

功能操作典型用途
局部参考点击画布左侧标签栏 → 选「Mark」→ 在目标图上标记区域 → 内容自动同步到对话框只改背景颜色，角色、造型、光线全不动
多图整合保留 A 图主体 + 引用 B 图的子元素，智能体后台自动整合视觉约束保留第一张图的鸭子形象，替换到第二张图作为主体

底层思维：零件化

这两个功能说的是同一件事——把一张图拆成若干可独立替换的零件。

  • 以前的说法：「帮我画一个戴帽子的鸭子」（在跟运气谈判）
  • 现在的说法：「主体沿用这张图，只把帽子换成这一顶，其他不要动」（在下订单）

你表达得越像订单，工具跑偏的空间就越小。

六、审查清单

  • 是否明确说出「图像模型不擅长理解长文本」这一归因，而不是笼统说「画得不好」？
  • 是否把链路拆成了「理解」与「执行」两层，而不是只写一段更长的提示词？
  • 三种意图（无效输入 / 直接指令 / 长文本）是否都定义了明确的判定特征？
  • 四种角色（语言模型 / 图像模型 / 用户 / 承载层）的分工是否写清楚？
  • 界面上是否能看到意图类别和生成的提示词原文（可观察性）？
  • 生图提示词的生成指令是否包含「判断标准 + 版式暗示 + 输出约束」三部分？
  • 输出约束是否明确要求只返回提示词、不要解释？
  • 系统提示词是否可在界面上编辑（而非写死在代码里）？
  • 是否明确了「以最终点击按钮时的提示词为准」？
  • 局部参考与多图整合两个功能是否都实际试过一次？
  • 测试时是否按「先无效输入 → 再直接指令 → 最后长文本」的顺序验证？

能力自测

不用真的把智能体搭出来，用下面五个问题判断自己是否真的懂了：

  1. 用户说「帮我配张图好看点」，这句话该判成哪一类意图？为什么它其实是个坏输入？
  2. 如果图像模型开始参与意图判断，会发生什么？
  3. 生图提示词的生成指令里，哪一句决定了下游能不能直接消费输出？
  4. 用户在界面上改了提示词但没点按钮，最终生成会听哪一次的？
  5. 如果要把这套结构改成「长文转演示文稿」，哪一层要换，哪一层可以不动？

能答上三个以上，说明「理解层 + 执行层」这个模型你已经内化了。

八、常见误区与纠正

误区表现纠正
把问题归因为模型不行换模型、加参数，反复试归因到结构：中间缺一层理解
用更长的提示词硬堆形容词越加越多，画面越来越乱约束变多而取舍能力没变，只是把混乱变得更精致
让一个模型干所有事又理解又画图，两头都不稳分层，谁决策谁执行写清楚
不做意图分流每次寒暄都走完整链路，烧额度还变慢三类意图先分流，先堵住不该走的路
跳过界面直接写脚本结果不对时完全无法定位界面是调试工具，中间产物必须可见
系统提示词写死在代码里每次换风格都要改代码重新部署暴露到界面上可编辑
四个环节一次全接上出问题定位不到是哪一环按界面 → 意图 → 提示词 → 生图的顺序逐步验证
忽略「以哪次输入为准」用户改了半天没生效，以为有 bug明确以最终点击按钮时的状态为准

九、时间不够时怎么砍出最小可行版本

  1. 必须先保留：意图识别（至少区分无效输入与其他）、长文本生成提示词、图像模型执行。这三步是「思考层」之所以成立的最小集合。
  2. 可以后置：局部参考与多图整合。它们是在主链路跑通之后的增强项。
  3. 可以简化：三种意图先砍成两种（无效输入 / 可生图），把长文本和直接指令合并处理，先把链路跑通再细分。
  4. 不能省：输出约束（只返回提示词、不要解释）。这一项省掉会让下游永远在打清洗补丁。

十、给第一次搭的人的顺序建议

严格按这个顺序推进，不要并行：

  1. 先只做界面框架，跑起来能看到页面，哪怕按钮都是空的。
  2. 再接语言模型做意图识别，先用三条边界样本测通：「你好」（无效）、「我要画一只猫」（直接指令）、一段说明文（长文本）。
  3. 确认意图分流准确之后，再做提示词生成模块。
  4. 最后才接图像模型。

不要一上来就把四个环节全接上。 全接上的结果是任何一个环节出问题你都定位不到，而按这个顺序，每一步结束时你都能明确知道「到目前为止是好的」。

十一、一页纸总结

环节一句话要点
问题长文配图翻车，不是画得差，是模型不擅长理解长文本
归因图像模型只有执行力，缺少分析与取舍的过程
解法不是写更长的提示词，而是补一层思考层
链路长文本 → 语言模型理解 → 视觉提示词 → 图像模型执行 → 出图
分流无效输入 / 直接指令 / 长文本，三类走三条路
分工语言模型决策、图像模型执行、用户介入、界面承载
关键系统提示词要含判断标准、版式暗示、输出约束
可控提示词可在界面编辑，以最终点击按钮时为准
技巧局部参考与多图整合，本质是把图拆成零件
心态留下的不是模型名字，而是「什么交给它、什么自己定」的分工感

十二、这条结构还能用在哪

「理解层 + 执行层」的拆法不局限于画图：

  • 长文转演示文稿：先让语言模型提炼大纲与每页要点，再交给排版工具执行。
  • 需求文档转原型：先让语言模型拆出页面结构与组件清单，再交给前端生成。
  • 会议纪要转任务：先让语言模型识别决策项与责任人，再写入项目管理系统。

共同点是：执行方只对明确指令负责，不做取舍。只要你的任务里存在「先想清楚再动手」这个环节，这套结构就能套上去。
