s3-15 作业实战合集 · 解读与音频稿件

本稿为音频配套解读，围绕三个 Stage 2 综合实战作业——在线考试与管理系统、生鲜电商微服务系统、Go 交通数据分析平台——梳理它们的共同主线与各自侧重，帮助你在动手前先建立正确的拆解动作。

一、为什么把三个作业放在一起讲

单看这三个作业，技术栈几乎没有交集：一个是 Express 加多角色权限，一个是 Next.js 加五个微服务，一个是 Go 加数据链路。放在一起讲，似乎有些跳跃。

但如果你把这层技术外壳剥掉，会发现它们的骨架高度同构。每一个都要经历同一串动作：读一份真实的需求文档，从中提取开发任务清单，把任务拆成一个个可以独立推进的模块，为核心业务规则定下明确的口径，把端到端链路跑通，最后用一份统一的交付物收口。差别只在每个作业把哪一环压得更重。

第一个作业压的是角色与权限。第二个作业压的是服务拆分与协作。第三个作业压的是数据链路与口径一致性。把这三者并排摆在一起，你看到的其实是同一套方法论在三种业务形态下的投影。这也是本集的核心判断：真正被反复训练的，不是某个框架的写法，而是面对约束之后的稳定拆解能力。

二、能力地图：三个作业共同要求的能力

如果我们把三个作业的交付物和评分标准摊开对照，会发现它们其实在反复点名同一组能力。

第一层是读需求的能力。 三个作业都明确要求你先读需求文档，并且都给出了同一句警告：如果关键问题没有明确答案，不要开始写代码。考试系统要你确认角色、页面、题型和流程；微服务要你确认下单链路和状态流；数据平台要你确认指标定义和告警规则。需求理解不清楚是导致返工最常见的原因，这句话在三个作业里被反复验证。

第二层是拆任务的能力。 考试系统拆成前台、学生端、管理后台三个子系统；微服务拆成网关、鉴权、商品、库存、订单五个服务；数据平台拆成接入、聚合、告警、看板四个模块。拆分的粒度可以不同，但动作是同一个：找到系统里相对独立的边界，让每一块都能被单独推进和验证。

第三层是定规则的能力。 考试系统的核心规则是判分，客观题自动判、简答题先存答案标记未复核。微服务的核心规则是下单，库存不足直接失败、同一订单只允许成功创建一次、所有状态变化可追踪。数据平台的核心规则是指标口径与告警阈值。规则一旦含糊，后面所有的代码都会失去判据。

第四层是连链路的能力。 三个作业都把端到端联调写进了交付要求。考试系统要跑通学生和教师两条完整路径，微服务要跑通下单主链路的六步，数据平台要跑通接入到看板的全链路。能跑通，才叫交付。

第五层是收口的能力。 三个作业的交付物结构惊人地一致：线上演示链接、源码仓库、需求文档、核心页面截图、六十秒演示视频。这不是巧合，而是一种刻意统一的验收标准。

这五层叠起来，就是这三个作业真正想让你长出的能力地图。技术栈会换，这五层不会。

三、作业一：在线考试与管理系统的拆解要点

3.1 角色边界要先立住

这个系统的第一个难点不是代码，而是角色。学生和管理员看到的页面、能执行的操作完全不同。如果你一上来就写页面，很容易写出一个两边混在一起的半成品。

正确的顺序是先划分系统：官网前台只负责介绍与登录入口，学生端负责考试列表、答题、提交和成绩查看，管理后台负责题库、考试、提交记录和成绩统计。角色清晰之后，接口该挂在哪个路径下、页面该归到哪个入口，都会变得顺理成章。

提示1 · 判分逻辑要显式写出来

判分是这个系统的核心业务规则，也是最容易被写乱的地方。务必把三类题型的规则分开处理：单选题答案与标准答案一致则得分，判断题同样自动判分，简答题在第一版里只保存答案、分数留空、状态标记为未复核。把「未复核」这个状态显式写进数据模型，后面的管理员复核功能才有落脚点。

3.2 页面骨架与检查清单

前端先立骨架，管理后台第一版聚焦三个区域：考试管理、题库管理、提交记录。骨架立好之后逐条对照检查清单：学生端和管理端入口是否分开，登录页、考试列表、答题页、成绩页是否完整，管理端各页是否可访问，以及两端页面风格是否有明显区分。最后一条常被忽略，但它直接影响评审对角色切分的判断。

提示2 · 端到端联调至少覆盖两条路径

一条是学生的完整路径：登录、查看考试列表、开始答题、提交、查看成绩。另一条是管理员的完整路径：登录、创建考试、添加题目、发布、查看提交记录。这两条路径都跑通，才说明业务闭环真正立住了。只测单点接口是不够的。

3.3 部署与交付

部署采用前后端分离：前端放 Vercel 或同类平台，Express 接口放支持 Node 的托管服务，数据库用托管 Postgres。上线前检查环境变量、接口地址、生产环境的登录态、管理员账号能否真实进后台，以及说明文档是否完整。交付物五项，评分从页面完整度、业务闭环、数据正确性、权限控制、工程交付五个维度衡量。注意权限控制这一项，基本要求是访问边界清晰，进阶要求是服务端接口本身也做角色校验。

四、作业二：生鲜电商微服务的拆解要点

4.1 服务边界决定一切

这个作业练的不是业务复杂度，而是服务协作。一句话定义是：做一个由网关、鉴权、商品、库存、订单协作完成交易闭环的系统。技术选型上，前端 Next.js，网关和服务层 Node 加 Express 或 Fastify，数据库 PostgreSQL，鉴权用令牌，编排用 Docker Compose。

五个服务的职责必须清晰：网关统一路由、鉴权和聚合返回；鉴权服务负责注册登录与令牌校验；商品服务负责商品信息、分类与上下架；库存服务负责查询、预扣与回滚；订单服务负责创建、状态流转与查询。第一版明确不做真实支付、优惠券、秒杀、消息队列集群和分布式事务框架——先把链路跑通，比堆功能更重要。

提示3 · 下单主链路的六步要能讲清楚

微服务最容易讲不清的就是一条链路到底经过谁。请记住这六步：用户提交订单，网关完成鉴权，订单服务校验商品，库存服务预扣库存，订单服务创建订单，成功则确认库存、失败则补偿回滚。再配上三条关键规则——库存不足直接失败、同一订单只允许成功创建一次、所有状态变化可追踪。前两条治并发和重复提交，第三条治排查。

4.2 前台体验要保持统一

微服务是藏在后台的，前台仍然应该像一个统一产品，而不是几个接口拼出来的样子。可以借鉴成熟生鲜电商的购物路径，让从浏览到购物车再到订单查看这条线足够直接。用户端强调快速下单，管理端强调状态管理。页面包括首页、商品详情、购物车、我的订单，以及管理端的商品维护、库存调整、订单列表。

4.3 监控与开发顺序

工程上有两件容易被忽略的事：后台指标至少看下单成功率、库存回滚次数、热销排行、订单状态分布和库存预警数；基础监控至少看网关错误率、鉴权成功率、库存服务超时率和订单创建失败率。开发顺序建议：先搭工作区和网关，再做鉴权服务，接着商品与库存，然后订单下单闭环，之后才是前端，最后补容器编排和文档。按这个顺序走，每一步都能跑到东西。

提示4 · 待确认项是取舍，不是遗漏

这个作业列了几项待确认项：前端是否做购物车持久化、服务间通信先用 HTTP 还是预留消息机制、商品与库存是否拆独立数据库、管理端是否允许直接修改订单状态。这些不是没想清楚，而是每一项都对应一个真实的取舍。动手前先形成自己的判断，比照抄一个默认答案更有价值。

五、作业三：Go 交通数据分析平台的拆解要点

5.1 数据链路是主线

这个作业换了一个物种，它不是增删改查，而是一条数据链路：数据接入、聚合、告警、可视化。平台分四个模块，接入负责接收原始事件并入库，聚合负责按时间窗口计算趋势和拥堵指标，告警负责基于规则生成记录，看板负责展示趋势图、排行榜和告警列表。

这也是你第一次接触 Go。有了前面的 JavaScript 和 TypeScript 基础，学 Go 并不难，重点其实是理解数据链路的设计思路。服务层推荐 Gin 或 Fiber，看板与后端保持数据一致。

提示5 · 数据产品最容易死在口径上

自检表要逐条过：原始数据是否正确入库，趋势和排名的计算逻辑是否一致，告警触发条件是否符合预期，看板展示和后端数据是否对得上，接口有没有统一返回结构和错误处理。数据类产品最容易出的问题不是程序报错，而是看板上的数字和数据库对不上。所以聚合的口径一定要在动手前就写在文档里，而不是留到联调时再猜。

5.2 按模块推进与自检

推进路线清晰：先做数据接入接口，再做窗口聚合，接着是告警规则，然后是看板接口，最后是前端看板。项目结构立好后先过一份验证清单：Go 服务能否正常启动，接入接口能否接收并存储数据，聚合任务框架是否搭好，前端看板能否展示基本图表。这四项是数据产品的四根柱子，缺任何一根后面都会返工。

六、三个作业的共同约束与行动建议

6.1 一份统一的验收标准

三个作业的交付物结构高度一致：线上演示链接、源码仓库（含 README）、需求文档、核心页面截图、六十秒演示视频。这说明课程在刻意统一验收尺度。无论你选哪个题目，这五项都要准备齐。

6.2 评分维度反过来提示了力气该花在哪

考试系统的评分维度是页面完整度、业务闭环、数据正确性、权限控制、工程交付。微服务大体对应服务边界、下单闭环、状态一致、监控和文档。数据平台的评分维度是需求对齐、数据链路、分析能力、前端展示、工程完整度。

你会发现，每个维度都分了基本要求和进阶要求。基本要求是及格线，进阶要求才是拉开差距的地方。比如权限控制，基本是访问边界清晰，进阶是服务端也做校验；比如数据链路，基本是能跑通，进阶是聚合支持增量更新。动手前先看一眼进阶要求，你的实现方式会不一样。

6.3 一条通用的动作序列

把三个作业的共性提炼出来，就是一条可以直接套用的动作序列：读需求，确认关键问题都有明确答案；拆任务，找到相对独立的模块边界；定规则，把核心业务规则显式写进文档和代码；连链路，把端到端路径真正跑通；做验收，按统一的交付物清单收口。

这条序列里，最容易被跳过的是第三步和第五步。跳过定规则，代码会失去判据；跳过验收，你以为完成了但其实没闭环。把这五步都走完，无论面对哪一个作业，你都能稳住。

6.4 三个作业的常见卡点对照

如果把历次实战里最容易卡住的地方列出来，三个作业各有各的坑，但坑的位置其实可以预判。

考试系统最容易卡在前端骨架和接口定义之间。很多人先埋头写接口，写完才发现前端要的字段和接口给的对不上，于是返工改接口。正确的做法是先把页面骨架和接口清单一起定下来，让两端在纸面上先对齐，再分别动工。第二个坑是判分规则写成了散落在各处的条件判断，而不是收敛成一个清晰的判分模块。规则一旦散开，后面想加题型或者加复核功能就会非常痛苦。

微服务最容易卡在链路串不通。五个服务各自都能跑，但下单的时候库存预扣了却没确认，或者订单重复创建了。这类问题的根因往往不是代码写错，而是状态流没有在动手前画清楚。所以务必先画订单状态流和库存状态流，把预扣、确认、回滚三个动作的触发条件写明白，再动手写服务。第二个坑是前台体验被微服务架构带偏，用户端变得像几个接口的拼装，这时候要记住架构隐藏、体验统一。

数据平台最容易卡在口径不一致。看板上的趋势线和数据库里的数字对不上，往往是因为聚合窗口的起止时间、时区或者空值处理没有统一。解决办法是在聚合模块里把口径写成一份明确的说明，并且让看板和聚合共用同一套计算逻辑，而不是前端自己再算一遍。第二个坑是告警规则一开始就想做得很复杂，结果连最简单的阈值告警都没跑通，建议第一版先收敛到简单规则。

6.5 三个作业的横向对照

把三个作业放在一张表里对照，差异和共性会同时变得清晰。

这张表最有用的地方在于最后两行。最大风险提示你提前设防，进阶信号提示你用力方向。两者都不是靠多写代码能解决的，而是靠动手前的判断。

6.6 交付前的一张自检表

在提交之前，无论哪个作业，都可以用同一张表快速过一遍：线上链接是否可访问且功能真实可用；源码仓库是否包含完整的说明文档，涵盖项目简介、核心页面、技术栈、本地启动步骤和环境变量清单；需求文档是否随项目一起提交；核心页面截图是否覆盖了主要流程；六十秒演示视频是否覆盖了关键角色或关键链路。

这五项里，最容易被敷衍的是演示视频。但它在评审里的权重并不低，因为它最直观地暴露了你是否真的跑通了闭环。录制之前先把流程走一遍，确保每一步都顺利，再正式录。

6.7 什么叫真正可演示

三个作业都要求交付可演示的产品原型，但可演示这个词有它的门槛。它不是指某个页面能打开，而是指一个不熟悉你项目的人，能在不看源码的情况下，独立走完一条核心链路并得到预期结果。

拿考试系统举例，可演示意味着评审能用学生账号登录、参加一场考试、提交并看到分数，同时能用管理员账号创建一场考试并看到提交记录。任何一环需要你本人在旁边解释或者手动改数据，都说明闭环还没真正成立。微服务和数据平台也是同理，可演示的判定标准始终是别人能独立走通，而不是你能演示通。

所以，在交付前请找一个没参与开发的人，让他自己试着走一遍。他卡住的地方，就是你需要补的地方。这个测试比自查一百遍都有效。对 Easy-Vibe 的学习者来说，把可演示当成一条硬约束，会让你在整个开发过程中都带着验收视角，而不是等到最后才想起要收口。

提示6 · 先选一个题目，把它走到交付

三个作业不需要同时开始。选一个最贴近你目标方向的题目，完整走到交付为止。走完一遍之后，你带走的不是某个框架的用法，而是面对一份完整需求时的稳定拆解动作。这个动作，才是这三个作业真正想留给你的东西。

七、收尾

三个作业，三种形态，一套方法。角色权限、服务协作、数据链路，看起来是三个不同的领域，但读需求、拆任务、定规则、连链路、做验收这五个动作始终没变。技术栈会更新，框架会替换，这套拆解动作不会过期。

Easy-Vibe 的约束和审查清单之所以重要，也正是这个原因：它把「怎么做才对」提前写清楚，让你在动手前就有判据，而不是等到交付时才发现方向偏了。把约束写清楚，永远比多写几个功能更能保证交付质量。
