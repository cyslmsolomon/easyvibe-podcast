一、这一集在解决什么问题

「把网站发到网上」这句话听起来像一句废话，但它是新手从「本地能跑」跨到「别人能用」之间最大的一道坎。原文在这一章的导读里给了一个非常贴切的比喻：你写了一篇文档，只有自己电脑能打开；发到博客之后，所有人都能看到。部署干的就是这件事，只不过搬上去的不是一篇文档，而是一个完整的网站。

这一章的任务，是把「上线」这件事从「一键按钮」升级成「我清楚地知道发生了什么」。原文铺了四层内容：

  1. 决策层——先用三个问题把平台选型变成条件筛选；
  2. 托管层——逐一拆解 Vercel、Cloudflare Pages、Netlify 等免费/低成本平台，讲清额度、用法与关键限制；
  3. 常驻层——Railway、Zeabur、Render、Fly.io 四个需要进程常驻的候选项；
  4. 自建层——买服务器、SSH 连接、安全组放行、环境初始化，以及静态站与容器编排两条上线路径。

音频稿按「先决策、后托管、再常驻、最后自建」的顺序重排了这四层。一句话概括这一集：部署选型不是挑一个最好的平台，而是回答三个问题之后，剩下的那个选项自己会浮出来。

三、决策图：先回答三个问题再谈平台

为什么要有决策图？因为新手面对部署时最常见的状态不是不会操作，而是不知道该往哪走。市面上平台几十个，每个都宣称自己最简单、最便宜、最快，于是很多人开始横向比较参数，比了三天，项目还没上线。决策图的作用，是把这场无止境的比较提前终止掉：先用三个条件把范围收窄，再在剩下的两三个里随便挑一个动手。

原文的决策图正是本集最值得记住的一段。它把「该选谁」这个开放题，拆成了三个判断题。

第一问：需要 24 小时在线吗？ 不需要——文档站、博客、企业官网这类「用户来了才响应」的应用——静态托管或 PaaS 就够。需要——定时任务、爬虫、Bot、WebSocket 长连接——必须常驻型方案或自建服务器。

第二问：需要 GPU 吗？ 只调用大模型 API，普通平台即可；要自己跑开源模型、生成图片视频，就得看 GPU 云平台（Modal、Replicate、AutoDL 等）。

第三问：用户在哪？ 国内用户优先国内云或 Cloudflare；海外用户选择面很宽；两边都有就上 CDN，各放一份。

这三问的意义在于把选型从审美问题变成条件问题。很多人纠结「哪个平台最好」，但平台没有最好，只有匹配。建议你真的拿纸写下来这三条答案，再往下看。

四、不用买服务器的那条路

对大多数个人项目、Demo、作品集，买服务器是过度设计。这一层四个重点：

Vercel——Next.js 官方平台，前端首选。GitHub 登录 → 新建项目 → 选仓库 → 自动识别框架 → 填环境变量 → 部署，一两分钟上线。免费额度 100 GB 带宽/月、100 小时构建时间，自动 HTTPS 与全球 CDN。但三条限制必须记住：免费版 Serverless 函数执行上限 10 秒（一次大模型调用就可能超时）；不能跑常驻进程（无 cron、无长连接、无永远在线的 Bot）；存在冷启动。付费 Pro 20 美元/月可延长到 60 秒，但 AI 流式输出吃带宽，用户量上来后账单可能飙到 200 美元/月。

Cloudflare Pages——最大卖点是无限带宽。免费额度含 500 次构建/月、无限请求、Workers 10 万请求/天，全球 300+ 边缘节点，国内访问速度明显优于 Vercel/Netlify。配套 Workers AI 可在边缘跑开源模型，每天 1 万神经元免费额度。静态站首选，尤其面向国内用户的项目。

Netlify——100 GB 带宽/月 + 300 分钟构建时间，优势在插件生态（表单、图片优化、A/B 测试）与分支预览。相比 Vercel 更中立，不绑定框架。

其他——GitHub Pages 最省心，推送即上线；Hugging Face Spaces 免费小实例，专放 AI Demo；Modal 每月 30 美元额度，Python 函数即服务，适合需要 GPU 又不想管机器。

六、自建服务器：从选购到连上

选购看三件事：配置（个人项目 1 核 2 GB 起步，跑数据库或构建建议 2 核 4 GB）、地域（国内节点需备案但延迟低，海外节点免备案但延迟高）、镜像（选 Ubuntu 22.04，教程最多）。

连接：ssh root@<公网地址>。连不上是最常见的新手问题——直接把报错复制给 AI：「我用 ssh 连不上，报错是 xxx，帮我排查」，它会从网络、安全组、防火墙、密钥权限逐项带你排除。

双层防火墙（本集最该记住的实操点）：云厂商安全组是外层，服务器内 ufw 是内层，两层都放行端口才通。典型症状「程序跑起来了但浏览器打不开」，十有八九是安全组没开。必开端口：22（SSH，建议限制为自家 IP）、80（HTTP）、443（HTTPS）；3000–3999 调试端口用完即关。

七、两条上线路径与上线之后

环境准备好之后，原文给出两条最常用路径。

路径 A：纯前端静态站。 本地 npm run build 生成 dist/ → 用 scp 或 Git 把目录传到服务器 → 在 Nginx 配置里把 root 指向 dist → 配 try_files 让未命中文件回退到 index.html（缺了这条，前端路由一刷新就是 404）→ 建软链接启用配置 → nginx -t 校验语法 → 重载服务 → 域名解析 A 记录 → 用 certbot 一条命令申请证书并自动写入配置。

路径 B：容器编排。 写一份 docker-compose.yml，把数据库、后端、前端一起声明进去，写清端口映射、数据卷与 depends_on 依赖。服务器装好 Docker 后，docker compose up -d 全部拉起，docker compose logs -f 看日志。它的价值不只是省事，更在于环境可复现——本地跑通的这份配置，换一台机器也能跑出一样的结果。

怎么选：只有前端，走 A，轻、快、省资源；多服务互相依赖，走 B，一次编排，之后迁移和扩容都方便。

上线之后还有三件事容易被忽略。 一是备份，数据库定时导出并放到另一处，别和服务器放在同一块盘上。二是监控，最起码要知道服务是不是还活着，一个简单的存活探测或第三方拨测就能覆盖大部分场景。三是日志，把访问日志和错误日志留存下来，出问题时你会非常需要它们。很多人把上线当成终点，其实上线只是运维的起点。

十、实践提示

提示1 · 用「三问法」写一张选型便签

拿一张便签，写下：是否需要 24 小时在线、是否需要 GPU、用户主要在哪。三个答案写完，再去平台列表里对号入座。你会发现候选通常只剩一两个，纠结时间从几小时降到五分钟。

提示2 · 读懂限制条款，而不是读宣传语

打开任意一个平台的定价页，直接跳到 Limits 那一节，把「超时秒数」「休眠策略」「带宽上限」三条抄下来。免费层的真实成本全部写在这里，首页的「Free Forever」不会告诉你。

提示3 · 故意制造一次「端口不通」，再修好它

在安全组里临时关掉 80 端口，刷新页面确认访问失败，再打开。这五分钟能让你记住「程序跑着 ≠ 外面能访问」，比读十遍文档都管用。

提示4 · 初始化一次做到位，然后立刻打快照

非 root 用户、密钥登录、防火墙、Docker 一次配好，马上在控制台创建快照。等你哪天把环境改崩，会非常庆幸自己花过这两分钟。

提示5 · 上线一个最小项目，而不是继续比较平台

今天挑一个免费平台，把手里最小的那个项目真的推上去一次。部署这件事的知识，只在你亲手走完一遍之后才真正属于你。
