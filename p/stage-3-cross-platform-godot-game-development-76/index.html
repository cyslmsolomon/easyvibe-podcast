一、这一集在解决什么问题

前面几集讨论的都是「AI 怎么帮你写代码、做产品」，这一集把镜头切到游戏开发，回答一个入门者真正会问的问题：我想做个游戏，该用什么引擎，又该从哪一步开始动手？

原文选的答案是 Godot，一篇讲透三件事：它是什么、什么时候该选它、以及用它的最小上手路径是什么。更难得的是，原文没有停在概念层，而是给了三条完整可跑的练习路线——横版、像素、3D——每条都配一个已经正式发行的参考作品。

全篇的骨架是这样的：

  1. Godot 是什么——免费、开源、不抽成，2D 不是压扁的 3D；
  2. 什么时候该选——独立团队、原型、教学、Game Jam 是主场，已有重资产或目标主机时要谨慎；
  3. 语言怎么选——GDScript 为主，C# 次之，C++ 只做少数底层模块；
  4. 节点、场景、脚本——场景负责「这里有什么」，脚本负责「它会做什么」；
  5. 环境准备——渲染器怎么选、版本差异、一次只做一个游戏；
  6. 三条练习路线——横版（Primal Light）、像素（Dome Keeper）、3D（Wrought Flesh）。

如果用一句话概括这一集：先做出一个最小的可玩循环，验证它成立，再一层层往上加内容。 这条纪律在横版、像素、3D 三条路线上完全一致。

原文的能力点分散在概念讲解与三条练习路线中。我按「选型 → 认知 → 环境 → 原型 → 打磨」五个环节重新排序。

三、Godot 是什么：三条硬事实

原文给出的定位非常明确。Godot 是一套免费、开源的 2D 与 3D 游戏引擎，编辑器、运行时和主要功能都开放源代码，不按营业额收取引擎抽成。它可以制作 Windows、macOS、Linux、Web、Android 和 iOS 游戏；主机平台通常还需要获得平台方开发资格，并使用官方或第三方移植方案。

第二条硬事实最容易被忽略：

Godot 的 2D 不是把 3D 摄像机压扁以后凑出来的。

它有独立的 2D 渲染、物理、TileMap、动画、粒子和灯光系统。这不是宣传话术，而是决定你做横版、俯视角和像素游戏时会不会被三维管线绊住脚的关键。

第三条是成熟度证据。官方 Showcase 里能找到《Dome Keeper》《Cassette Beasts》《Brotato》《The Case of the Golden Idol》《Wrought Flesh》等项目，而且收录标准要求项目已经发行或有公开试玩版本，并具备可访问的商店页面与一定完成度。

提示1 · 判断引擎成熟度，看它发行了什么，而不是看它演示了什么

Demo 和已发行作品之间隔着一条很宽的沟：存档、多分辨率、性能、商店合规、更新维护。原文特意强调 Showcase 的收录标准，就是在提醒你用「有没有人真的靠它发过游戏」来判断，而不是看宣传视频有多炫。

四、什么时候该选，什么时候别选

适合的情况：准备做 2D 或中小规模 3D 游戏，希望很快做出可玩版本，不想一开始就背上复杂的引擎授权和工程配置。尤其适合独立团队、游戏原型、教学项目、Game Jam，以及需要同时发布桌面和 Web 版本的作品。

不适合的情况：

  • 团队已经积累了大量 Unity 或 Unreal 资源；
  • 依赖特定商业插件；
  • 目标是大型开放世界和顶级写实画面；
  • 准备发布到 PlayStation / Xbox / Nintendo Switch，却还没确认主机 SDK、移植服务和平台资格。

提示2 · 「跨平台」三个字里，最容易踩的是主机

很多人看到「跨平台」就默认主机也能一键导出。原文专门提醒：主机平台通常还需要获得平台方开发资格，并使用官方或第三方移植方案。跨平台指的是桌面、网页和移动端这条链路，不等于主机可直接导出。这个误解在立项阶段不澄清，到发布前会变成硬阻塞。

五、三种语言怎么选

语言适用场景注意事项
GDScript默认首选，与节点、场景、信号结合最好为 Godot 设计，写法紧凑，第一次学习最省事
C#团队原有 .NET 技术栈需下载 Godot 的 .NET 版本
C++接入原生库或性能敏感模块以 GDExtension 形式编写

原文给出的是一个常见的成熟项目组合：玩法和界面用 GDScript 或 C#，真正需要优化的少数底层模块再交给 C++。

背后是一条工程纪律——不要还没测性能就把所有东西重写一遍。很多新手听说 C++ 快就想全量重写，结果开发速度掉一个数量级，性能却未必改善，因为瓶颈可能在绘制调用、资源加载或算法本身。

先跑起来，再测量，最后才优化。

六、节点、场景和脚本：三个词撑起整个引擎

编辑器左边的「场景树」里，每一项都是一个节点，每种节点只负责一类事情：CharacterBody2D 管角色运动与碰撞，Camera2D 负责镜头，Label 显示文字，DirectionalLight3D 提供方向光。

把一组节点组织成树并保存下来，就得到一个场景。价值在于复用：一个玩家场景可包含角色、碰撞体、动画和摄像机，被主关卡重复使用；同一个敌人场景可实例化十次，而不用复制十套代码。

GDScript 则把行为挂到节点上。于是有了那句精炼的分工：

场景负责「这里有什么」，脚本负责「它会做什么」。

提示3 · 拆分要趁早，别等牵连了再拆

原文给的拆法很朴素：玩家、关卡、HUD 和可收集物尽量各自负责一件事。原型很小时全塞在主场景里确实也能运行，但功能一多就会互相牵连。这条建议在所有引擎里都成立——结构债和技術债一样，越晚还利息越高。

七、准备开发环境

从 Godot 下载页获取当前稳定版；第一次使用 GDScript，下载标准版即可，只有确定使用 C# 时才需要 .NET 版。渲染器按目标平台倒推：

  • 主要做桌面 3D → 优先尝试 Forward+；
  • 需要照顾移动设备 → 先看 Mobile；
  • 2D、Web 或需兼容较老显卡 → 选择 Compatibility。

三个原型为了保持同一套运行环境，统一使用 Compatibility。实际验证使用 Godot 4.7.1 stable。

提示4 · 版本差异会吃掉你大量时间

使用更早的 Godot 4，个别菜单名称可能略有不同；如果是 Godot 3，不要直接照搬节点名称，因为 CharacterBody2D、TileMapLayer 等 API 已经发生变化。照着旧版本教程敲代码却一直报错，是新手最常见的时间黑洞。

另外记住两个快捷键：F6 运行当前场景，F5 运行主场景，场景还不存在时出现选择提示是正常的。

最后一条最重要：不要让 AI 一次生成三个游戏。 分别创建三个项目，每次只验证一种玩法。

八、路线一 · 横版：让路线和威胁一眼可读

参考《Primal Light》（Fat Gem 制作的线性 2D 动作平台游戏，已发行到 Windows、macOS、Linux 和 Nintendo Switch）。开发者在官方访谈中特别提到看重 Godot 的以像素为原生单位、信号系统和动画工具。

值得借鉴的不是美术，而是三个基础做法：

  1. 角色始终和背景有明显反差；
  2. 平台与危险物的边界清楚；
  3. 一段路线里总能看到下一个落脚点或目标。
玩家失败时应该知道是自己没有跳好，而不是看不清哪里能站。

练习原型 Skyline Courier 沿用这条思路：角色用暖色，平台边缘用高亮青色，右上角放持续发光的信标。

三步推进：

  1. 创建 1280×720 横版场景，放入地面、四个平台、玩家和右上角目标信标；
  2. 让玩家用 A、D 和方向键移动，空格跳跃，并与平台碰撞；
  3. 让目标信标持续发光，玩家靠近时显示「已送达」。

移动跑通后专门试四件事：角色会落到地面、不能穿过平台、空中不能无限跳、掉出画面后能回到起点。不要在这一步增加敌人和道具，否则很难判断是哪一层出了问题。

九、从原型走向正式横版

原型只证明「移动—跳跃—抵达目标」能成立。要接近正式发行项目，下一步不是堆十张地图，而是把这条短路线做扎实：

  • 用独立 Player 场景管理碰撞、动画和角色状态；
  • 增加土狼时间和跳跃输入缓冲，让晚一点或早一点按键也不显得生硬；
  • 用 AnimationPlayer 或 AnimationTree 管待机、奔跑、跳跃和受伤；
  • 用 Camera2D 设置前视范围和边界，避免镜头露出关卡外；
  • 用 TileMapLayer 或可复用场景搭关卡，不要在脚本里写死每块平台的位置；
  • 把抵达目标做成信号，让 HUD、音效和关卡切换各自响应。
画面升级不能弥补基础手感的问题。

十、路线二 · 像素：循环比画面重要

参考《Dome Keeper》（Bippinbits 制作的像素风生存采矿游戏，已正式发行）。玩家在攻击间隙向地下挖掘资源，再回到穹顶抵御怪物，并用资源升级装备。

最值得学的是循环清楚：离开安全区寻找资源 → 带着资源回来 → 资源改变下一轮能力。像素画面信息很多，但角色、资源、危险和可通行区域仍能迅速区分。

练习原型 Lantern Woods 保留「离开起点—寻找资源—看到计数变化」这条最小循环：三颗光晶用最亮的青色，背景限制在深蓝与绿色，右上角一直显示收集进度。

像素缩放的两条设置必须分开做：

设置作用具体做法
第一条决定画布和比例基础分辨率 320×180，窗口放大到 1280×720，使用整数缩放
第二条决定纹理采样2D 纹理使用 Nearest 过滤，不模糊像素边缘
运行时如果像素边缘发糊，先检查过滤方式，不要急着重画素材。

十一、从色块原型走向正式像素游戏

现在的树、道路和角色是简单像素块，适合验证比例和玩法，不是正式美术。沿《Dome Keeper》思路完善：

  • 先固定一套调色板，再画地表、角色和道具；
  • 使用 TileSet atlas、地形连接和 TileMapLayer 组织地图；
  • 用 SpriteFrames 管理走路方向和收集动画；
  • 让资源、出口和危险拥有稳定的颜色与轮廓，不要只靠文字说明；
  • 把「探索—收集—返回—升级」拆成几个可单独测试的状态；
  • 在 16:9、16:10 和超宽窗口检查黑边、扩展区域与 HUD 锚点。
像素风并不等于制作成本低。角色动画、地形拼接、不同分辨率和 UI 可读性都会消耗大量时间。先用色块验证循环，再投入正式逐帧美术，通常比先画一个月素材更稳妥。

十二、路线三 · 3D：先用空间和轮廓带路

参考《Wrought Flesh》（Miziziziz 制作的 3D 生物朋克动作 RPG，已正式发行）。规模与练习原型完全不同，但仍有可马上借鉴之处：不同区域要有清楚的色彩和轮廓，关键目标要在复杂场景里被看到，战斗或移动反馈不能只依赖 HUD 文字。

3D 原型 Signal Garden 先做最小灰盒：深色地面建立空间边界，粉色胶囊代表玩家，黄色晶体作为沿途参照，远处的青色发光门作为目标。方向光打开阴影，环境光保证暗部仍可读。

第一次学 3D，建议跟着官方的「你的第一个 3D 游戏」做一遍——从地面、角色和输入开始，再加入敌人、碰撞、动画、得分与重开，比直接下载大型模板更容易看懂。

十三、审查清单

  • 已从官网获取稳定版，且下载的是标准版（非 .NET 版）
  • 渲染器按目标平台选定，三个原型统一使用 Compatibility
  • 已确认自己使用的 Godot 版本，未照搬 Godot 3 的节点名称
  • 三个练习分别建了独立项目，没有一次生成三个游戏
  • 横版场景树至少能分出关卡、玩家和 HUD
  • 角色会落到地面、不穿平台、空中不能无限跳、掉出能回起点
  • 目标信标会发光，靠近有提示
  • 像素项目基础分辨率与整数缩放设置正确
  • 纹理过滤已设为 Nearest，像素边缘不发糊
  • 三颗光晶每颗只计数一次
  • 关卡用 TileMapLayer 或可复用场景，位置没有写死在脚本里
  • 已在 16:9、16:10、超宽窗口下检查黑边与 HUD 锚点
  • 3D 灰盒中玩家、参照物、目标门在摄像机里都能看到

十四、常见误区与纠正

误区为什么会犯正确的做法
看到「跨平台」就以为能上主机把桌面/移动跨平台与主机混为一谈主机需另确认 SDK、移植服务与平台资格
一上来就全量用 C++听说 C++ 性能最好先跑起来再测量，只把少数底层模块交给 C++

  • 选型边界：独立团队、原型、教学、桌面+Web 是主场；主机需另行确认。
  • 语言组合：GDScript 为主，C# 次之，C++ 只做少数底层模块；先测量再优化。
  • 核心概念：场景负责「有什么」，脚本负责「做什么」；尽早拆分。
  • 推进节奏：先搭场景 → 再加移动 → 最后给目标，每步只验证一件事。
